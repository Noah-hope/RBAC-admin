== 数据库设计概述

=== 设计目标

本系统集中管理多个业务系统的功能权限。数据库需要记录员工是谁、在哪些部门任职、管理员能管理什么范围、角色包含哪些权限，以及员工通过哪个部门来源获得了角色。同时需要保存权限申请、OA审批结果、执行结果和审计记录，使每次授权和撤销都能找到依据。

系统采用RBAC0模型，员工通过业务角色获得权限。组织岗位用于表达任职和资格，后台任命用于表达管理权限，两者分别保存。权限配置、角色分配和一般撤销通过OA审批后执行；离岗和员工停用引起的失效直接处理。

=== 存储方案与设计依据

数据库采用MySQL 8.4和InnoDB，字符集为utf8mb4，默认排序规则为utf8mb4_0900_bin。实体通过稳定内部ID关联，业务编码用于定位和对接，显示名称可以修改。UUID保存为CHAR(36)，日期时间使用DATETIME(6)并统一按UTC保存。

本文依据现有数据库逻辑模型、表元数据、建表SQL、不可变触发器、事务设计和后端实现整理。数据库结构沿用当前关系模型，文中ER图复用项目设计说明书已经采用的最新四页图。图中展示主要字段和关系，附录给出完整字段定义及外键引用。

== 组织与后台身份

=== 组织与任职的保存方式

company、department和position分别保存公司、部门和岗位。一个公司有多个平级部门，一个部门有多个岗位。employee只保存员工的统一身份和全局状态，具体在哪家公司、哪个部门和岗位任职，由employment记录。

这种分离可以表达兼岗：同一个员工可以拥有多条有效任职。员工离开某个岗位时结束对应任职记录，其他有效任职继续保留；以后重新任职时建立新记录，原来的结束历史仍然可查。

=== 账号、范围和任命分别负责什么

admin_account保存后台登录账号、密码摘要和凭据版本；admin_session保存已签发会话的标识、有效期和撤销状态。会话表不保存JWT原文。总管理员可由部署初始化，普通后台账号关联员工身份。

management_scope确定一个公司、一个部门；scope_system列出该范围可管理的业务系统。admin_appointment把账号与一个范围连接起来，表示一次独立任命。一个账号可以有多项任命，每次操作选择其中一项，服务端按该项范围检查目标。

例如，管理员同时负责A公司销售部和B公司财务部，数据库中保存两项任命。办理A公司的申请时，只使用A公司那项任命中的部门和系统集合，不能把另一项任命的系统集合拼进来。

=== 资格变化如何即时生效

账号停用、员工全局停用、密码重置和最后一项管理资格结束，都会影响旧会话的可用性。账号记录中的credential_version、session_epoch与会话中保存的值共同用于检查，服务端还会读取当前员工状态、任命与范围。

范围变化时保存新的scope_version，并检查原范围关联的未结束申请。如果新范围实质上不能覆盖某份固定申请的全部目标，该申请整份失效；仅增加无关系统或原提交人离任，不单独使仍被覆盖的申请失效。

== 目录、角色与独立来源

=== 系统、目录和权限项

business_system保存业务系统，directory_node保存导航与功能节点，通过parent_id连接父节点。permission保存独立功能操作，以及每个系统唯一的系统进入权限。

功能与操作通过permission.function_id关联：一个功能可以有多个操作。功能节点还可以通过directory_node.visibility_permission_id选择本功能中的一个操作，作为菜单是否显示的依据。这两条引用分别表达“操作属于哪个功能”和“菜单选哪个操作判断可见”，因此在ER图中分别连接。

系统与进入权限在同一事务中创建。目录保存前检查最终树无环、同系统、菜单绑定合法，再一起提交。

=== 角色配置与配置历史

business_role保存角色名称、归属及配置版本，role_permission保存角色当前生效的权限集合，展开角色与权限的多对多关系。角色元数据与权限配置使用不同版本。

角色配置审批成功并执行后，系统替换role_permission中的有效集合，递增配置版本，同时向role_configuration_history追加一份完整配置快照。因此，一个角色可以对应多条配置历史，每条历史记录只属于一个角色。

员工的有效角色授权使用更新后的权限集合，历史配置保留过去审批和执行的内容。

=== 为什么授权要区分来源

authorization_source按员工、公司、来源部门和业务系统记录一个独立来源。grant_baseline保存这个来源与某个角色之间的持久关系及版本，role_grant保存每一次具体授予。grant_employment_evidence保存授予时采用的任职依据。

例如，员工在销售部和财务部兼岗，两部门授予相同角色时分别保存来源。销售部撤销自己的授予，只结束其对应的role_grant，财务部的授予仍有效。

一般撤销结束选中的具体授予，并推进关系版本。离岗关闭来源时还会推进source_epoch，即使当时没有有效授予也会记录这个变化。旧申请保存的是提交时的周期和版本，迟到的批准无法绕过已经发生的关闭。后来重新任职、重新授权，需要建立新的授予记录。

有效权限查询检查员工及适用任职，读取周期一致的来源、有效授予和角色当前配置，并检查系统、目录和进入资格。同一公司、同一系统的合法来源取权限并集，全部读取在同一个快照内完成。

== 固定申请、OA与执行

=== 草稿与提交后的固定内容

change_request保存申请类型、内容、原因、提交依据和办理状态。change_target把申请涉及的角色、员工、来源和具体授予列成可检索的明细，便于执行复核，以及在范围、来源变化时查找受影响的申请。

草稿可以编辑。正式提交时，系统固定申请内容、目标清单、原管理依据及相关版本，并保存规范字节和内容摘要。OA审批和后续执行都针对这份固定内容，提交后不再通过修改草稿改变待执行事项。

role_change_claim和relation_change_claim保存正在办理的角色配置或授权关系占用，阻止同一目标同时出现互相冲突的申请。申请结束后释放占用；历史仍保留在申请、执行和审计记录中。

=== OA投递、关联和结果

oa_outbox保存需要发送给OA的待办、重试时间和领取租约。申请提交和投递待办一起落库；后台发送器随后调用OA，网络等待放在数据库事务外。可靠取得OA审批编号后，oa_link保存本地申请与外部审批的对应关系。

service_identity记录受信服务主体及其绑定系统或OA实例。oa_callback_event保存收到的回调事件，按OA实例和事件编号防重；oa_final_result保存一份申请的最终批准或驳回结果。同一个事件重复发送、不同事件重复报告相同结果，都不会形成第二份业务执行。

=== 批准结果与实际执行分开保存

OA批准表示同意这份申请，实际生效还需要本地事务完成角色配置或授权修改。执行前重新检查固定内容、原范围覆盖、来源周期和目标版本；任何目标已不再符合条件，就不能执行整份申请。

execution_success记录一份申请已经成功执行的凭据，并关联成功审计。业务修改、成功凭据、申请状态和占用释放在同一事务中提交。execution_attempt记录执行尝试；业务失败先回滚，随后再用独立事务保存失败尝试，保存前重新确认没有已经成功的结果。

audit_event保存操作者、目标、来源范围、原因和当时的变化快照；audit_subject为事件关联员工、角色等稳定目标，支持后续筛选。历史展示使用记录时的快照，避免当前名称或任职变化改变旧事件的含义。

== 导入、预览与可靠性

=== 文件导入如何落库

import_file保存上传文件的名称、摘要、大小和受控存储位置，文件本体放在文件存储中。import_batch保存来源批号、处理类型、冻结输入和执行结果；import_plan_row保存预检产生的规范行、候选ID、稳定编码、字段前后值与依赖版本，import_issue保存预检问题。

预检只生成待执行计划。首次导入缺少组织编码时，可在计划中为明确的组织路径分配候选ID和编码，正式提交时再检查冲突，并依次建立公司、部门、岗位、员工和任职。organization_mapping保存来源组织路径到正式组织的映射，employee_source_identity保存来源员工标识到内部员工的映射。

正式导入按冻结计划逐项重新校验。整批业务修改、相关失效、审计和批次成功结果在同一事务中保存，任意一行失败都会回滚整批。成功来源批号长期防重，重复提交同一成功批次返回原结果。

=== 影响预览如何保持一致

impact_preview保存预览输入、当时的管理依据、依赖版本及到期时间；preview_item保存可分页查看的安全明细。统计和各页明细来自同一份预览，避免翻页过程中重新计算而出现前后不一致。

预览有效期为五分钟。保存或提交时仍需检查当前身份、范围和依赖；过期或关键依赖变化后重新预览。预览编号用于定位这份计算结果，本身不能授予管理权限。

=== 重复请求与事务协调

http_idempotency按主体、HTTP方法、规范路径和幂等键记录请求摘要、处理租约及安全响应。相同内容重试可以在重新鉴权后回放原结果；相同幂等键换成其他内容则冲突。它处理HTTP重试，OA事件编号、执行成功凭据和成功导入批号分别处理各自的长期防重。

mutation_guard只有一条固定写协调记录。后端在正式写事务开始时锁定这条记录，使参与协议的写事务按顺序完成资格复核和提交。它协调数据库写入，不代表管理员资格或员工业务权限。

== 数据一致性与事务实现

=== 原子保存的实际过程

后端的CommandBoundary使用Spring TransactionTemplate开启独立的READ COMMITTED事务。首先执行以下加锁读取，要求固定记录存在：

[source,sql]
----
SELECT revision FROM mutation_guard WHERE id=1 FOR UPDATE;
----

取得锁后重新检查当前账号、员工和所选任命资格，再创建绑定当前线程、数据源和事务连接的WriteContext。领域写入和审计追加共用这个上下文；提交前检查事务是否已标记回滚，随后更新写协调记录的内部revision，由事务管理器统一提交。

例如管理员范围替换，会一起保存范围系统集合、任命变化、需要撤销的会话、受影响申请失效以及审计。只要其中一步失败，包括最后的审计写入失败，事务就整体回滚，原范围和相关状态一起保留。WriteContext会拒绝在事务结束后、其他线程或其他数据源上继续使用。

这个单写协调方案适用于一期的一致性实现。它使本地短写事务串行执行；文件解析、密码慢哈希和OA网络调用在事务外完成，避免持锁等待外部系统。

=== 当前记录、历史和版本

当前有效集合放在role_permission、scope_system等关系表中；角色配置历史、固定申请、审批结果和审计使用历史记录或快照保存。JSON快照保存当时的审批、差异和报告，当前角色权限集合仍由关系表表示。

任职、任命和具体授予结束后保留原行，重新建立时使用新ID。授权来源和关系基线持续保留并推进版本，避免删除之后丢掉旧申请的失效依据。active_slot是数据库计算的当前有效标记，配合唯一键限制当前记录，结束历史的槽值为NULL，允许保留多段记录。

业务版本分开表达不同变化：scope_version用于范围，appointment_version用于任命，configuration_version用于角色有效配置，source_epoch用于来源周期，relation_version用于同来源同角色关系。row_version用于内部并发控制，mutation_guard.revision用于内部写提交顺序，各自承担不同职责。

=== 查询快照与访问路径

ReadBoundary开启独立的REPEATABLE READ只读事务，先读取写协调记录建立快照，再完成当前资格检查和结果查询。有效权限计算和安全审计查询在同一快照内读取需要的表，保证一个响应采用一致的事实。

[cols="3,6",options="header"]
|===
|查询目标 |现有设计采用的定位路径
|登录及会话 |按login_name定位后台账号，按会话ID和token_jti检查会话。
|员工有效权限 |employee_key定位员工，经员工、公司、来源部门和系统找到来源，再关联基线、有效授予及角色权限。
|范围变化影响 |按scope_id定位相关申请，再检查change_target中整份目标清单的覆盖情况。
|审计列表 |按来源公司、部门、系统和发生时间过滤，按occurred_at、id稳定排序；员工和角色筛选经audit_subject定位。
|后台恢复 |按待办或申请状态、下次重试时间定位候选记录，逐份进入受控写事务重新检查。
|===

# UC-05 查询员工有效权限

版本：V1.1，2026-10-15。状态：功能权限范围已按用户确认修订，其他业务规则沿用原基线，供小组设计与验收使用。

本轮更新：按用户要求限定为功能权限管理，移除业务数据权限设计；保留公司授权上下文、任职持续资格、审批执行及历史规则。

### 当前需求基线（2026-10-15，功能权限修订）

- 一期实现 RBAC0 权限管理：员工经角色获得权限，无角色继承、直接用户授权或显式拒绝。外部系统只做简单 HTTP 调用演示，不实现其内部业务。
- 角色属于一个公司和一个业务系统，可限定部门；公司级角色要求本公司有效任职，部门级角色要求在该部门直接有效任职，不自动覆盖下属部门。岗位不自动绑定角色；任职条件与权限需要均未改变时，不因岗位名称变化更换角色。
- UC-05/06 按“员工＋当前公司＋业务系统”计算权限。仅合并该公司、该系统内的有效角色；系统进入资格与功能权限也必须来自该公司、该系统。公司上下文隔离的是功能授权来源，不定义业务数据访问范围。
- 任职变化后不再满足角色条件的授权立即失效；有其他符合条件的兼岗则保留该授权。员工全局停用使其全部业务授权及公司专员任命失效，不区分临时停用与离职。保留历史，不物理删除；恢复身份或任职不自动恢复失效授权，业务角色重新申请 OA 批准，专员由总管理员按 UC-07 重新任命。
- 当前 RBAC 系统只管理功能权限。目录登记系统进入权限与功能操作，角色配置是否授予；不定义、保存或返回业务数据范围，不设计本人记录判断或行过滤规则。
- 员工、公司、部门使用稳定内部 ID；首次导入以源唯一用户名建立员工映射，组织分配稳定编码，更名不改变身份。人员变更模板明确新增任职、结束任职、停用、恢复等动作，不从文件缺行推断离职。
- 一期使用至少两个公司、两个系统的代表性数据，覆盖多角色、兼岗、公司授权隔离、功能操作独立与去重、审批生效、撤销、失效及重新申请。其余资料后续逐步补齐。

以上为本轮已确认规则，详细流程与验收必须遵循；描述的是需求设计，不代表代码已实现或真实外部系统已完成对接。

## 1. 用例概述

| 项目 | 说明 |
| --- | --- |
| 编号与名称 | UC-05 查询员工有效权限 |
| 目标 | 为接入业务系统提供指定员工在该系统当前有效的权限集合 |
| 主要参与者 | 已登记并通过服务身份认证的业务系统后端 |
| 被查询对象 | 已由业务系统识别的员工；员工不必登录权限中心 |
| 触发 | 业务系统登录后加载菜单，或刷新员工权限展示 |
| 前置条件 | 调用方可信、绑定的业务系统有效；业务系统从自身登录上下文取得员工统一标识 |
| 成功结果 | 一次返回当前公司、当前系统的进入资格、菜单标识和有效功能操作集合；没有进入资格时返回空集合 |
| 后置条件 | 不创建、修改或撤销任何授权，仅记录必要调用信息 |

这里的菜单是员工在 OA、HR 等业务软件中使用的菜单，不是权限管理专员在权限中心管理后台的菜单。业务系统负责页面、路由和实际渲染，权限中心提供已登记目录对应的授权结果。

UC-05 查询“有哪些功能权限”，UC-06 检查“是否拥有指定操作权限”。调用 UC-05 不经过 OA 审批，也不触发申请流程；它只读取已经生效的授权。

### 统一管理与公司边界（本轮已确认）

“公司权限管理专员”即公司授权管理员（早期图中称部门授权管理员）；总公司和各分公司各自指定 1～3 名，可仅一名。公司人员范围按明确公司归属及所属部门层级计算，遇到另一个公司节点停止，不因总公司位于组织树上层而包含全部分公司。

权限中心总管理员可管理所有公司、所有系统及所有公司专员，也可办理 UC-02～04；公司专员仅在本公司获准系统内办理。双方的业务角色配置、分配、撤销均经过 OA。总管理员跨公司办理时仍明确目标公司；每份申请按一个公司归属保存，系统状态、目标合法性及版本校验照常执行。

一期公司管理范围只限定人员、角色归属与获准系统，不逐项指定可分配角色或可申请操作。获准系统目录内的合法权限可以申请，角色授权内容仍由 OA 审批。后台资格不自动产生外部业务系统进入权限。


## 2. 已确认规则与本稿约定

已确认并沿用：

- 一次返回系统进入资格、可见菜单和允许的功能操作集合。
- 一个角色具有组织归属并属于一个业务系统；同公司、同系统可有多个角色。员工允许兼岗和跨系统多角色。
- 只合并当前公司、当前业务系统的有效角色权限，重合功能权限去重。
- 撤销某个关联后，其他有效角色提供的权限仍然保留；员工身份停用时不提供可用权限。

菜单可见条件已由用户确认；其余实现约定如下：

1. **菜单可见条件（已确认）**：目录为每个可打开的功能菜单明确关联其“查看／进入”权限；获得对应权限才返回该菜单。仅有编辑、审批或导出权限不自动推导查看权限。必要的父级目录仅作为导航容器。已有查看权限时可直接用于菜单可见判断，不强制另建进入权限；没有查看操作的功能入口再考虑对应的进入权限。
2. 上述规则替代早期草稿 A08“任一操作即可显示菜单”的约定。配置角色时应提示缺少菜单查看权限，不能偷偷补授权限；具体菜单与查看权限的映射在 UC-01 的目录设计中落实。
3. 一期按当前数据库有效授权查询，不引入权限缓存，也不把返回集合长期固化为登录令牌中的授权依据。
4. 员工不存在、停用或没有进入资格，统一返回 canAccessSystem=false 和成功的空菜单、空操作集合，不返回姓名、组织等无关资料；服务身份无效、越系统请求及数据库故障分别返回错误。
5. 系统进入权限作为独立的必要前提；没有它即返回不可进入及空集合，有它也不自动获得功能权限。

### 系统进入权限（已确认）

先验证调用身份、绑定系统及员工有效性，再查当前公司、当前系统全部有效角色是否提供 SYSTEM_ACCESS。没有进入资格时返回 `canAccessSystem=false`、空 menus 和空 operations，即使保存着功能授权也不返回可用功能。

有进入资格时返回 `canAccessSystem=true`，再合并功能操作集合并生成菜单。仅有进入权限时两个集合仍可为空。SYSTEM_ACCESS 单独由 canAccessSystem 表达，不混入 operations。系统进入资格和菜单／操作必须来自同一次一致读取，避免并发撤权时产生矛盾响应。

判断公式：可用功能权限＝员工及系统有效 ∧ 当前公司、当前系统有效进入授权存在 ∧ 目标功能操作有效授权存在。进入资格可来自角色 A，功能权限来自角色 B；同公司、同系统即可，不要求同一角色。普通管理后台的账号登录仍属于 UC-09。

## 3. 调用身份与职责边界

```text
员工在 HR 登录
    ↓
HR 后端从登录上下文取得员工统一标识
    ↓ 使用绑定 HR 的服务身份
权限中心验证调用方与当前公司，并查询该员工在该公司的 HR 权限
    ↓
HR 根据返回标识显示菜单和操作入口，并在实际调用功能时执行权限校验
```

调用方凭据证明“哪个系统在调用”，并不能单独证明“当前登录的是哪名员工”。本用例以受信业务后端正确认证员工为前提；后端不得直接相信浏览器任意传来的 employeeId。凭据只保存在业务后端，具体认证机制在 API 设计中确定。

目标系统从已认证的服务身份确定；若请求也传 systemCode，必须与绑定系统一致，不能仅通过改参数读取另一系统权限。员工用稳定统一标识映射，不按姓名或职位名称匹配。

当前公司是本次功能权限计算上下文，并非固定取员工主公司。员工跨公司兼岗时分别查询；仅当前公司的角色参与合并。权限中心验证公司存在、有效且员工在该公司具有有效任职，不接受修改公司参数来混合授权。此处隔离的是授权来源与管理归属，不设计业务数据行过滤。

一期可模拟业务后端调用，无需实现 HR 或 OA 的登录功能；模拟仍使用绑定系统的调用身份。

## 4. 输入与输出

| 输入 | 说明 |
| --- | --- |
| 服务调用凭据 | 验证调用方并确定允许查询的业务系统 |
| 当前公司标识 | 必填；调用方提供当前业务公司，权限中心验证公司有效及员工任职，不跨公司合并 |
| 员工统一标识 | 由受信业务后端从已认证员工身份取得 |
| 系统编码（若接口保留） | 必须与服务身份绑定系统一致 |
| 请求编号 | 关联调用与排错记录，不是授权凭据 |

| 输出 | 说明 |
| --- | --- |
| 系统编码 | 当前调用方所属系统 |
| canAccessSystem | 员工在该系统是否具有有效进入资格；与菜单、操作共同返回 |
| 菜单集合 | 目录编码、父级编码、必要显示名称，以及导航容器标记；不包含未授权兄弟菜单 |
| 操作集合 | 功能编码及操作权限编码，每个有效操作只返回一次 |
| 请求编号 | 对应本次调用，便于排错 |

示例仅说明数据含义，字段和编码不是老师原始清单或已定 API：

```json
{
  "systemCode": "hr",
  "companyId": "COMP_BRIDGE",
  "canAccessSystem": true,
  "menus": [
    {"code": "employee", "parentCode": null, "name": "员工信息", "containerOnly": false}
  ],
  "operations": [
    {"menuCode": "employee", "permissionCode": "employee:view"},
    {"menuCode": "employee", "permissionCode": "employee:edit"}
  ],
  "requestId": "example-query-001"
}
```

没有进入资格时 canAccessSystem=false，menus 和 operations 均为空数组；有进入资格但无功能授权时 canAccessSystem=true，两集合仍为空。以下仅编辑场景均以有进入资格为前提：若只配置编辑权限而未配置查看，操作集合仍如实返回已授予的编辑权限，菜单不因此出现；不能把菜单不可见误当成操作从未授权，实际接口仍按 UC-06 检查。

没有进入资格的响应示例：

```json
{"systemCode":"hr","companyId":"COMP_BRIDGE","canAccessSystem":false,"menus":[],"operations":[],"requestId":"example-query-002"}
```

## 5. 正常流程

| 步骤 | 参与者操作 | 权限中心处理 |
| --- | --- | --- |
| 1 | 业务后端发送查询 | 校验必填字段、服务身份及系统绑定关系 |
| 2 | 等待结果 | 解析统一员工标识，检查员工与系统状态；无效调用拒绝，员工不可用则返回 canAccessSystem=false 和空集合 |
| 3 | — | 一致读取当前公司、当前系统有效角色关联，过滤已失效关联并核对当前任职，先计算进入资格；无资格立即返回 false 和空集合，有资格再读取功能授权 |
| 4 | — | 读取这些角色的有效功能权限；忽略草稿、待审批变更、停用权限和跨系统内容 |
| 5 | — | 按“当前公司＋系统＋功能＋操作”合并权限集合，相同操作只返回一次 |
| 6 | — | 根据有效查看/进入权限生成菜单集合，补充必要导航祖先并标记仅容器 |
| 7 | — | 记录必要调用摘要，返回进入资格、菜单与操作的一致结果 |
| 8 | 业务系统展示入口 | 将目录标识映射为本系统页面；后续具体访问由业务后端按 UC-06 校验 |

同一次响应的菜单与操作基于同一份一致的授权读取结果生成，避免恰好发生撤权时两部分相互矛盾。并发变更的读取一致性在数据库设计中落实；结果仅代表本次读取时的状态，不保证之后永远有效。

## 6. 合并与菜单规则示例

以下返回功能权限的示例均以该员工已有当前公司、当前公司、当前系统进入资格为前提。

| 有效来源 | 查询结果 |
| --- | --- |
| HR 角色 A：查看；HR 角色 B：编辑 | 返回查看、编辑；查看对应菜单可见 |
| HR 角色 A：查看；HR 角色 B：查看 | 查看只返回一次 |
| 撤销上述 B，A 仍有效 | 查看仍有，不因撤销一个重合来源而丢失 |
| HR 查看角色与 OA 审批角色并存，调用来自 HR | 只返回 HR 查看，不返回 OA 审批 |
| 桥梁公司 OA 查看、水利公司 OA 编辑，分别查询 | 分别返回查看、编辑，不跨公司合并功能权限 |
| 仅子菜单有查看权限，父级本身没有页面权限 | 返回子菜单及必要父级容器，不授予父页面或兄弟菜单权限 |

功能权限按操作独立判断：有查看不意味着有编辑，有编辑不自动授予查看。多个有效角色只对同公司、同系统的操作集合取并集，不形成业务数据范围。

功能或操作停用时不作为有效授权返回。按 [UC-01_维护业务系统与权限目录.md](UC-01_维护业务系统与权限目录.md) 的一期设计约定，停用导航目录使子树功能及操作暂不参与有效授权；恢复父级不恢复单独停用的子节点或已撤销关联。这是目录有效性过滤，不是角色继承或权限继承；目录缺失、循环等完整性错误返回服务错误，不拼出错误导航树或默认放行。

## 7. 替代与异常流程

| 编号 | 条件 | 处理 |
| --- | --- | --- |
| E01 | 缺少员工标识、格式错误 | 参数错误，不查询任意默认员工 |
| E02 | 调用凭据缺失或无效 | 认证失败，不返回菜单或权限 |
| E03 | 请求系统与调用方绑定系统不同，或该系统停用 | 拒绝调用，不返回其他系统权限 |
| E04 | 员工不存在、停用或没有有效角色权限 | 成功返回空集合，不泄露额外身份详情 |
| E05 | 角色配置/分配仍待审批，或批准后尚未执行 | 只读取当前有效授权，不能提前应用待执行方案 |
| E06 | 角色撤销仍待审批 | 该申请不改变当前权限；如另有停用等变化，按实际有效状态处理 |
| E07 | 重合权限或跨系统同名编码 | 当前系统内按操作合并，跨系统不混淆 |
| E08 | 数据库不可用或必要目录数据损坏 | 返回服务错误，不伪装成成功空集合或默认放行 |

查询失败时业务系统应提示权限暂不可用；不能把错误当成允许访问。具体受保护操作仍需后端校验，不能依赖隐藏按钮来防止访问。

## 8. 数据与事务边界

读取 Employee、Application、EmployeeRole、Role、RolePermission、Permission 及菜单目录；写入必要调用日志，不写授权关系，不生成 OA 申请。

查询只使用已提交的有效数据，菜单与操作从同一份结果生成；数据库事务仅覆盖本地读取，不跨业务系统网络调用。日志记录请求编号、调用系统、必要员工标识、时间和结果即可，不记录原始服务凭据或无关人员资料。

权限撤销执行成功后发起的新查询应反映新状态。一期不实现缓存或主动推送；已打开页面可能尚未刷新，业务后端仍须检查后续操作，不把旧菜单结果当作长期通行证。

## 9. 结构化功能分解

```text
查询员工有效权限
├── 校验输入、当前公司及业务调用身份
├── 确定目标系统与员工状态
├── 查询当前系统有效进入授权，无资格返回不可进入和空集合
├── 查询当前系统的有效功能角色和权限
├── 合并有效功能操作集合并去重
├── 生成可见菜单与必要导航容器
└── 记录调用摘要并返回结果

业务系统：根据标识展示入口
UC-06：返回是否拥有指定功能权限；业务后端执行功能访问拦截
```

这是功能分解，不要求每一步独立部署。UC-06 可独立调用，不要求先调用 UC-05 才能校验权限。

## 10. 验收示例

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| UC05-T01 | 员工有 HR 查看、编辑功能权限 | 一次返回对应菜单和两个操作 |
| UC05-T02 | 两角色提供相同查看操作 | 查看只返回一次 |
| UC05-T03 | 相同查看操作有两个有效来源 | 返回一个查看权限 |
| UC05-T04 | 仅授予查看，未授予编辑 | 返回查看，不推导编辑权限 |
| UC05-T05 | 撤销一个查看来源，另一查看来源仍有效 | 后续新查询仍返回查看 |
| UC05-T06 | HR 调用，员工同时拥有 OA 权限 | 不返回 OA 菜单或操作 |
| UC05-T07 | 同系统桥梁公司查看、水利公司编辑，员工兼岗 | 各公司分别查询并返回自身功能权限，不跨公司合并 |
| UC05-T08 | 子菜单有查看权限，父级仅作导航 | 返回必要父级容器，不返回兄弟菜单权限 |
| UC05-T09 | 只授予编辑，未授予菜单查看/进入 | 编辑操作如实返回，菜单不自动可见 |
| UC05-T10 | 员工未知、停用或无授权 | 返回空菜单和空操作，不返回无关身份资料 |
| UC05-T11 | 角色尚未生效、权限停用或关系撤销 | 该来源不参与合并，其他有效来源保留 |
| UC05-T12 | 新授予待审批或批准待执行 | 不提前返回新增权限；撤销待审批也不提前扣除 |
| UC05-T13 | 凭据无效或伪造其他系统编码 | 返回认证/授权错误，不返回权限 |
| UC05-T14 | 缺少员工统一标识 | 参数错误，不用姓名猜测 |
| UC05-T15 | 数据库故障或必要目录数据损坏 | 返回服务错误，不返回假成功或默认放行 |
| UC05-T16 | 返回菜单后授权已撤销，员工仍点击旧入口 | 新查询反映撤销；实际操作经 UC-06 被拒绝 |

### 系统进入权限补充验收

其余功能权限验收场景若预期允许，均以已具备当前公司、当前系统进入资格为前提；专门验证缺失进入资格的场景除外。

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| UC05-T17 | 有功能配置但没有系统进入权限 | canAccessSystem=false，菜单及操作为空 |
| UC05-T18 | 只有进入权限，没有功能权限 | canAccessSystem=true，菜单及操作为空 |
| UC05-T19 | 进入与功能分属同系统不同角色 | 返回 true 及有效菜单、操作 |
| UC05-T20 | 撤销最后进入来源后再次恢复 | 先不可进入，再返回仍有效功能；其他系统不受影响 |

## 11. 后续衔接

- UC-01 落实菜单与查看/进入权限的对应关系、导航目录定义及停用行为；菜单可见条件已由用户确认，不表述为老师明确要求。
- [UC-06_检查员工指定操作权限.md](UC-06_检查员工指定操作权限.md) 定义单项功能权限检查；权限中心不接收业务记录或数据过滤条件，不新增 OA 审批。
- API/数据库设计确定服务认证、员工标识映射、响应字段、错误码及一致读取方式。无需实现外部系统登录或前端页面。

### 本轮补充验收

| 场景 | 预期 |
| --- | --- |
| 当前公司缺失或公司不存在／停用 | 缺失／格式错误返回参数错误；未知／停用公司返回无进入资格／无权限，不混合其他公司授权 |
| 员工没有当前公司有效任职 | 返回无进入资格／无权限 |
| 桥梁公司查看、水利公司编辑，员工兼岗 | 分别查询桥梁、水利，返回查看、编辑，互不扩大 |
| 进入来源与功能来源属于不同公司 | 当前公司不同时满足进入与功能条件时拒绝功能访问 |
| 员工停用后恢复，或离开适用部门后重新回来 | 旧失效授权仍不参与计算；重新批准授予后才可用 |
| 简单独立 HTTP 调用端查询、校验，并在授权变更后再次调用 | 展示实际功能权限返回变化；不实现外部业务页面、登录或数据权限 |

# UC-02 创建角色并配置权限

版本：V1.2，2026-10-15。状态：功能权限、部门管理范围及员工启停流程已按用户确认修订，可作为界面原型依据。

本轮更新：管理范围按公司、部门子树及系统指定；离岗关闭原部门来源权限立即生效，全局停用仅总管理员；保留功能权限、OA 及历史规则。

### 当前需求基线（2026-10-15，V1.2 部门范围与员工启停）

- 一期实现 RBAC0 权限管理：员工经角色获得权限，无角色继承、直接用户授权或显式拒绝。外部系统只做简单 HTTP 调用演示，不实现其内部业务。
- 角色属于一个公司和一个业务系统，可限定部门；公司级角色要求本公司有效任职，部门级角色要求在该部门直接有效任职，不自动覆盖下属部门。岗位不自动绑定角色；任职条件与权限需要均未改变时，不因岗位名称变化更换角色。
- UC-05/06 按“员工＋当前公司＋业务系统”计算权限。仅合并该公司、该系统内的有效角色；系统进入资格与功能权限也必须来自该公司、该系统。公司上下文隔离的是功能授权来源，不定义业务数据访问范围。
- 授权同时校验角色适用条件与来源部门。离岗关闭原部门来源立即失效，其他独立兼岗来源保留；公司级共享角色不随调岗自动转移。仅总管理员可全局停用/恢复员工；恢复不复权。新授权经 OA，新管理任命由总管理员办理。
- 当前 RBAC 系统只管理功能权限。目录登记系统进入权限与功能操作，角色配置是否授予；不定义、保存或返回业务数据范围，不设计本人记录判断或行过滤规则。
- 员工、公司、部门使用稳定内部 ID；首次导入以源唯一用户名建立员工映射，组织分配稳定编码，更名不改变身份。人员变更模板明确新增任职、结束任职、停用、恢复等动作，不从文件缺行推断离职。
- 一期使用至少两个公司、两个系统的代表性数据，覆盖多角色、兼岗、公司授权隔离、功能操作独立与去重、审批生效、撤销、失效及重新申请。其余资料后续逐步补齐。

以上为本轮已确认规则，详细流程与验收必须遵循；描述的是需求设计，不代表代码已实现或真实外部系统已完成对接。

角色草稿创建、权限配置是两个可独立进入的子流程。修改已有角色权限不需要重新创建角色。角色分配给员工属于 UC-03，不属于本用例。

### 管理范围与人员权限（V1.2 已确认）

完整规则见 [管理范围与人员权限规则](管理范围与人员权限规则.md)。总管理员指定公司、管理根部门及系统，部门范围含下级但不跨公司；同范围协作，不因同公司就共享整家公司权限。

公司级共享角色只由总管理员维护，权限管理员可为范围内合格员工申请分配；部门角色按明确归属维护。每次员工授权固定实际来源部门，不等同管理员根部门或角色归属。

离岗关闭原部门来源权限立即生效、不等待 OA；一般角色配置、分配及撤销仍经 OA。全局员工停用/恢复仅总管理员；恢复不自动复权。不设计公司/部门启停，普通员工不登录本平台。

## 2. 已确定的规则与实现约定

已确认：当前 RBAC 系统只管理功能权限；允许创建角色、配置独立操作权限，不设计业务数据权限。

本稿沿用当前角色方案：一个角色属于一个系统，有公司或部门归属；五类角色是参考，不写死；岗位任职不自动授权；无角色继承和直接用户权限。

2026-10-12 按最新确认简化 OA 边界，替代此前关于固定审批人员和两级流程的约定。以下作为小组方案，不表述为教师逐字要求：

- R1（已确认）：总管理员或权限管理员发起，OA 负责审批；谁审批、审批几级、如何流转均由外部 OA 决定，不作为本项目需设计或待确认的事项。业务必要性包含在外部审批中，权限中心不增加独立确认步骤。
- R1a（V1.2 已确认）：总管理员指定公司、管理根部门及可管理系统；范围覆盖该部门子树但不跨公司，同范围协作。公司级共享角色仅总管理员维护，权限管理员可申请为范围内合格员工分配，不因此取得共享角色配置权。
- R2（已确认）：配置方案提交不立即生效；OA 审批完成后交付最终批准结果，由权限中心通过 UC-11 校验并执行，无须在权限中心重复人工批准。

以下按本轮讨论作为设计约定落入用例；不再将草稿状态、旧配置保留、驳回重提及编码唯一性列为待确认问题：

- R0：新建角色先保存为待配置草稿，不可分配；首次配置批准执行时激活。已有角色等待新方案时继续使用旧有效配置。
- R3：角色编码 code 全局唯一并保持稳定，由数据库唯一约束保证；内部 id 是关联主键，显示名称 name 可以重名或修改。更新角色权限不改变其 id、code，不通过编码字符串推断管理范围。
- R4：角色创建后不通过本用例修改所属组织和系统；归属变化另建角色，避免无意把既有授权转移到其他组织/系统。
- R5：角色配置表达是否拥有功能操作；不区分业务数据归属，不配置数据范围。

### 一期角色状态边界（已确认）

一期角色仅区分“待配置/未生效”和“已生效”，不提供独立的角色停用、重新启用或恢复操作，不增加相应审批类型。角色已生效不代表员工必然可访问，还须满足员工、系统、目录、权限及角色关联的有效性和系统进入前提。

调整角色权限使用 UC-02，经 OA 后执行；一般取消员工持有的指定角色使用 UC-04，经 OA 后撤销关联；离岗关闭原部门来源则直接办理。未提交且无历史引用的新角色草稿可按既定规则删除；已生效角色及历史保留，不借角色启停绕过审批。业务系统、菜单、操作权限的启停仍由 UC-01 管理，员工全局状态仍按 UC-10 处理。

### 2.1 方案状态与角色状态分开

审批状态属于“配置方案”，不是角色当前有效权限本身。一个已有角色可以正常使用，同时有一份待审批的修改方案。OA 提供审批结果，权限中心维护方案记录和执行状态。

| 方案状态 | 含义 | 当前有效权限 |
| --- | --- | --- |
| 草稿 DRAFT | 正在编辑，尚未提交 OA | 不改变权限；新角色不可分配 |
| 待审批 PENDING | 已提交固定方案，等待 OA 最终结果 | 已有角色继续使用旧配置，新角色不可分配 |
| 已驳回 REJECTED | OA 未批准 | 不改变权限；保留驳回内容，复制为新草稿修改重提 |
| 已批准、待执行 APPROVED | 收到并验证 OA 最终批准结果，尚未成功写入配置 | 不改变权限；不能显示已生效 |
| 执行成功 EXECUTED | 该方案的配置、版本、审计已原子提交 | 新配置生效；首次配置成功后角色可分配 |
| 执行失败 EXECUTION_FAILED | 已批准方案执行失败且未提交变更 | 保留旧配置；显示失败原因，合法重试成功后才生效 |

补充终止状态：已撤回 WITHDRAWN 仅在后续支持可信撤回对接时启用，用于已提交方案取消后重新申请；已失效 INVALIDATED 用于原资格来源对应的范围或目标条件已变化、导致不再合法且不可重试的方案。这两项是防止旧审批覆盖新配置的实现约定，不是额外人工审批环节。

```text
草稿 → 待审批 → 已批准、待执行 → 执行成功
          │             └→ 执行失败 → 合法重试
          ├→ 已驳回 → 复制为新草稿 → 重新提交
          └→ 已撤回（可选扩展）→ 新建修改方案 → 重新提交
```

- 新角色自身保持“待配置/未生效”，直至首次执行成功；已有角色自身不因修改方案待审批而失去已生效状态。
- OA 批准不等于执行成功。数据库错误时不得显示新配置已生效；执行失败记录应在业务变更回滚后另行可靠保存，不能与回滚一起丢失。失败写入也不可用时，保持可恢复的已批准待执行状态并记录服务端错误。
- 业务必要性的认可包含在 OA 对角色方案的审批中，不设置“必要性已确认”方案状态。

### 2.2 新旧方案与重提规则

同一角色同一时间只允许一份占用变更通道的方案：草稿、待审批、已批准待执行，或仍允许重试的执行失败方案。已驳回、已撤回、已失效及执行成功的方案保留作历史，不占用通道。该限制应由后端事务控制，不能只靠前端禁用按钮。

已提交方案不能原地修改。驳回后保留原方案及原因，复制为新草稿、修改配置、再次提交。审批中不允许直接修改；若后续支持撤回，可在可信撤回完成后新建方案，否则等待最终结果后再按状态处理；一期不提供人为放弃或取消已批准方案的操作。合法方案执行或因短暂故障重试，实际条件不再合法才标记失效；执行成功后的调整须新建申请，不能仅点开另一份草稿覆盖。

每次提交关联具体方案编号、基础角色版本和固定内容摘要。权限中心仅执行当前有效且内容一致的批准结果；重复成功回调返回原结果，迟到的旧方案通知不能重新覆盖新配置。最新有效配置指“基于正确版本、获最终批准且执行成功的配置”，不是最后到达服务器的通知。

同一获准范围的管理员可协作，但不各自创建并行方案；可查看当前占用方案，在仍为草稿时按编辑版本检查协作修改，记录具体操作者。

### 系统进入权限（已确认）

配置页面单独展示“允许进入本系统”选项，通过同一 OA 配置方案授予或移除，不自动勾选。功能操作各自选择是否授予；所有权限均无数据范围字段。

一个角色可以只有进入权限，也可以只有功能权限；不强制每个角色包含进入权限。员工的进入资格和功能权限可来自同一公司、同一系统的不同有效角色，最终合并后同时满足才生效。缺少进入权限时提示影响，不自动补授，也不以此禁止保存角色。

移除角色中的进入权限可能影响所有持有该角色且无其他进入来源的员工；预览须区分“配置移除”和“当前剩余来源仍可进入”。菜单或功能仍被配置不代表可绕过系统进入检查。

### 申请归属、资格来源与自动执行（已确认）

角色和已提交申请不归原申请人个人；角色按公司/部门归属，员工授权明细按来源公司/部门归属。同范围管理员可协作，不能因同公司就访问其他范围。原管理员离任不单独阻断已提交合法申请，目标员工来源关闭则按来源周期拒绝旧批准；保留原提交人与固定内容。

提交时固定资格依据：总管理员为全局资格，权限管理员为明确公司、部门子树及系统的范围记录和版本。UC-11 按原范围记录复核，不能换用当前查看人的更大资格；按申请类型检查对应目标条件：配置查角色归属及版本，授予查来源部门/任职/周期与角色关系版本，一般撤销查指定来源及关系版本，不机械要求当前授予资格。总管理员原申请仍明确实际来源部门，不受普通管理员系统清单限制。

收到可信最终批准后，权限中心自动尝试执行合法的固定方案，不等待任何管理员点击接手或再次确认；原申请人离任、公司暂时没有权限管理员均不单独阻止执行。短暂故障保留批准依据并由服务端重试，重试仍检查原资格来源对应的范围及目标条件；仅实际范围或目标条件不再合法时标记失效。员工角色分配仍须检查目标员工有效任职，撤销历史关联不要求目标员工仍在原岗位。

一期不提供人为取消已批准方案的入口，不以“失效”代替任意取消。合法方案执行或在短暂故障后重试；实际条件不再合法则失效并记录原因。执行成功后如需调整，按 UC-02～04 重新申请。未提交草稿的删除规则保持独立。

未提交草稿可由范围内管理员删除并记录删除事件，释放变更占用；新角色从未提交、从未生效且无引用时一并删除空草稿。已正式提交或已生效的角色/申请保留历史，不借删除绕过审批。正式角色配置提交后须至少包含一项权限（系统进入权限或功能操作均可），不产生已生效空角色；清理员工授权走 UC-04。


## 3. 输入与输出

### 创建角色输入

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| 所属组织 | 是 | 公司或部门的稳定 ID；不是解析角色名称获得 |
| 所属业务系统 | 是 | 老师清单中已登记系统的 ID |
| 角色名称 | 是 | 人可读名称，例如“普通员工”“项目查询员” |
| 角色编码 | 是 | 全局唯一稳定标识，例如 `ROLE_000001`，可由后端生成；不在不同公司重复使用 `employee` |
| 角色说明 | 否 | 用途说明，不参与权限计算 |

输出：角色草稿 ID、名称、归属、版本及待配置状态。操作者身份由后端从登录会话取得，不由表单指定。

### 配置权限输入

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| 角色 ID | 是 | 配置目标 |
| 基础版本 | 是 | 页面读取的角色配置版本，用于拒绝陈旧提交 |
| 权限变更 | 是 | 明确新增、移除系统进入权限或功能操作的权限 ID 集合 |
| 变更原因 | 是，建议 | 审批和审计依据 |
| 提交请求编号 | 是，建议由客户端生成 | 网络重试时防止重复创建方案 |

输出：方案编号、状态、操作差异、基础版本、提交人、时间；无差异时返回“未发生变化”。输入缺少权限字段不能视为清空全部权限。

## 4. 基本流程

### A. 创建角色草稿

| 步骤 | 管理员操作 | 系统处理 |
| --- | --- | --- |
| A1 | 打开角色管理，点击新建 | 展示获准发起配置的组织和有效业务系统 |
| A2 | 选择组织、系统，填写名称、编码和说明 | 进行表单基本校验 |
| A3 | 点击“保存角色草稿” | 后端校验登录身份、配置申请资格及组织/系统范围、状态、字段与编码唯一性 |
| A4 | 查看结果 | 同事务保存待配置角色、关联的配置草稿及审计，返回角色 ID、方案 ID 与版本；提示未生效、不可分配 |
| A5 | 点击“配置权限”或返回列表 | 可进入流程 B；返回列表仅完成草稿保存，不代表角色已经批准可用 |

### B. 配置操作权限

| 步骤 | 管理员操作 | 系统处理 |
| --- | --- | --- |
| B1 | 选择角色，点击配置权限 | 校验配置申请资格及角色范围，读取角色归属、系统、版本及当前有效配置 |
| B2 | 浏览菜单/功能树 | 显示本角色所属系统的进入权限和功能操作目录，功能操作显示当前是否已授予 |
| B3 | 勾选系统进入权限或功能操作，也可取消已有权限，并填写申请原因 | 保存编辑中的变更，尚不改变有效权限 |
| B4 | 点击预览变更 | 展示新增、移除功能操作和当前拥有该角色的有效员工影响；明细只在获准范围内返回 |
| B5 | 填写原因并确认提交 | 后端重新校验身份、组织/角色配置申请范围、版本、单一未结束方案、同公司角色归属、同系统权限归属、权限状态、类型合法性和变更完整性 |
| B6 | 查看提交结果 | 保存固定内容、范围依据、版本和提交事件；分别展示 OA 待发送/发送失败/已关联、审批与执行状态；旧配置继续有效 |
| B7 | 后续查看方案状态 | UC-11 收到可信批准结果后重新检查条件，实际执行配置。页面区分草稿、待审批、已驳回、已批准待执行、执行成功及执行失败 |

B7 是衔接说明：执行与审批接入规则在 UC-11 定义，不在本用例重复实现审批引擎。提交成功不能显示成“权限已生效”。

### C. OA 审批及执行衔接

| 步骤 | 责任人/系统 | 处理 |
| --- | --- | --- |
| C1 | 办理管理员/权限中心 | 将固定的配置方案编号、内容、基础版本和摘要关联 OA 审批单；传输方式在集成设计中确定 |
| C2 | OA 系统 | 在外部完成审批，返回关联原申请的最终批准或驳回结果；内部流程不在本项目展开 |
| C3 | 权限中心，UC-11 | 验证结果来源、申请编号与固定内容；驳回只更新方案状态，批准后按原资格来源复核范围、目标条件与版本并自动执行，再原子更新配置、版本、执行状态和审计。首次执行成功时激活角色草稿 |
| C4 | 办理管理员 | 查看执行结果；批准但执行失败应显示未生效及原因，不能显示权限已生效 |

OA 最终驳回时，已有角色仍使用旧配置，新角色草稿不可分配。被驳回的方案保留为历史，修改功能权限集合后以新方案重新提交、重新审批。

权限中心不维护 OA 审批节点、审批人、会签或转交规则，也不根据审批层级数判断能否执行；只识别可信的最终结果。普通管理页面不能直接把申请改成“已批准”。

一期使用模拟 OA 返回批准/驳回结果即可验证对接流程，不实现审批页面或流转引擎。模拟结果仍须经过相同的来源校验、申请匹配和防重复执行逻辑；模拟入口仅用于开发与验收，不作为普通管理员的审批功能。

## 5. 页面示例

角色：桥梁工程分公司 / HR 系统 / 普通员工。

| 功能点 | 操作 | 是否授权 |
| --- | --- | --- |
| 员工台账管理 | 查看 | 是 |
| 员工台账管理 | 编辑 | 是 |
| 员工台账管理 | 导出 | 否；仅在目录已登记此操作时展示 |
| 薪酬核算 | 查看 | 是 |

在员工已有本系统进入资格、操作目录有效且配置已经批准并成功执行的前提下，获得该角色的员工拥有上述查看、编辑功能权限。此结果只判断能否执行功能，不承诺对任何具体业务记录的访问资格。

这里只定义角色能力，没有把角色授给任何人。即使员工岗位叫“普通员工”，未分配角色也不会自动获得权限。员工有多个有效角色时，同公司同系统的功能权限集合取并集并去重。

建议按钮：“保存角色草稿”“预览变更”“提交 OA 审批”“取消”。页面分别展示“当前有效配置”和“待审批变更”，避免把方案当有效授权。

## 6. 替代与异常流程

| 编号 | 发生位置/条件 | 处理结果 |
| --- | --- | --- |
| E01 | A3/B1/B5：会话无效、无配置申请资格或超出组织/角色范围 | 拒绝请求；不接受前端伪造的管理员身份 |
| E02 | A3：编码重复、组织或系统无效 | 提示对应问题；不创建角色 |
| E03 | B3：用户取消编辑 | 丢弃未提交变更；当前有效配置不变；之前已创建的草稿保留且不可分配 |
| E04 | B5：请求混入其他系统权限 | 整体拒绝，不仅从页面隐藏跨系统项 |
| E05 | B5：权限不存在、已停用或功能归属非法 | 拒绝新增无效授权；允许明确移除已有停用权限关系 |
| E06 | B5：配置版本与读取时不同 | 返回冲突，要求重新读取、查看差异后提交，不静默覆盖 |
| E07 | B4/B5：准备移除全部权限 | 拒绝提交空权限配置；需取消员工授权时走 UC-04，未提交的新角色草稿可以删除 |
| E08 | B5：无实际差异 | 返回未发生变化，不制造审批任务 |
| E09 | B6：同请求编号重试 | 相同内容返回原方案；不同内容拒绝，避免重复或篡改 |
| E10 | A4/B6：业务写入或审计写入失败 | 该事务整体回滚，返回失败；配置方案失败不删除之前已成功保存的角色草稿 |
| E11 | UC-11 执行前角色、权限、原资格来源对应范围或版本变化 | 重新校验并拒绝失效方案；旧有效配置不被覆盖，提示重新提交 |
| E12 | 同一请求将同一权限既新增又移除 | 拒绝歧义输入，不自动猜测最终意图 |
| E13 | 同一角色已有未结束方案，另一权限管理员新建并行方案 | 拒绝新建，提示查看/处理现有方案；草稿修改需校验版本 |
| E14 | 旧审批通知迟到、重复或指向已撤回方案 | 已执行相同通知幂等返回，其余拒绝执行；不覆盖当前有效配置 |

审批未通过时不修改有效配置；驳回状态通过可信 OA 结果同步更新；撤回同步仅在启用可选扩展时适用，具体采用回调或查询在 UC-11 的接口设计中明确。申请人不能自行伪造这些结果。

## 7. 业务规则

1. 一个角色只关联一个系统内的权限；数据库和后端共同保证完整性。
2. 组织归属、业务系统、角色类别是不同维度；不按角色名称推断权限。
3. 不强制为全部岗位或全部五类组合创建角色；按实际需要维护。
4. 查看和编辑分别配置是否授予；不存在隐含的本人数据限制或操作继承。
5. 编辑不自动包含查看，父菜单不自动授予子功能，功能依赖若有要求必须单独定义。
6. 角色变更影响所有通过该角色获得授权的员工，因此提交前提示影响；不把角色配置当成单人特例。
7. 未明确的“全部”操作集合和空白来源单元格不能自动变成宽泛授权，应先经 UC-01/导入预检明确目录与映射。
8. 执行后的新请求读取最新权限；不承诺回滚已执行中的外部业务事务。
9. 只有总管理员或有效权限管理员可提出范围内申请。公司级共享角色仅总管理员维护，部门角色按指定范围协作；取消管理员任命不自动删除业务角色，员工离岗关权另按 UC-04 处理。

## 8. 数据与事务边界

| 处理 | 读取数据 | 写入数据 | 事务边界 |
| --- | --- | --- | --- |
| 创建角色草稿 | 申请资格和范围、组织、系统、全局编码唯一性 | 待配置角色、关联配置草稿、创建审计 | 一起提交或回滚 |
| 展示配置与影响 | 角色、操作目录、角色权限、有效员工角色关系 | 无 | 只读；提交时重新校验 |
| 提交方案 | 当前身份、状态和版本 | 配置方案、请求防重信息、提交事件 | 一起提交；不更新有效角色权限 |
| 接收最终批准结果，属于 UC-11 | OA 服务身份、方案编号和固定内容 | 已批准待执行状态、接收记录 | 先可靠保存，重复通知幂等 |
| 执行批准方案，属于 UC-11 | 固定方案及提交资格依据、对应范围、角色版本、权限状态 | 角色权限、版本、执行状态、成功审计 | 同一本地事务；不将等待 OA 的时间放在数据库事务内 |

核心逻辑实体：Role、Permission、RolePermission（只关联功能权限）、EmployeeRole、AuthorizationChange、AuditLog。具体表名和接口 URI 留到数据库/API 设计阶段统一。

## 9. 结构化功能分解草案

```text
角色创建与权限配置
├── 创建角色处理
│   ├── 校验配置申请资格和组织归属
│   ├── 校验输入与编码唯一性
│   └── 保存角色草稿及审计
└── 配置权限处理
    ├── 读取角色及本系统权限目录
    ├── 计算功能权限集合的变更
    ├── 校验申请范围、系统归属及版本
    ├── 查询当前授权影响
    └── 保存配置方案及提交记录

外部：OA 完成审批并返回最终结果（内部流程不展开）
后续：UC-11 校验最终批准结果并执行方案
```

这张功能分解草案用于推导模块结构图，不表示每一行都必须建立一个 Java 类。Controller 接收输入，Service 组织处理，数据访问模块执行查询与事务内写入。

## 分析与设计方法

本项目采用结构化分析与结构化设计，按自顶向下、逐步求精的方式推进。需求阶段通过数据流分析分解处理过程，结合用例确定业务规则和验收行为；设计阶段在既定阶段顺序内，将处理职责细化为高内聚、低耦合的模块，明确模块层次、调用关系与接口。用例、活动图和时序图作为辅助表达，不替代模块结构设计。

现有顶层与第一层数据流图是结构化分析产物；逻辑处理过程、逻辑存储不直接等同于代码模块或物理表。采用结构化设计方法不代表详细设计阶段已完成。

## 技术栈约束

2026-10-16 用户确认（D-028）：前端 Vue 3 + TypeScript + Tailwind CSS；后端 Spring Boot + Spring Data JPA；数据库 MySQL；API 风格为 RESTful API，契约继续通过 Apifox 管理；身份认证凭证采用 JWT，功能授权依据既有 RBAC 规则。分析与设计继续采用上述结构化方法。

各阶段沿用这些选型，具体版本、测试框架与最终工程布局待细化。API 与详细设计阶段明确 JWT 有效期、续期、退出及失效机制，满足后台账号停用、员工停用和资格变更等现有用例边界；JWT 不能替代当前账号、管理员任命及管理范围的有效性判断。选型确认不改变阶段顺序，不表示后端、数据库或认证已实现。

2026-10-15 已将四个项目技能及配套文件复制到 `.agents/skills/`，随 Git 分发；TDD 同时保留固定上游版本的 MIT 许可证。优先读取仓库内技能，不依赖某台机器的全局安装路径。来源与文件摘要见 [SKILLS.md](SKILLS.md)。当前界面原型首版已实现，待用户评审；未开始正式业务逻辑实现，也未产生正式模块的 TDD 测试结果。

每个模块采用以下循环：

1. 根据已确定的业务行为和契约编写测试，覆盖正常与关键边界情况。
2. 运行测试，确认因目标行为未实现而失败，记录命令及失败原因。
3. 编写满足测试的最小实现，使测试通过。
4. 在测试通过的保护下重构，重新运行受影响检查。
5. 完成模块间集成验证，更新设计、追踪关系和共享记忆，再提交对应改动。

测试重点包括跨公司授权隔离、功能权限独立与去重、系统进入资格、审批幂等和重复回调、批量回滚、任职变更、停用/恢复与会话失效。测试框架随技术选型确定。

## 阶段交接和变更

各阶段及团队、agent 交流统一使用 [GLOSSARY.md](GLOSSARY.md) 的名称与含义。新增概念补充定义、别称、适用边界和需求依据；术语涉及业务规则变化时先完成需求确认，再同步术语及受影响交付物。术语表不预先确定 API 字段或数据库命名。

阶段完成时，将交付物路径、已解决决策、未决项和验证证据更新至 `MEMORY.md`，重要决策更新至 `DECISIONS.md`，与交付物一起提交 Git。

需求变化先修改需求，再检查原型、API、数据与实现影响。后续阶段发现前置问题时回补相关文档并记录原因，不静默改变已确定规则。

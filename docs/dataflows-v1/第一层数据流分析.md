## 2. 七个处理过程

| 编号 | 处理过程 | 输入如何变成输出 | 对应用例 |
| --- | --- | --- | --- |
| 1.0 | 管理身份与管理范围 | 后台登录、账号、改密、退出和专员任免／范围请求，结合当前员工任职与管理资格，形成身份、会话及范围变更结果 | UC-07、09 |
| 2.0 | 维护系统与权限目录 | 目录维护内容结合编码、层级、引用、功能归属和版本规则，形成目录、影响预览与保存结果 | UC-01 |
| 3.0 | 导入组织人员并处理失效 | 来源资料及管理员映射、确认，结合现有人员任职与历史引用，形成批次报告、人员数据及必要失效记录 | UC-10 |
| 4.0 | 办理角色与员工授权申请 | 管理请求结合当前范围、任职、权限目录、角色与关系版本，形成角色草稿、差异、固定申请、OA 关联及可见实际状态 | UC-02、03、04 |
| 5.0 | 接收审批并执行权限变更 | OA 结果结合本地固定方案、原资格来源及当前目标条件，形成可靠接收记录和实际执行／失败／失效结果 | UC-11 |
| 6.0 | 查询与校验有效访问权限 | 可信调用身份、员工、当前公司、系统和可选权限编码，结合已提交的有效来源，形成权限集合、单项结论或调用／服务错误 | UC-05、06 |
| 7.0 | 查询范围内授权审计 | 管理员筛选、分页和详情请求，结合最新管理范围，形成可读审计摘要、数量、差异与关联事件 | UC-08 |

这里按数据处理职责分解，不强制“一个用例一个过程”。UC-02～04 共享申请办理；UC-05／06 共用有效性过滤与范围计算；UC-07／09 共用后台身份和管理范围。后续再把过程转化为结构化模块及接口，不直接把这些编号当成 Java 类或数据库表。

## 3. 九个逻辑数据存储

| 编号 | 名称 | 内容与边界 |
| --- | --- | --- |
| D1 | 身份、会话与管理范围 | 后台账号、密码摘要／凭据版本、会话、专员任命及公司系统范围；也归组现有外部调用所需的受信身份与绑定配置，不因此新增“在后台管理所有外部凭据”的功能 |
| D2 | 组织、员工与任职 | 公司、部门、岗位、员工、任职状态及来源稳定标识映射；保留兼岗和变更历史 |
| D3 | 系统、菜单与操作目录 | 系统状态、SYSTEM_ACCESS、菜单结构、操作权限、功能归属、菜单可见绑定及版本 |
| D4 | 角色与角色权限 | 公司＋系统＋可选部门归属、角色草稿、生效配置、范围与版本；草稿不等于有效权限 |
| D5 | 员工角色授权 | 具体员工角色关系、授予来源、状态、关系版本与失效／撤销历史 |
| D6 | 变更申请、审批与执行记录 | 草稿／固定方案、请求编号、原资格来源、摘要、基础版本、外部关联、最终结果、执行／失败／失效与恢复依据 |
| D7 | 授权及管理审计 | 目录、任免、方案、实际变更和人员失效等审计；历史快照和差异不表示当前权限 |
| D8 | 导入批次与报告 | 来源批次、字段映射、固定输入、预检问题、影响、实际结果及防重信息 |
| D9 | 运行与调用日志 | 登录和业务接口等必要运行摘要，与 UC-08 展示的授权审计分开；不保存原始密码、令牌或无关个人信息 |

九个存储是分析层的数据分组，**不是要求数据库必须建九张表**。一个逻辑存储可能映射多张关联表，也可能包含部署配置或日志介质；数据库字段、表名和物理存储尚未定稿。

### 主要写入责任

- 1.0 写后台身份、会话与任命范围，不自动生成业务角色授权。
- 2.0 写目录及审计，读取已有角色与授权以分析引用影响，不直接改变员工授权。
- 3.0 更新组织员工任职，同时使不满足条件的 D5 授权和 D1 任命失效；恢复身份不复活旧授权／任命。相关正式更新、批次结果和成功审计须整体提交。
- 4.0 可写 D4 中不可分配的角色草稿及清理记录，写 D6 方案与外部关联；不直接更新已生效角色权限，也不授予／撤销 D5 员工授权。
- 5.0 是经过 OA 的有效配置变更执行方：成功时更新 D4 或 D5、执行状态及成功审计。接收最终结果先独立可靠保存，不能因业务执行回滚而丢失批准依据。
- 6.0 读取当前已提交授权，写最少调用摘要，不写授权、不生成审批。
- 7.0 只读当前范围允许访问的审计及关联记录，不改写历史，也不重放授权。

## 4. 上下层边界平衡

第一层保留顶层五类外部实体，未增加直接登录权限中心的普通员工，也未增加向 HR 回写或主动向业务系统推送权限的接口。

| 顶层流 | 第一层细分 | 进入／离开的过程 | 保留的内容 |
| --- | --- | --- | --- |
| F01 总管理员输入 | F01.1～F01.5 | 1.0、2.0、3.0、4.0、7.0 | 后台身份与管理范围、目录、导入、角色授权申请及查询、审计查询 |
| F02 总管理员输出 | F02.1～F02.5 | 1.0、2.0、3.0、4.0、7.0 | 身份范围、账号办理、目录、导入报告、配置与实际申请状态、审计及相应错误 |
| F03 公司专员输入 | F03.1～F03.3 | 1.0、4.0、7.0 | 本人账号与会话、本公司获准范围内申请及配置查询、审计查询 |
| F04 公司专员输出 | F04.1～F04.3 | 1.0、4.0、7.0 | 身份范围、本人账号办理、范围内配置与申请状态、审计及相应错误 |
| F05 HR 输入 | F05 | 3.0 | 组织、岗位、员工、任职及明确变更数据 |
| F06 向 OA 提交 | F06 | 4.0 | 固定申请、编号、版本／摘要及关联信息 |
| F07 OA 输入 | F07.1、F07.2 | 4.0、5.0 | 申请提交时的外部关联信息；最终批准／驳回结果及可信匹配依据 |
| F08 对 OA 反馈 | F08 | 5.0 | 接收、拒绝、重复及实际处理／执行状态 |
| F09 业务系统输入 | F09 | 6.0 | 可信调用身份、员工、公司、系统及指定权限 |
| F10 业务系统输出 | F10 | 6.0 | 进入资格、菜单、功能操作集合、单项校验以及调用／服务错误 |

共 23 条边界流。图中边界标签采用概括名称；请求附带的当前身份／会话、目标公司系统、必要原因／版本和安全错误结果仍遵循详细用例，不因省略标签字数而取消。第一层细分编号可在 [边界平衡检查记录](第一层边界平衡检查.json) 中逐项核对。

## 5. 过程之间如何关联

### 角色与员工授权的核心数据通路

4.0 保存 D6 固定方案并提交 OA；5.0 接收结果、读取同一 D6，复核后更新 D4／D5 及执行状态；6.0 读取 D2、D3、D4、D5，得到当前有效权限。4.0 查询 D6 向管理员展示实际状态，7.0 读取 D7 及 D6 追溯拟变更与实际变更。

图中的这种关系是数据依赖，不是要求前端依次调用全部过程。权限查询无需先访问 OA，也不需要员工在权限中心登录。

### 人员变更与失效

3.0 结合更新后的全部任职与角色适用条件更新 D2、D5、D1，并记录批次与审计。3.0 可以因资格不再满足而使旧授权失效，这是既定身份有效性规则，不是绕过 OA 主动给员工授予新权限。新授权仍从 4.0 申请、由 5.0 执行。

### 身份、范围与外部调用

各处理过程读取 D1 中适用的最新资格，不把登录时的旧范围当成长期通行证。OA 服务身份和业务系统调用身份，与管理员会话分别验证；在 D1 中归组不表示共用同一个账号或登录方式。员工身份仍来自业务系统的可信上下文。

## 6. 本层保留的约束

- 多角色只在同公司、同系统内合并功能权限集合；相同操作去重，不同操作互不推导，不定义数据范围。
- 当前公司有效任职、系统进入前提及目录有效性参与 6.0 判定；业务系统按结果执行功能访问拦截，本系统不设计业务数据权限。
- 批准与实际执行分开；5.0 保留批准依据并自动恢复重试，原申请人离任不单独阻止合法执行。
- 服务故障不包装为普通拒绝或空集合。失败日志在可用时记录，数据库不可用时不能伪称日志／审计已经持久化。
- DFD 中多条写入线表达数据去向，不等于这些写入可各自独立提交；原子性仍按各详细用例规定。
- D7 授权审计与 D9 运行日志分开，7.0 不因此获得读取所有登录与调用日志的功能。

## 7. 后续工作

先按本图整理数据字典，定义上述输入输出、逻辑实体及关键状态；再对 4.0、5.0、6.0 等复杂过程决定是否需要第二层分解或加工说明。之后进行结构化模块、数据库和 API 设计。本图不要求立即增加第二层所有细节或额外业务需求。

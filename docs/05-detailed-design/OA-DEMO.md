# 演示OA与示例链路

用户已明确没有真实OA接入，本次后续实现采用示例演示；保留正式固定申请、可靠结果和自动执行语义，不再把采购/对接真实OA当作本轮前置条件。没有新管理员审批、人工强制执行或跳过OaJwt的API。API出站oaSubmission仍是契约资源，演示实现与未来HTTP适配器共用同一OaSubmissionPort及DTO。

## 单应用演示实现

采用`DemoOaSubmissionAdapter`内进程受理实现，只在显式demo profile启用；外层M08仍按事务外调用/回执回写协议。该实现对固定requestId产生稳定`DEMO-<requestId>`审批编号，返回契约允许的受理回执。它读取已冻结申请核对输入版本/摘要，相同键异内容必须拒绝；不以进程内Map作为唯一防重依据，不自动决定批准。

稳定关联最终由权限中心oa_link持久化。进程重启再受理同固定申请得到同审批编号；真实HTTP已受理后超时等故障由测试端口包装器模拟，双方真实网络未接通的事实保持明确。演示受理不允许任何外部回调自报审批号来创建关联。切换真实OA时替换适配器并重新验证外部幂等/回调能力，本轮不宣称已实现真实HTTP集成。

模拟最终批准/驳回由Apifox或受控演示命令调用**原POST /api/v1/oa/final-results**，必须使用配置OA实例的OaJwt并携带准确requestId/submittedVersion/contentDigest/oaApprovalId/eventId/isFinal。先查询申请确认可靠关联，再决定；仅202代表可靠接收，轮询原申请查看实际EXECUTED/INVALIDATED/FAILED。适配器受理与OA决定是两件事。

## 受控工具与凭据

拟在同一后端产物提供非Web命令模式，部署时独立调用：bootstrap-admin、configure-demo-service、issue-demo-service-token。命令读取明确参数/环境和服务器密钥文件；服务身份公钥/iss/aud/system或OA绑定存受控配置及service_identity，不提供公开令牌签发接口。token仅输出给本机操作者供临时请求，不进入日志/样例文件/文档；CLI模式不启动调度器或HTTP服务。

初始总管理员可无员工关联，仅作为部署身份；任命及其他后台账号仍按正式员工资格。命令只在显式初始化/demo模式和授权部署身份下可用；非空库不得默认重复创建总管理员或清空数据。维护写入同样参与guard，不绕过已运行应用的T0协议。

演示脚本使用运行时变量接收返回ID/版本/摘要/当前token，预先提交到Git的是无凭据模板。service JWT在调用前生成、≤5分钟；不能把示例里的占位digest当实际批准内容，也不能由浏览器/普通员工持有业务服务密钥。

## 场景与数据

使用明确虚构的公司A/B、部门A1/A2、两个系统S1/S2及三类员工：多部门兼岗、只有单部门任职、普通员工。数据通过正式导入预检/提交录入；角色/配置/授予通过正式申请和演示回调生效，避免初始化SQL直接造“已批准成功”历史。原清单“全部”、I340、本人限定等未知映射不参与自动seed。

| 场景 | 操作顺序与观察结果 |
| --- | --- |
| 正常批准 | 总管理员建立目录/账号/范围→配置角色草稿→预览/提交→演示受理可靠关联→OA批准202→执行成功→授予申请重复同流程→业务查询得到功能 |
| 驳回 | 创建另一个固定配置/授予申请→可信最终驳回→有效权限保持，原申请终态不重编，允许按契约复制新草稿 |
| 独立来源 | 同员工/角色分别从A1/A2授予→只关A1→保留A2；A1零关系再关仍推进周期 |
| 迟到批准 | 提交旧A1授予→关A1/离岗→再发匹配旧批准→仅留历史，不恢复关系、不部分执行 |
| 恢复不复权 | 停用员工→恢复→旧grant/任命/会话保持失效，重新办理需新资格/新申请 |
| 一次执行 | 同事件重复、换事件同决定、反决定冲突、执行过程中失败/重启→结果符合三层防重和恢复协议 |
| Q-01 | 一个原子HR批次明确END最后适用任职再ADD同部门新岗→旧周期和失效事实保留；对照始终有兼岗/仅更名 |

BE-31负责演示受理与可信工具，BE-33/34负责完整脚本、真实后端/数据库与服务器验收。权限中心内进程受理是模拟，回调HTTP、存储和执行应是真实实现；不能用原型Mock响应或手改数据库代替整条链路。

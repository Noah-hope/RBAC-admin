## 分派与依赖

1. 用户先完成并确认BE-01～05基座，纳入共同主线，再分批将BE-06～35分给真实成员。A～D只是职责建议，不能视为已派工。
2. 每项登记唯一Owner、实际Issue或本地任务编号、涉及API/模块、依赖提交和验收范围；不登记Reviewer。
3. 业务正式开工仍要求FOUNDATION_ACCEPTED、BUSINESS_OWNER_ASSIGNED及原技术依赖同时满足。政策调整不自动接受任务、解除依赖或授权合并推送。
4. 团队成员验证仓库访问权限，从最新共同主线创建`codex/be-xx-主题`分支。PR用于集中呈现差异、测试和集成记录，不要求另一成员批准。

## 负责人如何确认完成

负责人核对以下内容，再记录自己的明确确认及对应提交：

- 行为符合对应UC、API、数据库和模块设计，验收范围及未完成项写清楚。
- TDD有实际失败原因及通过结果，权限边界、异常、并发/回滚与恢复覆盖适用场景；需要真实MySQL的场景没有用Mock结果替代。
- 自检代码差异、配置、迁移和日志，秘密没有进入Git；公共接口变化已通知受影响任务的负责人并协调集成。
- 提交代码、测试和共享文档，保留构建报告及产物证据；未运行或未通过项不标完成。

Agent可执行代码检查、测试和文档整理，但不凭“代码已生成”替负责人确认。完成声明记录负责人、日期、任务/提交、验证证据和限制；集成状态按实际主线合入结果记录，确认完成不等于已合入或已部署。

## 任务数据约定

所有任务采用`reviewPolicy=OWNER_ACCEPTANCE`、`reviewRequired=false`、`acceptanceOwnerPolicy=TASK_OWNER`。`reviewerSlot`及`suggestedReviewerSlot`暂保留为null以兼容现有资料，不是待分配字段；`reviewHours`均0。业务ownerSlot=null仍表示未分派。

TASKS、issues、API/模块追踪及共享记忆同步维护。先更新[design_plan.py](design_plan.py)，再生成资料并运行[validate_design.py](validate_design.py)，避免手改JSON被覆盖。

原开发估算包含设计细化、TDD、自测、文档和负责人核对。取消独立评审单列工时后，总量低/中/高为70.5/130.5/209人时；未依据agent速度下调技术工作量。低估接近72人时上限，中估仍超预算，不承诺5～6天全量交付。

## 提交与PR说明

```text
关联：BE-xx / 实际Issue（如有）
行为：触发条件、预期结果、UC/API/数据库及设计章节
改动：模块边界、迁移/配置影响、依赖提交
验证：RED失败原因；GREEN命令和结果；真实数据库/并发证据
限制：未运行或未通过项、后续任务
负责人确认：负责人、日期、确认范围及对应提交
```

API/表变化先同步权威设计，不能只改实体或Apifox。多人同时修改公共基座、DTO或迁移时，相关负责人协调接口及提交顺序；协调不新增独立审批门槛。是否合并/推送仍按该次授权和仓库实际权限执行。

## 自动化与交付

拟议自动检查保留：固定JDK/Wrapper、离线/HTTP测试、专属MySQL迁移/JPA/并发验证、候选jar和校验和。云端部署、重启持久化、备份恢复和全链路演示继续由BE-32/34/35按实际结果记录。工具不可用应明确未运行，不能静默跳过后称验收通过。

当前尚未配置远程保护/CI。本轮只同步本地规则；日后启用托管规则时采用负责人确认和自动检查，不把强制他人批准作为任务完成条件。

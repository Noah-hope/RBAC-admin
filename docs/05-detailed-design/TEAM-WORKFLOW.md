# 四人Issue与PR协作方案

本方案设计交付时只生成本地可复制任务，尚无远程仓库。后续用户已指定GitHub仓库并授权设计合并与推送，main已建立origin/main跟踪，当前事实见MEMORY/D-037；真实成员账号、远程Issue/PR、保护规则及CI尚未落实。以下按Issue/PR工作流设计，链接/保护分支能力依据GitHub官方说明，套餐/仓库权限实际是否可配置由BE-01确认，不能将拟议检查记为已启用。

## 团队职责与共用边界

| 槽位 | 主责 | 交接重点 |
| --- | --- | --- |
| A | 公共工程/事务/身份/范围、集成/部署；员工与范围生命周期入口共同负责 | WriteContext、当前资格读取、错误与幂等、构建和迁移接口先稳定；当前负载较高，需按估算协调 |
| B | 目录、角色、有效权限/影响计算及跨模块集成验收 | 只实现角色配置应用器，审批后应用由C执行器调用；M11拆投影文件，不独占所有查询工作 |
| C | 申请/claims、OA演示/可靠回调、执行与恢复、审计读取 | 提交不授权、回调独立提交、执行一次成功；向D提供统一RequestInvalidator端口 |
| D | 组织员工/任职、来源/关系、生命周期及HR导入 | 与A/C约定同一事务内的状态失效，不能底层服务自行提交；岗位不自动授予 |

槽位不是已分配真实账号，可兼任/调配。A不独自代写所有控制器或43实体；域实体/DTO/投影/测试由所属Issue维护，A只协调公共骨架。每人一次主做一项小任务，跨文件变更前在关联Issue说明。共享记忆由集成负责人协调合并，各PR仍带自己的设计/验收记录。

## 远程启用顺序

1. 平台已确定GitHub、首次远程默认分支已核对为main，设计已按用户明确授权纳入主线。团队确认仓库可见性及四人账号权限，从最新origin/main的共同基线创建后续分支，避免分别从旧main/不同API分支起步。
2. 创建拟定milestone“后端全范围可部署演示”，将[issues.json](issues.json)/[TASKS](TASKS.md)逐项登记，填真实负责人/评审人、实际Issue号和链接。BE-xx是本地键，不能直接写成不存在的GitHub #号。
3. 建立主线保护建议：至少一名非作者批准、必需构建/测试通过、新提交后重新确认评审、无未解决讨论；有权限时启用平台规则，否则人工记录同等门禁。紧急变更也留Issue/PR与验证事实。
4. 每个任务从共同主线建短分支，命名可用`codex/be-xx-主题`。公共接口先发小PR，依赖方可基于已约定端口写行为测试并用草稿PR提早暴露问题；最终依赖未合并/验收不得关闭子Issue。

## Issue状态与内容

建议状态：Planned→Ready→In progress→In review→Integrated→Accepted；Blocked记录具体前置条件和责任人，不因耗时长随意标阻塞。Ready要求对应详细设计/契约、依赖接口、虚构测试数据与验收定义清楚；Accepted要求业务及环境验收有证据。接口列表数、代码行数或“已生成”不代表完成。

每卡已有owner/reviewer、低中高开发/评审人时、依赖、模块/API、交付和AT验收，跨阶段表/T/I见TRACEABILITY。登记时补实际UC/API链接、测试数据、受影响文件、是否修改契约/迁移、预计完成时段。每次验收在Issue/PR写命令/版本/实际结果、剩余失败和阻塞；秘密不进正文。

每卡acceptanceScope明确本任务负责的验收部分；基础任务可按该部分验收合并，不能因此关闭完整AT。BE-01只完成准备核验，不提前要求构建或发布包；BE-33汇总完整业务与契约，BE-34实测目标服务器，BE-35汇总发布证据。环境、协作与发布核验留实际记录，涉及业务及可执行基础能力的实现遵守TDD。

本地milestone名称/标签只是建议，服务器采购/环境准备也有BE-01/34责任，正式前端不进本期后端预算。全量低估79.25h已超过容量，保持所有任务可见；调整范围或工期先明确，不把未验收Issue自动关闭制造完成率。

## PR模板（后续复制到托管配置）

```text
关联：BE-xx / 实际Issue链接
行为：具体触发条件与变更后结果；UC/API/数据库T/I及设计章节
改动：边界、接口/迁移影响、与依赖PR的关系
验证：RED实际命令/失败原因；GREEN命令/结果；集成/Schema/并发证据
限制：未运行项、环境阻塞、未通过场景与后续Issue
评审：另一成员确认权限/版本/原子性/恢复/日志与凭据边界
```

每个PR尽量覆盖一个可验收行为或明确基础能力，避免35个任务合成一个大PR。共用guard/身份/请求状态/迁移及DTO变更必须由相关域主责参与评审。API/表变化先更新权威设计并校验，不能在Apifox或实体中单独演进。PR通过后集成负责人更新共享MEMORY/DECISIONS及导航，与对应集成改动同提交；不另建个人项目状态记忆。

若采用GitHub，`Closes #实际号`只对默认分支的受支持关联场景起自动关闭作用，不能假设向任意集成分支合并就关Issue；向其他分支先引用/手动关联，最终Accepted后关闭。官方依据：[链接Issue与PR](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)、[评审及保护分支](https://docs.github.com/en/pull-requests/reference/managing-and-standardizing-pull-requests)。这些流程尚未在远程启用。

## TDD和CI门禁

正式业务实现前读取项目TDD及writing-good-tests。每模块先写验收行为，再运行失败测试确认因为缺目标行为而失败，随后最小实现、GREEN及重构。依赖OA慢/不确定可以替换外部端口，数据库事务/身份授权不能以mock调用次数充当结果验收。

拟议CI：固定JDK/Wrapper→编译和单元→HTTP契约→隔离MySQL迁移/JPA/并发关键集成→生成候选jar/校验和。工具不可用应失败或明确待运行，不静默跳过后称已验收。部署BE-34单独记录目标环境，CI产物通过不等于服务器已部署。当前不创建`.github`或运行CI/业务测试。

每天2～3小时内预留短沟通/评审时段，优先消除依赖PR；PR说明使用已有模板降低往返。跨域问题在Issue集中记，已确认需求不重新全量访谈；真正改变含义的冲突由团队负责人向用户确认，同时继续独立工作。

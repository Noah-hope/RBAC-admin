# 公共基座范围与交接验收

修订1.1；2026-10-17；D-038已确认：**用户先实现公共基座，验收并纳入共同主线后，再将业务工作分派给团队。** 本文件是后续实施标准，本次只更新设计/任务，不表示已写代码、运行迁移或通过基座验收。

## 两阶段及当前归属

| 阶段 | 范围 | 负责人 | 当前事实 |
| --- | --- | --- | --- |
| 第一阶段：公共基座 | BE-01～05；工程及HTTP公共适配、迁移/JPA基础、读写事务、幂等、审计追加、测试支撑与调用说明 | 用户已确认负责；机器字段用USER表示 | 5项PLANNED，基座门槛NOT_EVALUATED，无验收证据 |
| 第二阶段：业务及交付 | BE-06～35，包括身份、权限、申请、组织业务、演示OA、部署与完整验收 | 基座验收后由用户分派；当前ownerSlot=null | 30项PLANNED/UNASSIGNED，评审人也未登记 |

USER仅是计划中的基座负责人代号，不是后台账号、员工身份、JWT主体或业务角色。A～D及suggestedOwnerSlot只保留历史职责建议，不能据此认定已分配真实人员。其他成员可阅读、评审和准备样例；实际业务分派和开工留在第二阶段。

## 基座到底做到哪里

| 任务 | 必须交付的公共能力 | 后续业务负责的部分 |
| --- | --- | --- |
| BE-01 | 核对共同main、用户本机工具及隔离MySQL条件、基座PR和非作者评审方式，登记环境待办 | 不要求提前分派30项业务；服务器采购和部署条件留后续，不能阻断可独立完成的本地基座 |
| BE-02 | 可构建/启动的工程、固定Wrapper/依赖、配置及缺配置失败、健康、请求ID、严格DTO和Problem公共适配、测试运行方式 | 67个入站业务接口由对应任务实现；不生成空业务接口冒充已完成 |
| BE-03 | 将现有43表及41触发器草案审查为可管理迁移，在隔离MySQL实测；提供UUID、UTC、生成列及版本映射基础样例 | 各域实体/Repository和领域不变量由业务任务补齐，不为所有表预写完整业务模型 |
| BE-04 | CommandBoundary/ReadBoundary、WriteContext、写锚点与锁约定、同事务AuditAppender、失败分类及原事务回滚后记录约定；真实双连接验证 | 当前账号/任命/任职等资格读取和事件业务内容由后续领域提供；审计查询及可见性是BE-19，不放进公共追加器 |
| BE-05 | 幂等摘要/预留/租约/栅栏、同key冲突、安全结果回放及当前授权回调；验证重复、过期接管、丢响应和删除后重放机制 | 用隔离夹具演示目标删除后的回放，不提前实现草稿API；BE-20/33验证真实草稿删除链路 |

`common`在本轮表示公共基座责任范围，代码包仍沿用既有设计的`core`，不额外建立第二套同义公共包。M00是主要承载者，M12的公共HTTP装配和M11的读事务约定也有基座部分；它们的业务实现不因此全部归用户。13个逻辑模块、数据边界及命令依赖保留。

身份/权限/申请/组织四组是第二阶段的分工视图：身份组覆盖M01/M03等，权限组覆盖M04/M05及权限读投影，申请组覆盖M07/M08/M09及审计读取，组织组覆盖M02/M06/M10的相应能力；跨域生命周期用例仍有明确协调者，M11/M12按所属任务维护。实际人员届时确定。

公共ActorContext、资格读取端口及授权回调先明确参数和调用约定。真实登录、JWT、会话、管理员范围及资格校验属于BE-06/08等第二阶段任务，不把完整identity提前塞进基座。测试夹具只在测试中提供身份，运行模式不能默认总管理员或信任请求自报范围；业务HTTP验收仍等待真实身份能力。

CanonicalPayloadCodec先明确规范摘要接口和调用边界；固定申请的RFC8785实现、选库及向量验证归BE-21，不能成为反向要求申请业务先完成的基座门槛。业务校验、审批状态、来源周期、导入计划和有效权限计算保持所属领域职责。

## 基座交接门槛

以下是未来验收清单，当前均未运行、未勾选。每项都要在Issue/PR登记实际命令、环境版本和观察结果，不能仅写“加事务”“应用保证”或引用设计静态PASS。

| 门槛项 | 需要看到的证据 |
| --- | --- |
| F-01 可重复工程 | 另一成员按说明从固定提交构建、启动；缺必要配置能明确失败；健康和日志不泄露秘密；记录依赖及实际工具版本 |
| F-02 真实持久化基础 | 隔离MySQL版本/迁移历史、43表/41触发器编译及非法约束拒绝、UUID/UTC/生成列/版本基础映射结果；不能用H2替代 |
| F-03 原子性及读一致性 | 两个真实连接控制取得锁与提交顺序；业务夹具写入和审计注入故障后整体回滚；新读事务不复用旧快照 |
| F-04 公共幂等 | 同key同/异内容、接管栅栏、成功丢响应、删除后按当前授权回放的可观察结果；夹具与实际业务端到端证据分开 |
| F-05 使用说明 | 公共接口输入输出、异常、事务由谁开启、端口能否另开事务、何时复核、如何写测试及后续扩展；秘密由环境提供 |
| F-06 独立评审与主线交付 | 至少一名未参与相应改动的成员评审；5项任务各自负责部分验收，已合入共同主线，记录提交、PR和残留事项 |

BE-01/02/03/04/05各按TASKS的acceptanceScope验收，部分AT包含业务阶段补充项：例如BE-05证明公共机制，不代表整个AT-04及草稿业务已通过。全量行为和服务器仍由BE-33/34/35汇总，不借基座交接关闭后续任务。

F-01～F-06实际满足后，在`delivery-phases.json`记录基座验收证据及FOUNDATION_ACCEPTED，由用户据此分派后续任务。当前生成器保存的是计划，所有证据为空；实施时应同步维护生成器的计划状态来源，不能手改JSON后重新生成又被覆盖。尚未满足的必需门槛不得以“有说明”替代；确有范围调整先明确修订设计和交接边界。

## 分派业务任务时要补什么

1. 用户把BE-06～35分配给实际成员，填写唯一Owner、未参与该改动的Reviewer、真实Issue链接、实际API/模块改动范围和依赖PR。可以分批分派，不要求每项同时开工。
2. 同步TASKS、issues、操作追踪及模块的真实人员信息；suggested字段保留参考身份，不能把建议组当账号。当前NULL不等于“大家共同负责”。
3. 每项业务同时满足FOUNDATION_ACCEPTED、BUSINESS_OWNER_ASSIGNED和原dependencies才进入正式实现；基座通过不替代BE-06/10等业务前置。
4. 分派后按实际负载更新估算。B协助账号、C协助打包等此前讨论只是可选建议，本轮不固化为任命或分配。
5. 正式业务仍逐任务TDD、PR及集成验收。服务器可并行准备；前端后置、演示OA及全量需求边界不变。

## 2. 工程方案

用户已确认采用 Vue 3、TypeScript、Vite 和 Element Plus。配套使用 Vue Router、Pinia 和 npm。工程拟放在仓库根目录 `frontend/`，与两套后端并列。

- `api/`：按身份、应用权限、角色、用户部门、申请和日志划分请求函数及类型。
- `stores/`：保存会话和当前身份，页面列表与表单状态留在对应功能内。
- `router/`、`layouts/`、`views/`：分别组织路由、导航外壳和业务页面。
- `components/`：复用权限目录、角色配置表单、权限来源展示和无权限申请入口。
- 请求层统一处理 Bearer、Problem 响应、401 和 204；成功数据直接使用，不假设存在 `data` 包装。
- 开发代理将 `/auth`、`/api/v1` 转发到 `http://localhost:8081`，保留路径。当前后端没有配置 CORS，先通过同源代理联调。

参考 [Vue 官方初始化说明](https://vuejs.org/guide/quick-start.html)、[Vite 环境要求](https://vite.dev/guide/)及 [Element Plus 安装说明](https://element-plus.org/en-US/guide/installation.html)。依赖版本在初始化时核对兼容性并通过锁文件固定。

沿用原型的深蓝导航 `#172C43`、绿色操作强调 `#096A5A`、浅灰蓝画布 `#F3F6FA`、白色内容区 `#FFFFFF`、正文 `#172A3D` 和边线 `#DCE5EE`。字体沿用微软雅黑及系统中文字体。保留左导航、顶部身份、列表筛选和配置弹窗结构；权限名称、获得方式和来源角色是角色配置的主要信息。

## 3. 页面与接口

以下为页面对应的主要路径，完整方法、参数和响应以 RBAC1 契约为准。

| 页面或能力 | 主要接口 | 实施要点 |
| --- | --- | --- |
| 登录、恢复身份、退出 | `/auth/login`、`/auth/me`、`/auth/logout` | 登录指定 `systems=["permission-center"]`；刷新后重新读取身份 |
| 应用与菜单按钮权限 | `/api/v1/applications`、`/api/v1/applications/{applicationId}/permissions` | 应用 code 固定；按钮归属同应用菜单；保留完整 API 关联 |
| API 登记 | `/api/v1/applications/{applicationId}/apis`、`/api/v1/applications/{applicationId}/apis/{apiId}` | API 清单和权限关联分别维护；解绑保留 API，删除登记另作确认 |
| 角色管理 | `/api/v1/roles`、`/api/v1/roles/{roleId}`、`/api/v1/permission-catalog` | 直接权限与父角色一起保存；展示有效权限和全部来源 |
| 用户与部门 | `/api/v1/departments`、`/api/v1/users` | 总管理员与部门管理员按职责显示操作，后端校验管理范围 |
| 用户授权 | `/api/v1/users/{userId}/roles`、`/api/v1/user-role-assignments` | 单人完整替换角色列表，批量按分配或撤销动作处理 |
| 我的权限 | `/api/v1/me/permissions` | 按应用展示菜单按钮及配置来源 |
| 我的申请、权限申请审核 | `/api/v1/me/requestable-permissions`、`/api/v1/permission-requests` | 用 `view=MINE/REVIEW` 区分；详情读取候选角色，另调用撤回或审核接口 |
| 角色创建申请 | `/api/v1/role-creation-requests` | 复用角色编辑器；总管理员提交审核配置时创建角色 |
| 操作记录 | `/api/v1/operation-logs` | 搜索、分页；记录范围和内容以服务端返回为准 |

课程管理系统在现有 HTML 中是接入演示，本轮准备不将其课程业务页面计入权限中心正式前端。

## 4. 对接时必须保留的规则

### 身份与权限

- 权限中心前端使用 `permission-center` 应用下的 `/auth/me`，由 `managementRole` 识别 `TOTAL_ADMIN`、`DEPARTMENT_ADMIN`、`NONE`。默认的 `roles` 是数字 ID 字符串。启用映射的接入应用将收到自身配置的角色码。
- JWT 不携带权限，不从 JWT 推导导航或按钮权限。登录、恢复会话及授权修改后按需重新读取当前授权，服务端拒绝结果仍需即时展示。
- 无权限菜单、按钮保留入口；点击时展示无法访问提示和申请入口，不加载受保护业务数据。职责专属功能按管理员职责控制。
- 申请目录直接读取服务端结果：尚无菜单时申请菜单，已有菜单后才申请其下按钮。
- 401 清理失效会话并返回登录；403 展示无权限状态，保留有效会话。退出调用服务端撤销接口。

### 角色配置与继承

- 表单分别维护 `permissionIds` 和 `inheritedRoleIds`，创建和修改都提交最终完整列表。空数组表示清空，不能省略继承列表，也不能把有效权限全量回传为直接权限。
- `DIRECT`、`INHERITED`、`BOTH` 分别显示直接、继承、两者同时存在。权限只显示一行，来源列出全部实际直接配置角色并去重。
- 仅继承权限只读，不能新增重复直接配置。已有直接权限后来与继承重叠时保留；取消直接配置后，仍通过继承获得权限。
- 切换父角色时，以本次父角色选择预览继承结果；根据已保存的直接权限判断哪些是允许保留的原有重叠配置。
- 按钮所属菜单可以通过直接或继承满足。后端会校验当前角色及后代，保存失败时保留编辑内容并展示具体角色、按钮和菜单。
- 预置管理角色只读且不能参与继承。删除业务角色前展示关联用户数和双向继承关系，最终以删除接口校验为准。

### 申请、列表与错误

- 权限申请审核使用详情返回的 `approvalRoles`、`selectable`、`extraPermissionIds`，展示候选角色在所有应用中的完整有效权限，不自行猜测最小角色。
- 角色创建申请“受理”只打开表单。审核接口成功创建角色后才显示已通过；取消或失败保持待审核，不自动为员工分配角色。
- 申请中的父角色 `exists=false` 时保留名称快照，`effectivePermissions` 可以为 null；审批前改选有效父角色。
- 列表统一使用 `items/page/pageSize/total`，页码从 1 开始，每页最多 100 条。用于父角色等完整选择的候选列表应读取全部分页，避免只使用第一页。
- 错误按 `application/problem+json` 读取服务端提示；204 无正文时不解析 JSON。表单应提交明确类型，后端拒绝数字字符串及未知字段。

## 5. 开发顺序与验收

1. 建立前端工程、开发代理、请求层、登录恢复、退出和导航外壳。验收登录成功、刷新恢复、401 返回登录、403 保留会话。
2. 实现应用权限、API 登记和角色配置。优先验收多层多继承、来源去重、仅继承只读、已有重叠保留、取消直接配置、循环拒绝和后代菜单依赖错误。
3. 实现用户部门、单人与批量授权。验收部门管理范围、停用提示、完整列表替换和批量动作区别。
4. 实现我的权限、两类申请与审核。验收无权限申请入口、候选角色限制、撤回、已满足状态和审批创建失败保留待审核。
5. 实现操作记录，完成真实后端联调、三类身份操作检查和前端构建验证。

复杂权限表单与会话行为先写能失败的测试，再实现；页面验收使用真实业务场景。至少覆盖总管理员、部门管理员、普通用户，以及加载、空列表、无权限和失败反馈。

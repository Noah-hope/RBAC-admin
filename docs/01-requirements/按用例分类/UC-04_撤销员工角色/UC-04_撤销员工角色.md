# UC-04 撤销员工角色

版本：V1.2，2026-10-15。状态：功能权限、部门管理范围及员工启停流程已按用户确认修订，可作为界面原型依据。

本轮更新：管理范围按公司、部门子树及系统指定；离岗关闭原部门来源权限立即生效，全局停用仅总管理员；保留功能权限、OA 及历史规则。

### 当前需求基线（2026-10-15，V1.2 部门范围与员工启停）

- 一期实现 RBAC0 权限管理：员工经角色获得权限，无角色继承、直接用户授权或显式拒绝。外部系统只做简单 HTTP 调用演示，不实现其内部业务。
- 角色属于一个公司和一个业务系统，可限定部门；公司级角色要求本公司有效任职，部门级角色要求在该部门直接有效任职，不自动覆盖下属部门。岗位不自动绑定角色；任职条件与权限需要均未改变时，不因岗位名称变化更换角色。
- UC-05/06 按“员工＋当前公司＋业务系统”计算权限。仅合并该公司、该系统内的有效角色；系统进入资格与功能权限也必须来自该公司、该系统。公司上下文隔离的是功能授权来源，不定义业务数据访问范围。
- 授权同时校验角色适用条件与来源部门。离岗关闭原部门来源立即失效，其他独立兼岗来源保留；公司级共享角色不随调岗自动转移。仅总管理员可全局停用/恢复员工；恢复不复权。新授权经 OA，新管理任命由总管理员办理。
- 当前 RBAC 系统只管理功能权限。目录登记系统进入权限与功能操作，角色配置是否授予；不定义、保存或返回业务数据范围，不设计本人记录判断或行过滤规则。
- 员工、公司、部门使用稳定内部 ID；首次导入以源唯一用户名建立员工映射，组织分配稳定编码，更名不改变身份。人员变更模板明确新增任职、结束任职、停用、恢复等动作，不从文件缺行推断离职。
- 一期使用至少两个公司、两个系统的代表性数据，覆盖多角色、兼岗、公司授权隔离、功能操作独立与去重、审批生效、撤销、失效及重新申请。其余资料后续逐步补齐。

以上为本轮已确认规则，详细流程与验收必须遵循；描述的是需求设计，不代表代码已实现或真实外部系统已完成对接。

## 1. 用例概述

| 项目 | 说明 |
| --- | --- |
| 编号与名称 | UC-04 撤销员工角色 |
| 目标 | 撤销指定员工的指定角色授权，保留其他有效授权来源 |
| 发起者 | 总管理员，或获准公司、来源部门子树及系统内的权限管理员；不限于原分配人 |
| 外部参与者 | OA 系统，负责审批并返回最终结果；不展开审批人和内部流程 |
| 执行者 | 权限中心，通过 UC-11 接收结果、校验并执行 |
| 触发 | 一般角色撤销走 OA；员工调离/离职关闭原部门来源权限走本用例的直接办理子流程 |
| 前置条件 | 管理员已登录且具备目标来源组织的撤权资格；一般撤销关系存在且可定位；离岗关权允许仅有待执行分配或来源周期 |
| 提交成功结果 | 保存待审批撤销方案，当前授权不因提交而改变 |
| 执行成功结果 | 选中的授权关系标记为已撤销，后续权限查询按剩余有效角色计算 |
| 失败保证 | 驳回、校验失败或执行失败不撤销授权；执行失败整批回滚 |

撤销的是员工与角色的关联，不删除角色、不修改角色权限，也不影响其他员工拥有该角色。本用例的一般撤销与离岗关权均不执行员工全局身份停用。

### 管理范围与人员权限（V1.2 已确认）

完整规则见 [管理范围与人员权限规则](../../usecases-v1/管理范围与人员权限规则.md)。总管理员指定公司、管理根部门及系统，部门范围含下级但不跨公司；同范围协作，不因同公司就共享整家公司权限。

公司级共享角色只由总管理员维护，权限管理员可为范围内合格员工申请分配；部门角色按明确归属维护。每次员工授权固定实际来源部门，不等同管理员根部门或角色归属。

离岗关闭原部门来源权限立即生效、不等待 OA；一般角色配置、分配及撤销仍经 OA。全局员工停用/恢复仅总管理员；恢复不自动复权。不设计公司/部门启停，普通员工不登录本平台。

## 2. 已确认规则与设计约定

已确认的核心规则：

- 一般指定角色撤销必须经 OA；离职/调离关闭原部门来源使用直接子流程，不等待 OA。批准不等于一般撤销已执行成功。
- 只撤销选中的员工—角色关联，重合权限由其他有效角色继续提供。
- OA 是外部系统，本项目不设计审批人员、层级或流转规则。

沿用当前管理规则：管理员仅在共同获准范围协作，不按原分配人隔离；员工可兼岗并拥有多个系统的角色，不能借撤销某项授权覆盖其他公司的授权。

本稿采用以下实现约定，供后续接口和数据库设计落实：

1. 一份申请办理一个来源公司（总公司或分公司）的撤销，可包含多名员工、多个系统的明确授权关系。每条关系单独校验范围。
2. 批量方案整体执行或整体回滚；不擅自执行已批准清单的一部分。
3. 保留已撤销关系及审计记录，不通过物理删除丢失授权历史。
4. 已失效或已撤销的来源只读展示、无需再次审批。系统停用但关联仍有效时允许合法一般撤销。离岗关权可直接关闭获准部门来源，不等待 OA，也不全局停用员工。
5. 提交时校验办理人资格；执行时按原资格来源复核对应范围及关系版本，不等待人员接手，原申请人离任不单独使方案失效。

### 系统进入权限（已确认）

撤销后先计算该系统是否还存在有效进入权限来源。若最后一个来源被撤销，UC-05 返回不可进入且菜单、操作为空，UC-06 对该系统功能检查返回无权限；其他功能授权关联保留，不批量删除。

其他角色仍提供进入权限时，按剩余功能权限正常计算；重新通过批准执行获得进入权限后，尚有效的功能配置可以恢复使用，已撤销的角色关联不会恢复。移除一个系统的进入资格不影响其他系统，也不等于全局员工停用。

### 申请归属、资格来源与自动执行（已确认）

角色和已提交申请不归原申请人个人；角色按公司/部门归属，员工授权明细按来源公司/部门归属。同范围管理员可协作，不能因同公司就访问其他范围。原管理员离任不单独阻断已提交合法申请，目标员工来源关闭则按来源周期拒绝旧批准；保留原提交人与固定内容。

提交时固定资格依据：总管理员为全局资格，权限管理员为明确公司、部门子树及系统的范围记录和版本。UC-11 按原范围记录复核，不能换用当前查看人的更大资格；按申请类型检查对应目标条件：配置查角色归属及版本，授予查来源部门/任职/周期与角色关系版本，一般撤销查指定来源及关系版本，不机械要求当前授予资格。总管理员原申请仍明确实际来源部门，不受普通管理员系统清单限制。

收到可信最终批准后，权限中心自动尝试执行合法的固定方案，不等待任何管理员点击接手或再次确认；原申请人离任、公司暂时没有权限管理员均不单独阻止执行。短暂故障保留批准依据并由服务端重试，重试仍检查原资格来源对应的范围及目标条件；仅实际范围或目标条件不再合法时标记失效。员工角色分配仍须检查目标员工有效任职，撤销历史关联不要求目标员工仍在原岗位。

一期不提供人为取消已批准方案的入口，不以“失效”代替任意取消。合法方案执行或在短暂故障后重试；实际条件不再合法则失效并记录原因。执行成功后如需调整，按 UC-02～04 重新申请。未提交草稿的删除规则保持独立。

未提交草稿可由范围内管理员删除并记录删除事件，释放变更占用；新角色从未提交、从未生效且无引用时一并删除空草稿。已正式提交或已生效的角色/申请保留历史，不借删除绕过审批。正式角色配置提交后须至少包含一项权限（系统进入权限或功能操作均可），不产生已生效空角色；清理员工授权走 UC-04。


## 3. 输入与输出

| 输入 | 含义 |
| --- | --- |
| 授权关系 ID 列表 | 明确撤销哪些员工—角色关联；不只传角色名或员工名 |
| 来源组织 | 由已有关系确定并由后端核对，不能任意改写成当前权限管理员的组织 |
| 授权关系版本 | 绑定审批对象，避免旧撤销申请误撤后续重新授予的关系 |
| 撤销原因 | 职责调整、不再需要等，供外部审批和审计使用 |
| 方案/编辑版本、请求编号 | 区分申请、检测编辑冲突并防止重复提交 |

操作者来自后端登录上下文。后端根据关系 ID 读取员工、角色、系统与来源，前端显示的名称只作辅助。

提交输出方案编号、待审批状态和撤销明细；执行输出结果、实际撤销关系与审计关联编号。无变化、待审批、已批准待执行、执行成功必须分别表示。

## 4. 正常流程

| 步骤 | 管理员/外部系统操作 | 权限中心处理 |
| --- | --- | --- |
| 1 | 管理员进入员工授权页面 | 验证总管理员或权限管理员身份及对应撤权范围，展示可管理的授权关系，支持查找已调离员工的本组织历史授权 |
| 2 | 选择员工与拟撤销的角色关联 | 展示角色、系统、授权来源和当前状态；只能选择可管理关系 |
| 3 | 预览并填写原因 | 列出明确撤销明细及可见范围内的影响，提示其他角色可能继续提供重合权限 |
| 4 | 确认提交 | 校验范围、关系状态与版本，去除提交前已撤销的无变化项；冻结实际撤销清单并记录申请 |
| 5 | 查看一般撤销申请 | 保留原有效授权，分别显示 OA 投递、审批和执行状态；未发送成功不能称为 OA 已受理 |
| 6 | OA 完成审批 | 返回关联原申请的最终批准或驳回结果，不展开内部审批过程 |
| 7 | UC-11 接收结果 | 校验来源、申请编号和内容一致性；驳回只更新方案状态，批准进入待执行 |
| 8 | 权限中心执行撤销 | 按原资格来源复核对应范围和全部关系版本，批准后自动执行，原子标记关系已撤销、更新版本、执行状态及成功审计 |
| 9 | 管理员查看结果，业务系统再次校验 | 显示执行成功；权限中心按剩余有效角色计算权限，业务系统据结果拦截或放行 |

提交待审批仅表示本次撤销尚未执行，不保证原授权在等待期间不会因员工停用或其他合法变更失效。

预览只是当前状态的参考，不是未来权限保证。权限管理员无权查看的其他组织角色不应泄露，也不能因此断言员工撤销后必然没有某项权限。

## 5. OA 边界与方案状态

采用与 UC-02、UC-03 一致的状态：草稿 DRAFT、待审批 PENDING、已驳回 REJECTED、已批准待执行 APPROVED、执行成功 EXECUTED、执行失败 EXECUTION_FAILED；原资格来源对应的范围或目标条件不再合法的方案使用已失效 INVALIDATED。

- 已提交内容不能直接修改；驳回后保留原记录，复制新草稿、修改并重新提交。
- 一期通过模拟 OA 返回批准/驳回结果验证交互，不实现 OA 页面或审批引擎。
- 普通管理页面不能将申请直接改为已批准；模拟结果也须经过来源校验和申请匹配。
- 短暂执行故障可重试同一已批准方案，重试仍按原资格来源检查对应范围、目标条件与版本。
- 撤回 WITHDRAWN 为可选扩展，一期不要求对接；未支持时不能仅在本地取消待审批申请后忽略 OA 状态。

## 6. 权限变化示例与身份停用边界

以下功能保留示例以撤销后仍有对应系统进入权限为前提。

| 原有角色 | 撤销目标 | 执行后的权限 |
| --- | --- | --- |
| A：查看、审批报销；B：查看报销 | A | 保留查看，失去审批 |
| A：查看员工信息；B：查看员工信息 | A | B 仍提供查看，结果去重且功能权限保留 |
| 桥梁公司 HR 角色；另一公司项目角色 | 桥梁公司 HR 角色 | 项目角色保持不变 |

先判断剩余角色是否提供系统进入资格，再取剩余有效角色的功能操作并集；还需考虑员工、角色、系统及权限自身的有效状态。不能直接把被撤角色包含的权限逐项从员工身上删除；同一操作仍有有效来源时继续保留。

员工身份停用是另一项操作：权限中心发现员工已停用时拒绝访问，同时使其业务授权失效并保留历史。UC-04 不停用或恢复员工身份，也不绕过 OA 自动批量撤销所有角色。实际拦截由已接入且执行权限校验的业务系统完成，不承诺回滚已完成或正在执行的外部业务操作。

## 7. 替代、异常与并发

| 编号 | 条件 | 处理 |
| --- | --- | --- |
| E01 | 既无总管理员资格也无权限管理员资格，或目标不在对应管理范围 | 拒绝整次请求，不披露越范围人员信息 |
| E02 | 关系不存在或提交版本已改变 | 提示重新读取，不按名称猜测或替换目标 |
| E03 | 提交前关系已撤销或因任职／停用已失效 | 标记无变化并排除；全部无变化时不发起 OA |
| E04 | 员工已调离/停用或系统停用 | 失效历史只读；仍有效且可管理的来源可走一般撤销。离岗关权使用直接子流程，不等待 OA |
| E05 | OA 驳回 | 保留原授权和审批历史，修改后以新方案重提 |
| E06 | OA 结果来源不可信或与固定申请不匹配 | 拒绝执行，不把填写审批单号当作批准证明 |
| E07 | 重复成功通知 | 返回原执行结果，不重复撤销或新记一次成功撤权事件 |
| E08 | 执行前关系已被其他方案改变、撤销或重新授予 | 旧方案失效，不误撤新授权；整批不部分执行 |
| E09 | 原申请人离任或原公司、部门及系统管理范围变化 | 仅离任不阻止自动执行；按原范围依据复核，指定来源或关系版本不合法时失效重提 |
| E10 | 批量中一项越权或关系版本冲突 | 整体拒绝，不擅自缩小原批准清单后执行 |
| E11 | 撤销或成功审计写入失败 | 整批回滚；另行记录失败，保留可恢复状态，不能显示已撤销 |

同一获准范围的管理员可协作查看方案；草稿编辑检查版本。对于相同授权关系，一期建议拒绝重叠的未结束变更申请，避免重复办理；不同员工的同一角色不互相锁住。

执行以关系 ID 和版本定位一次授权；员工停用或失去适用任职导致的失效也更新关联状态／版本，保留原因与历史。若撤销或失效后重新授予，应形成新的授权记录或递增的授权版本；旧撤销审批不得作用于新授权。此规则与 UC-03 的防止旧授予恢复已撤销或已失效权限共同落实于 UC-11。

角色权限调整不会改变本次“撤销指定角色关联”的目标，因此不机械沿用 UC-03 的角色权限版本一致要求；保留申请时的影响摘要，实际剩余权限由当前有效配置计算。若目标关系或原资格来源对应的范围改变，则仍按上述版本/范围规则处理。

| 保存/提交方案 | 范围、目标关系与版本、重叠申请 | 固定撤销明细、原因、请求编号与提交记录 | 不修改有效授权；保存与提交记录一致 |
| 接收最终结果，UC-11 | OA 身份、申请编号与内容 | 审批结果、接收记录和方案状态 | 可靠记录且防重复；批准和执行成功分开 |
| 执行撤销，UC-11 | 提交资格依据及对应范围、关系版本、批准方案 | 关系状态/版本、执行状态与成功审计 | 全批次同一本地事务，校验与更新防并发覆盖 |

逻辑实体沿用 EmployeeRole、Role、RolePermission、AdminScope、AuthorizationChange 及明细、AuditLog；本用例不要求新增一套权限表。等待 OA 时不持有数据库事务。数据库整体不可用时，记录服务端错误并保留可恢复的批准状态，不伪报成功。

## 9. 结构化功能分解

```text
撤销员工角色
├── 查询范围内授权关系
├── 整理撤销明细并预览影响
├── 校验管理范围、关系状态与版本
├── 排除无变化项、检查重叠申请
└── 保存固定方案并提交外部 OA

外部 OA：完成审批 → 返回最终结果
UC-11：验证结果 → 按原资格来源复核范围及关系版本 → 原子撤销及记录审计
UC-05/06：按剩余有效角色计算功能权限集合
```

这些是处理职责的分解，不要求每一步独立部署，也不因此把所有相关用例连成 include。

## 10. 验收示例

| 编号 | 场景 | 预期 |

| UC04-T02 | OA 批准且执行成功 | 只撤销批准的关联，不删除角色或影响其他员工 |

| UC04-T05 | 员工跨公司兼岗，撤销本公司角色 | 其他公司/系统授权保持不变 |
| UC04-T06 | 同一指定范围的管理员乙处理甲授予的来源 | 允许在来源公司、部门及系统范围内办理；同公司其他范围不自动获权 |

| UC04-T13 | OA 批准但执行失败 | 显示未成功执行，关系不因本次失败而改变 |
| UC04-T14 | 伪造审批结果或仅手填审批号 | 不执行撤权 |

| UC04-T16 | 目标关系未变，角色权限在审批期间调整 | 仍撤销批准的指定关联；剩余权限按最新有效配置计算 |

## 11. 后续衔接

UC-04 的一般撤销经 OA、离岗关权直接生效已确认，不再混用。后续在 UC-11 及 API/数据库设计中统一结果来源校验、关系版本、防重复执行、批量限制和失败恢复，不设计 OA 内部流程。

员工身份停用、任职同步后的处理在员工状态相关用例中另行说明，不能通过本用例隐式扩大为停用员工或清除全部角色。

### 失效历史与撤销边界

UC-10 任职变化/全局停用或本用例离岗关权使来源失效时，不等待 OA，不删除历史。失效项作为历史／无变化项，不再申请撤销；新授予必须新批准，并受来源授权周期与关系版本保护。

## 离岗关闭原部门权限（直接办理子流程）

本子流程用于员工离职/调离，和前述“一般指定角色撤销申请”分开。权限管理员只在当前选定公司、来源部门子树及获准系统内办理，总管理员可办理所有来源；不修改员工全局身份或 HR 任职资料。

| 步骤 | 办理与处理 |
| --- | --- |
| D1 | 选择员工、明确原来源部门、获准系统，填写离职/调离原因 |
| D2 | 后端校验当前管理资格与来源范围；读取来源内有效授权、待执行分配及周期，预览影响，不泄露其他来源 |
| D3 | 明确确认关闭原部门权限；后端复核范围及全部相关版本 |
| D4 | 同一本地事务更新来源授权周期、将该来源有效关系及旧待执行分配标记失效，保存关闭事件及成功审计；全部成功才提交 |
| D5 | 返回立即生效结果；不发送 OA，后续功能查询保留其他独立有效来源 |

即使只有待审批/待执行分配、尚无有效关联，也更新来源周期以拒绝旧批准。一般撤销申请和离岗关权并发时依据周期及关系版本处理，不能让旧批准恢复被关闭来源。已失效历史只读；重复同一请求返回原结果，同编号不同内容拒绝；数据或成功审计写入失败整体回滚。

公司级共享角色也按来源关闭，不删除共享角色。重新授予必须新 OA 申请，不通过恢复员工身份复活旧来源。

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| UC04-D01 | A/B 部门分别授予同一公司角色，关闭 A | A 来源立即失效，B 保留，功能按有效来源去重 |
| UC04-D02 | A 来源只有待执行新增申请 | 关闭更新周期，之后旧批准不执行 |
| UC04-D03 | 员工从 A 到 B 后回 A | 旧来源与旧批准不恢复，需新申请 |
| UC04-D04 | 部门管理员请求全局停用或关闭越范围来源 | 拒绝，不能越出指定部门和系统 |
| UC04-D05 | 关闭事务或审计失败 | 整体回滚，不显示已关权 |

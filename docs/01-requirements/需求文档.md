# RBAC权限管理系统需求文档

2026-11-13

## 系统目标

为多个业务系统统一管理权限，决定用户可以看到哪些菜单、使用哪些按钮、调用哪些后端接口。

为本系统及所有接入的业务系统提供统一账号、登录、退出和权限检查服务。同一用户在不同应用中的权限分别管理。

权限先分配给角色，再把角色分配给用户。例如，“新增用户”和“删除用户”是两项不同的权限，可以分别授予。

## 基本功能

### 1 统一登录与退出

权限管理系统、课程管理系统及以后接入的其他系统，统一使用权限中心维护的账号和登录、退出服务。各业务系统不另设独立密码。

用户使用同一账号和密码登录接入系统时，由权限中心验证身份并返回登录令牌。各系统根据有效的登录令牌识别当前用户。

登录后，接入系统可以查询当前用户信息、角色和当前应用中的菜单、按钮权限。权限中心的「我的权限」页面可以按应用汇总展示用户拥有的权限。

用户可以从任一接入系统发起退出。权限中心使本次登录令牌失效，使用该令牌的各接入系统不能继续访问受保护接口。

### 2 用户与部门管理

管理员可以查询、新增、修改和停用管理范围内的用户。新增用户时，选择用户所属的部门。停用后，用户不能登录或使用受保护的功能。

总管理员维护公司、分公司和部门的上下级关系。

员工跨部门调动由总管理员负责。调动后，员工保留原有的业务角色，调入部门的管理员可以按需分配或撤销角色。

### 3 应用与权限管理

总管理员可以查看、新增和修改业务应用。

权限管理系统自身也作为一个应用管理，其菜单、按钮和管理 API 在本系统中统一配置。以后接入的业务系统按应用分别登记权限和 API。

选择一个应用后，总管理员可以查看、新增和修改该应用的菜单和按钮权限。新增按钮时，选择它所在的菜单。

登记权限时，权限标识由业务系统制定并提供。总管理员在对应应用下登记该标识。权限标识格式为 `资源:操作`，同一应用内必须唯一。权限中心不自动生成权限标识。

新权限保存后，会出现在该应用的角色配置树里。总管理员可以勾选它并授予角色。

总管理员在权限配置中查看、新增、修改和移除关联的 API。登记时填写业务系统 API 文档提供的接口标识（`operationId`）、请求方法和请求路径。权限中心保存并校验这些信息，不生成业务接口代码。

一项菜单或按钮权限可以关联多个 API，一个 API 也可以关联多个菜单或按钮权限。权限与 API 通过关联表建立关系，二者必须属于同一应用。同一应用内，接口标识唯一，请求方法与请求路径的组合也唯一。

角色仍然勾选菜单和按钮权限，不单独勾选 API。用户通过角色获得权限后，也获得调用该权限关联 API 的资格。

### 4 角色管理

总管理员可以创建和修改角色。配置角色时，在同一个界面选择业务应用，在一棵权限树中勾选菜单和按钮，一起保存。

一个角色可以包含多个应用的权限。

### 5 分配与撤销角色

管理员可以为管理范围内的用户分配或撤销已有的业务角色。保存成功后直接生效。

批量操作时，管理员勾选多名用户，再选择要分配或撤销的角色。用户的其他角色保留。

一个用户可以有多个角色，同时拥有这些角色授予的权限，重复的权限只算一次。撤销某个角色后，用户通过其他角色获得的权限仍然保留。

### 6 管理员范围

管理员也是用户，通过角色获得管理权限。系统预置一个总管理员账号，负责首次配置和全局管理。

总管理员可以给用户分配「部门管理员」角色。系统根据该用户的所属部门确定管理范围，包括本部门和下级部门。

部门管理员负责维护管理范围内的用户，并为这些用户分配或撤销已有的业务角色。

部门范围用于限制管理员可以管理哪些用户。业务数据的访问范围由各业务系统决定。

### 7 权限检查

前端保留本应用的菜单和按钮，根据当前用户的权限控制能否使用。无权限时的展示和申请入口按第 10 节执行。需要时，可以单独查询当前用户是否拥有某项菜单或按钮权限。

业务系统按以下流程检查接口权限。

1. 用户发起受保护的操作时，业务系统后端验证当前登录身份，并根据实际请求确定业务系统提供的 `operationId`。执行操作前，使用当前用户的登录令牌、目标应用和 `operationId` 向权限中心检查权限。
2. 权限中心识别当前用户和目标应用，查找该应用中 API 关联的权限。用户通过有效角色拥有其中任意一项权限，即通过该 API 的功能权限检查；管理员职责、部门范围和业务对象访问规则仍需满足。用户身份由登录令牌确定，不由前端任意指定用户 ID。
3. 登录令牌无效、用户停用、用户不存在、API 未登记或用户未获授权时，拒绝操作。业务系统收到允许结果后才执行操作；收到拒绝结果或无法完成检查时，不执行操作并提示用户。

权限管理系统自身受保护的管理接口也使用统一身份和权限检查，管理员的管理范围仍按第 6 节执行。

业务系统后端必须检查直接发送的 HTTP 请求，不能仅依靠前端隐藏菜单或按钮。权限中心不管理业务数据的访问范围，课程成员、任课教师、小组成员等具体业务对象的访问规则由业务系统自行判断。

保留按权限标识检查当前用户权限的能力。按 API 检查时，接口需要的权限由已登记的关联关系确定。

角色、权限或 API 关联修改保存后，下一次权限检查应反映修改结果。移除 API 登记后，针对该接口的检查返回拒绝。

### 8 操作记录

系统记录权限配置、API 登记与关联修改、角色分配与撤销、员工跨部门调动等重要操作。每条记录包含操作人、时间、操作对象、操作内容和结果。

总管理员可以查看全部记录。部门管理员可以查看本部门及下级部门用户的管理记录，例如分配角色、撤销角色和停用账号。

查看范围按操作发生时被操作用户的所属部门判断。一次操作涉及多名用户时，部门管理员只看到管理范围内的用户。

应用登记、API 配置、角色权限配置、员工跨部门调动，以及权限申请和角色创建申请处理等全局操作记录由总管理员查看。

系统不记录打开页面、浏览菜单或未保存的编辑行为。通过用户角色管理解除用户与角色关联时，记录为解除用户角色关联，不记录为撤销权限申请。

### 9 业务角色删除

总管理员可以删除未关联用户的业务角色。角色仍关联用户时禁止删除，提示关联人数，先撤销用户关联后再删除。停用账号的角色关联同样计入。总管理员和部门管理员等预置管理角色不能删除。删除时一并清理角色权限关联，保留用户、权限本身和历史操作日志，并记录本次删除。

### 10 权限申请
- 正常状态的普通用户可以申请业务菜单或功能按钮。
- 停用用户不能申请权限。
- 无权限的菜单继续显示。用户点击后，系统显示暂时无法访问的页面，并提供申请入口，不展示受保护的业务数据。
- 无权限的功能按钮继续显示。用户点击后，系统提示没有权限，并提供申请入口。
- 申请目录按应用区分菜单和按钮，只列出用户尚未获得的权限。未获得菜单时只展示该菜单；获得菜单后，才展示其下尚未获得的按钮。已获得的权限在「我的权限」查看。
- 用户提交申请时填写申请理由。
- 部门管理员只能审核自己管理范围内员工的申请。总管理员可以审核全部申请。
- 审批通过后，管理员选择包含所申请权限的现有业务角色，并通过用户与业务角色的关联授予权限。申请不直接授予单项权限。
- 管理员审批时可以查看角色的全部权限。现有角色包含无关权限时，不能直接使用该角色，应先拆分或新建最小权限角色。
- 申请状态包括：待审核、已通过、已拒绝、已满足、已撤回。
- 用户可以撤回待审核申请，撤回后状态变为已撤回。
- 待审核期间，用户已通过其他角色获得所申请权限的，系统将申请标记为已满足。
- 权限不设置有效期。
- 被拒绝的申请不会因后续创建角色而恢复。

## 角色创建申请

- 部门管理员没有创建或修改角色的权限。
- 现有角色无法满足员工权限需求时，部门管理员可以提交角色创建申请。
- 角色创建申请使用总管理员创建角色的编辑界面。
- 申请内容包括角色名称、角色说明和直接权限。
- 提交申请不会创建角色，也不会改变用户权限。
- 总管理员可以拒绝申请，或受理申请并进入角色编辑界面。
- 进入角色编辑界面后，申请仍为待审核。
- 总管理员可以调整角色配置。角色成功创建后，申请状态变为已通过。
- 取消编辑或未完成角色创建时，申请保持待审核。
- 角色创建申请状态包括：待审核、已通过、已拒绝。
- 角色创建申请不自动授予员工角色。员工需要重新申请，或由管理员按正常流程分配角色。

## 术语说明

- `operationId` 是业务系统 API 文档中用于唯一标识接口操作的名称，例如 `createCourse`。

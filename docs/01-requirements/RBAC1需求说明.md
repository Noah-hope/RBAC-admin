# RBAC1 需求说明

**适用范围：** 结构化设计与面向对象设计实现  
**状态：** 已确认需求

## 1. 角色继承

- 子角色继承父角色的全部有效权限。
- 支持多继承和多层继承，关系必须是有向无环图（DAG）。
- 禁止自继承和循环继承。
- TOTAL_ADMIN 和 DEPARTMENT_ADMIN 不参与业务角色继承。
- 角色不绑定单一应用；继承将包含父角色在所有应用中的权限。

## 2. 权限计算与展示

角色有效权限为其直接权限与所有可达父角色权限的并集。用户有效权限为其所有业务角色有效权限的并集。

- 重复权限只计算一次。
- 角色权限页面同时展示直接权限和继承权限。
- 继承权限显示来源角色；有多个来源时显示全部来源。
- 权限或继承关系保存成功后，下一次权限检查立即反映变更。
- 移除一个权限来源时，若该权限仍有其他来源，则继续有效。

## 3. 角色创建与修改

创建和编辑角色时，一并配置：

- 角色直接权限；
- 当前角色继承的角色。

修改时提交最终继承角色列表。系统据此新增、保留或解除继承关系。直接权限和继承关系须一起校验、在同一事务中保存；形成循环时整次操作失败，原配置不变。

## 4. 用户角色关联

用户角色关联继续采用完整列表替换：提交用户最终拥有的业务角色列表，系统只新增或解除发生变化的关联。空列表表示解除全部业务角色。分配和解除在同一事务中完成，保存成功后立即生效。

不新增单条用户角色解除接口。

## 5. 删除规则

### 用户

新增用户物理删除。删除用户时，在同一事务中先删除用户角色关联，再删除用户记录。

### 角色

新增业务角色删除，并采用关联检查：

- 内置管理员角色不可删除。
- 角色仍被用户持有时，拒绝删除并提示先解除用户角色关联。
- 角色仍参与继承关系时，拒绝删除并提示先解除继承关系。
- 删除时自动清理角色权限关联，保留权限定义。
- 删除角色及其权限关联在同一事务中完成。

### 应用

本阶段不实现应用删除。

## 6. 一致性要求

结构化实现与面向对象实现必须采用相同的继承方向、权限计算、关系修改和删除规则。

## 7. 验收条件

1. 多继承和多层继承的角色能获得所有父角色权限；重复权限不重复计算。
2. 系统拒绝自继承、循环继承和管理员角色参与业务继承。
3. 修改继承列表后，下一次权限检查反映新增或解除的权限；其他来源仍提供的权限保留。
4. 权限页面能区分直接权限与继承权限，并显示继承来源。
5. 更新用户角色列表只变更差异；空列表解除全部业务角色。
6. 用户删除会清理其角色关联；角色存在用户关联或继承关系时删除失败并提示先解除关系。
7. 删除角色会清理角色权限关联，但保留权限定义；应用不能删除。
8. 两种实现通过相同的上述验收条件。

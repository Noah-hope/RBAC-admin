# UC-06 检查员工指定操作权限

版本：V1.3，2026-10-16。状态：功能权限、部门管理范围及员工启停流程已按用户确认修订，可作为界面原型依据。

本轮更新：按参考材料采用公司—部门—岗位，部门平级；管理范围按公司、指定部门及系统指定；离岗关闭原部门来源权限立即生效，全局停用仅总管理员；保留功能权限、OA 及历史规则。

### 当前需求基线（2026-10-16，V1.3 平级部门与员工启停）

- 一期实现 RBAC0 权限管理：员工经角色获得权限，无角色继承、直接用户授权或显式拒绝。外部系统只做简单 HTTP 调用演示，不实现其内部业务。
- 角色属于一个公司和一个业务系统，可限定部门；公司级角色要求本公司有效任职，部门级角色要求在该部门有效任职，不适用于其他部门。岗位不自动绑定角色；任职条件与权限需要均未改变时，不因岗位名称变化更换角色。
- UC-05/06 按“员工＋当前公司＋业务系统”计算权限。仅合并该公司、该系统内的有效角色；系统进入资格与功能权限也必须来自该公司、该系统。公司上下文隔离的是功能授权来源，不定义业务数据访问范围。
- 授权同时校验角色适用条件与来源部门。离岗关闭原部门来源立即失效，其他独立兼岗来源保留；公司级共享角色不随调岗自动转移。仅总管理员可全局停用/恢复员工；恢复不复权。新授权经 OA，新管理任命由总管理员办理。
- 当前 RBAC 系统只管理功能权限。目录登记系统进入权限与功能操作，角色配置是否授予；不定义、保存或返回业务数据范围，不设计本人记录判断或行过滤规则。
- 员工、公司、部门使用稳定内部 ID；首次导入以源唯一用户名建立员工映射，组织分配稳定编码，更名不改变身份。人员变更模板明确新增任职、结束任职、停用、恢复等动作，不从文件缺行推断离职。
- 一期使用至少两个公司、两个系统的代表性数据，覆盖多角色、兼岗、公司授权隔离、功能操作独立与去重、审批生效、撤销、失效及重新申请。其余资料后续逐步补齐。

以上为本轮已确认规则，详细流程与验收必须遵循；描述的是需求设计，不代表代码已实现或真实外部系统已完成对接。

## 1. 用例概述

| 项目 | 说明 |
| --- | --- |
| 编号 | UC-06，沿用原编号；旧图名为“校验业务访问权限” |
| 名称 | 检查员工指定操作权限 |
| 目标 | 判断员工在当前公司、调用方所属业务系统中是否拥有指定功能操作权限 |
| 主要参与者 | 已登记且通过服务身份认证的业务系统后端 |
| 触发 | 外部系统需要检查某名员工的一项操作权限 |
| 前置条件 | 调用方身份及系统绑定有效；业务系统自行认证员工，并提供稳定的员工统一标识 |
| 成功结果 | 有权限返回 hasPermission=true，无权限返回 false；结果不包含数据范围 |
| 后置条件 | 不修改角色、授权或外部业务数据，仅记录必要调用信息 |

UC-05 返回员工在当前系统的全部有效权限，UC-06 只检查指定的一项。二者可独立调用，不要求先查询全部权限再检查单项权限。本用例不经过 OA 审批。

### 管理范围与人员权限（V1.3 已确认）

完整规则见 [管理范围与人员权限规则](管理范围与人员权限规则.md)。总管理员指定公司、管理部门及系统，部门范围只包含指定部门，不跨部门或公司；同范围协作，不因同公司就共享整家公司权限。

公司级共享角色只由总管理员维护，权限管理员可为范围内合格员工申请分配；部门角色按明确归属维护。每次员工授权固定实际来源部门，不等同管理员的管理部门或角色归属。

离岗关闭原部门来源权限立即生效、不等待 OA；一般角色配置、分配及撤销仍经 OA。全局员工停用/恢复仅总管理员；恢复不自动复权。不设计公司/部门启停，普通员工不登录本平台。

## 2. 职责边界

| 权限中心负责 | 外部业务系统负责 |
| --- | --- |
| 定义调用参数、认证要求及返回格式 | 按接口约定接入，决定何时调用 |
| 验证调用身份及系统范围 | 登录认证员工，从自身登录上下文取得员工标识 |
| 计算指定操作的当前有效功能授权 | 确定业务功能对应哪个权限编码 |
| 返回是否拥有指定功能权限 | 在实际功能执行入口按结果拦截访问 |

权限中心不接收业务记录 ID、记录所属员工 ownerId 或数据过滤条件，不连接外部业务数据库。外部系统自身的业务规则不由本项目设计；本项目只演示功能访问检查。

接口返回“有编辑权限”表示拥有该编辑功能，不表示对某条具体业务记录作出了访问决定，也不携带或承诺任何业务数据范围。

### 系统进入权限（已确认）

本接口同时支持检查系统进入权限和功能操作。先认证调用方并验证绑定系统、员工状态及当前公司任职。目标为 SYSTEM_ACCESS 时，直接检查其有效授权来源，无需递归检查自己；有则返回 `hasPermission=true`，无则返回 `false`。

目标为 FUNCTION_OPERATION 时，必须先确认当前公司、当前系统有效进入授权；缺少时直接返回 `hasPermission=false`，即使角色仍配置着该功能操作。有进入资格且该操作存在有效授权来源时返回 true，否则 false。进入权限和功能操作可来自同公司、同系统的不同有效角色。

响应建议回显 permissionCode 和 permissionType，方便调用方识别目标权限。未知编码返回 hasPermission=false（类型可为 null）；认证错误与服务故障仍按错误响应处理，不能伪装成无权限或放行。

## 3. 输入与输出

| 输入 | 说明 |
| --- | --- |
| 服务调用凭据 | 识别已登记调用方并确定其绑定业务系统，不放在浏览器公开使用 |
| 当前公司标识 | 必填；调用方提供当前业务公司，权限中心验证公司有效及员工任职，不跨公司合并 |
| 员工统一标识 | 由受信业务后端取得，不按姓名或岗位名称猜测身份 |
| 权限编码 | 当前系统内唯一，可指定系统访问权限或功能操作权限 |
| 系统编码（若请求保留） | 必须与服务身份绑定的系统一致，不能靠改参数跨系统查询 |
| 请求编号 | 关联排错记录，不是授权凭据 |

建议使用 hasPermission 表达“拥有该操作权限”，避免 allow 被理解为已对具体业务记录放行。以下 JSON 只说明含义，接口地址、字段及错误码在 API 设计时最终确定：

```json
{
  "systemCode": "hr",
  "companyId": "COMP_BRIDGE",
  "employeeId": "EMP_DEMO_001",
  "permissionCode": "employee:edit",
  "requestId": "example-check-001"
}
```

有功能操作权限（已满足当前系统进入资格）：

```json
{"permissionCode": "employee:edit", "permissionType": "FUNCTION_OPERATION", "hasPermission": true, "requestId": "example-check-001"}
```

无权限：

```json
{"permissionCode": "employee:edit", "permissionType": "FUNCTION_OPERATION", "hasPermission": false, "requestId": "example-check-001"}
```

返回结果只对应本次被检查的功能操作。查看权限不能代替编辑权限；调用方不能用某一操作检查成功来放行其他操作。

直接检查系统进入权限的成功响应示例：

```json
{"permissionCode":"hr:access","permissionType":"SYSTEM_ACCESS","hasPermission":true,"requestId":"example-check-002"}
```

## 4. 核心规则

1. 只读取员工在当前公司、当前系统已生效且未失效的角色授权，并核对适用任职。其他系统同名权限不参与计算；跨公司兼岗时按当前公司分别查询，其他公司的角色不参与本次计算。
2. 按功能操作计算有效授权：至少一个有效角色提供该操作时有权限，无有效来源时无权限。相同操作的重复来源不产生额外权限，查看不自动包含编辑。
3. 员工停用、角色尚未生效、权限停用或关联撤销时，相应来源不产生有效权限；员工停用直接返回无权限。
4. 草稿、待审批和批准待执行的新增方案不能提前增加权限；撤销待审批本身不扣除权限。只读实际生效状态。
5. 不从岗位名称、角色显示名称或菜单是否显示推导操作授权；编辑不自动包含查看，菜单父子关系不等于权限继承。
6. 一期与 UC-05 共用有效授权及功能权限去重规则，不引入权限缓存。返回结果代表本次读取时的状态，不是永久访问凭证。
7. 系统进入权限是功能操作检查的必要前提；直接检查进入权限不递归检查自身，不因获得进入资格授予全部功能。

目录有效性与 UC-05 一致：按 [UC-01_维护业务系统与权限目录.md](UC-01_维护业务系统与权限目录.md) 的一期约定，功能或任一祖先目录停用时，该功能操作不参与授权计算。重新启用可能恢复仍有效的旧授权，但不恢复已撤销关联。

## 5. 正常流程

| 步骤 | 外部系统操作 | 权限中心处理 |
| --- | --- | --- |
| 1 | 携带服务凭据发送员工标识和操作编码 | 校验参数、服务身份及系统绑定 |
| 2 | 等待结果 | 检查员工状态及当前公司任职，查找当前系统目标权限及其有效性 |
| 3 | — | 先查系统进入资格：直接检查 SYSTEM_ACCESS 则返回其结果；检查功能时，无进入资格直接返回 false，否则再查目标操作来源 |
| 4 | — | 无有效来源时返回无权限；至少一个有效来源提供该操作时返回有权限 |
| 5 | — | 记录必要调用摘要并返回结果，认证失败或服务故障另行返回错误 |
| 6 | 接收结果 | 外部系统按功能检查结果执行访问拦截及自身业务校验；权限中心不继续处理业务记录 |

接口正常返回无权限与调用失败是不同结果。权限中心不使用超时、数据库异常等故障伪造正常的无权限响应，更不能故障默认放行。

## 6. 替代与异常流程

本稿采用以下接口行为约定，具体 HTTP 状态码留到 API 设计：

| 编号 | 条件 | 处理 |
| --- | --- | --- |
| E01 | 员工标识或操作编码缺失、格式错误 | 参数错误，不使用默认员工或默认权限 |
| E02 | 调用凭据无效、缺失 | 认证错误，不返回权限结果 |
| E03 | 请求跨出绑定系统，或绑定系统已停用 | 授权错误，不检查其他系统权限 |
| E04 | 员工不存在或停用 | 正常返回 hasPermission=false，不泄露额外人员资料 |
| E05 | 操作不存在、停用或无有效授权来源 | 正常返回无权限，不把未知编码当成无限制操作 |
| E06 | 多角色重复授予指定操作 | 合并为同一个有权限结果，不重复计算或扩张权限 |
| E07 | 必要权限数据损坏或数据库不可用 | 返回服务错误，不默认放行或假成功 |
| E08 | 查询期间发生授权变更 | 按一致读取的已提交状态返回；变更成功后发起的新检查反映新状态 |

外部系统应将接口错误视为本次检查未成功，不能据此执行受保护操作；此处只声明调用契约，不设计其内部故障处理框架。

## 7. 交互示例

员工甲已有 HR 系统进入资格及编辑员工信息功能。HR 后端询问“员工甲是否有编辑员工信息权限”，权限中心返回 hasPermission=true；没有该功能的员工乙检查同一操作时返回 false。接口不接收目标业务记录，也不判断记录属于谁。

如果甲有两个有效角色均提供编辑操作，撤销其中一个关联后仍返回 true；最后一个有效编辑来源撤销并执行成功后，新检查返回 false。

查看列表、导出等功能也按各自操作编码独立检查；接口不返回外部业务数据、行过滤规则或数据范围。

## 8. 数据与事务边界

读取员工、系统、员工角色关联、角色、角色权限及操作目录的有效状态。无需读取外部业务记录，不读取 OA 审批节点，不写授权关系。

复用 UC-05 的有效性过滤和功能权限去重，保证相同数据状态下，单项检查与全量查询对应操作一致。采用本地一致读取；接口不持有跨系统事务，也不承诺回滚已经开始或完成的外部操作。

调用日志记录请求编号、系统、必要员工标识、操作编码、功能检查结果和时间，不记录服务凭据及无关人员资料。具体日志失败策略在公共日志设计中统一，不引入新的审批流程。

## 9. 结构化功能分解

```text
检查员工指定操作权限
├── 校验请求参数与调用身份
├── 确定绑定系统、员工和目标操作
├── 判断系统进入资格（直接检查进入权限则返回结果）
├── 有进入资格后查询目标功能操作有效授权来源
├── 判定是否存在该操作的有效授权来源
└── 记录调用摘要并返回

外部业务系统：接收结果 → 执行功能访问检查及自身业务规则 → 放行或拦截
```

与 UC-05 共用查询和合并的内部处理模块即可，不要求拆为独立服务；两个用例没有必须先后调用的关系。

## 11. 后续衔接

- API 设计确定服务认证、参数、响应和错误码；外部系统按约定接入。
- UC-05 与 UC-06 共享有效功能授权规则；本项目不配置、返回或验收业务数据权限。
- 用例图与正文均使用“UC-06 检查员工指定操作权限”，已统一文字并保留手工布局。

### 本轮补充验收

| 场景 | 预期 |
| --- | --- |
| 当前公司缺失或公司不存在／未知 | 缺失／格式错误返回参数错误；未知公司返回无进入资格／无权限，不混合其他公司授权 |
| 员工没有当前公司有效任职 | 返回无进入资格／无权限 |
| 桥梁公司查看、水利公司编辑，员工兼岗 | 分别检查桥梁、水利，功能权限互不扩大 |

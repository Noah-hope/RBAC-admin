# UC-11 接收审批结果并执行权限变更

版本：V1.3，2026-10-16。状态：功能权限、部门管理范围及员工启停流程已按用户确认修订，可作为界面原型依据。

### 当前需求基线（2026-10-16，V1.3 平级部门与员工启停）

- 一期实现 RBAC0 权限管理：员工经角色获得权限，无角色继承、直接用户授权或显式拒绝。外部系统只做简单 HTTP 调用演示，不实现其内部业务。
- 角色属于一个公司和一个业务系统，可限定部门；公司级角色要求本公司有效任职，部门级角色要求在该部门有效任职，不适用于其他部门。岗位不自动绑定角色；任职条件与权限需要均未改变时，不因岗位名称变化更换角色。
- UC-05/06 按“员工＋当前公司＋业务系统”计算权限。仅合并该公司、该系统内的有效角色；系统进入资格与功能权限也必须来自该公司、该系统。公司上下文隔离的是功能授权来源，不定义业务数据访问范围。
- 授权同时校验角色适用条件与来源部门。离岗关闭原部门来源立即失效，其他独立兼岗来源保留；公司级共享角色不随调岗自动转移。仅总管理员可全局停用/恢复员工；恢复不复权。新授权经 OA，新管理任命由总管理员办理。
- 当前 RBAC 系统只管理功能权限。目录登记系统进入权限与功能操作，角色配置是否授予；不定义、保存或返回业务数据范围，不设计本人记录判断或行过滤规则。
- 员工、公司、部门使用稳定内部 ID；首次导入以源唯一用户名建立员工映射，组织分配稳定编码，更名不改变身份。人员变更模板明确新增任职、结束任职、停用、恢复等动作，不从文件缺行推断离职。
- 一期使用至少两个公司、两个系统的代表性数据，覆盖多角色、兼岗、公司授权隔离、功能操作独立与去重、审批生效、撤销、失效及重新申请。其余资料后续逐步补齐。

以上为本轮已确认规则，详细流程与验收必须遵循；描述的是需求设计，不代表代码已实现或真实外部系统已完成对接。

## 1. 用例概述

| 项目 | 说明 |
| --- | --- |
| 编号与名称 | UC-11 接收审批结果并执行权限变更，沿用原“执行已批准的权限变更”编号 |
| 目标 | 识别外部 OA 的最终结果，只对匹配且仍有效的已批准申请执行一次变更 |
| 主要参与者 | 外部 OA 系统；一期使用模拟 OA 调用方 |
| 触发 | OA 返回最终批准或驳回结果，或权限中心重试已批准但执行失败的申请 |
| 前置条件 | UC-02/03/04 已保存固定申请；结果调用方通过专用服务认证，申请和外部审批编号可关联 |
| 成功结果 | 驳回结果可靠记录；或批准申请的变更、执行状态及成功审计一致提交 |
| 失败保证 | 不执行未批准、内容不匹配或失效申请；业务执行失败整体回滚，不显示已生效 |

本用例不设计 OA 审批人、审批层级、会签或转交，也不实现审批页面。UC-01、UC-07、UC-09、UC-10 的直接管理操作不通过本用例。

### 管理范围与人员权限（V1.3 已确认）

完整规则见 [管理范围与人员权限规则](管理范围与人员权限规则.md)。总管理员指定公司、管理部门及系统，部门范围只包含指定部门，不跨部门或公司；同范围协作，不因同公司就共享整家公司权限。

公司级共享角色只由总管理员维护，权限管理员可为范围内合格员工申请分配；部门角色按明确归属维护。每次员工授权固定实际来源部门，不等同管理员的管理部门或角色归属。

离岗关闭原部门来源权限立即生效、不等待 OA；一般角色配置、分配及撤销仍经 OA。全局员工停用/恢复仅总管理员；恢复不自动复权。不设计公司/部门启停，普通员工不登录本平台。

## 2. 一期交互边界

```text
UC-02/03/04 固定申请内容
    ↓ 提交/关联外部审批申请
OA 完成审批（一期模拟）
    ↓ 返回批准或驳回结果
UC-11 认证与匹配 → 记录结果 → 复核条件 → 执行并审计
```

一期建议使用服务端回调接收最终结果；模拟调用方也使用专门的服务凭据，不能用普通权限管理员会话代替。真实 OA 协议、轮询或消息传输留到实际接入时适配，不要求一期实现多种通道。

提交侧保存固定申请、原范围依据和每条明细的来源部门/周期。页面单独展示 OA 待发送、发送失败、已关联；网络失败重试同一固定申请，不伪造批准或重复创建。UC-11 仅执行已保存方案。

结果确认与执行确认分开：OA 得到“结果已接收”不等于权限已生效，管理页面仍以权限中心的执行状态为准。

### 申请归属、资格来源与自动执行（已确认）

角色和已提交申请不归原申请人个人；角色按公司/部门归属，员工授权明细按来源公司/部门归属。同范围管理员可协作，不能因同公司就访问其他范围。原管理员离任不单独阻断已提交合法申请，目标员工来源关闭则按来源周期拒绝旧批准；保留原提交人与固定内容。

提交时固定资格依据：总管理员为全局资格，权限管理员为明确公司、指定部门及系统的范围记录和版本。UC-11 按原范围记录复核，不能换用当前查看人的更大资格；按申请类型检查对应目标条件：配置查角色归属及版本，授予查来源部门/任职/周期与角色关系版本，一般撤销查指定来源及关系版本，不机械要求当前授予资格。总管理员原申请仍明确实际来源部门，不受普通管理员系统清单限制。

收到可信最终批准后，权限中心自动尝试执行合法的固定方案，不等待任何管理员点击接手或再次确认；原申请人离任、公司暂时没有权限管理员均不单独阻止执行。短暂故障保留批准依据并由服务端重试，重试仍检查原资格来源对应的范围及目标条件；仅实际范围或目标条件不再合法时标记失效。员工角色分配仍须检查目标员工有效任职，撤销历史关联不要求目标员工仍在原岗位。

一期不提供人为取消已批准方案的入口，不以“失效”代替任意取消。合法方案执行或在短暂故障后重试；实际条件不再合法则失效并记录原因。执行成功后如需调整，按 UC-02～04 重新申请。未提交草稿的删除规则保持独立。

未提交草稿可由范围内管理员删除并记录删除事件，释放变更占用；新角色从未提交、从未生效且无引用时一并删除空草稿。已正式提交或已生效的角色/申请保留历史，不借删除绕过审批。正式角色配置提交后须至少包含一项权限（系统进入权限或功能操作均可），不产生已生效空角色；清理员工授权走 UC-04。


## 3. 输入与输出

| 输入 | 说明 |
| --- | --- |
| OA 服务凭据 | 验证结果来源；不从浏览器公开调用或手填审批号推断可信 |
| 本地申请编号、外部审批编号 | 定位固定申请并核对关联，不能让审批编号改绑其他申请 |
| 最终结果 | 一期支持批准、驳回；中间节点意见不作为执行依据 |
| 申请版本/内容摘要 | 核对返回结果批准的就是原固定内容，不取代服务认证 |
| 结果事件/请求编号 | 用于重复通知识别及排错 |
| 结果时间、意见摘要 | 用于追溯；不以通知时间较新就覆盖原结果 |

输出区分：结果已接收、已执行及原结果、执行失败可重试、申请失效、结果不合法。具体 JSON 字段和错误码在 API 设计确定，不用一个“成功”混淆接收和生效。

返回不含服务凭据、密码、完整人员资料或数据库堆栈。来源校验失败时不泄露申请详细内容。

## 4. 状态与最终结果规则

| 当前状态与事件 | 处理 |
| --- | --- |
| DRAFT 草稿收到审批结果 | 拒绝执行，草稿尚未正式提交 |
| PENDING 待审批收到可信驳回 | 记录最终结果，转 REJECTED，业务数据不变 |
| PENDING 收到可信批准 | 可靠记录结果，转 APPROVED 已批准待执行 |
| APPROVED 或可重试的 EXECUTION_FAILED | 服务端按原资格来源复核范围及目标条件后自动尝试执行，不要求管理员接手 |
| 原申请人离任或公司暂时没有权限管理员 | 不单独改变申请状态，不阻止合法批准方案自动执行；原申请人不能继续人工管理 |
| 管理员要求人为取消已批准方案或任意标记失效 | 一期不提供该操作；失效必须有实际范围、目标条件或版本不再合法的依据 |
| 执行事务成功 | 转 EXECUTED，业务变更与成功审计已提交 |
| 原资格来源对应的范围或目标条件不再合法、版本陈旧 | 转 INVALIDATED，不能靠重试强行执行；修正后新申请审批 |
| 已执行申请收到相同结果 | 返回原执行结果，不再次改数据 |
| 同一申请收到相互矛盾的最终结果 | 拒绝冲突结果并记录问题，不按最后到达时间覆盖 |

驳回后改内容应创建新申请，不把同一申请从驳回改为批准。已执行后的撤销或再次修改也须按 UC-02～04 新建方案，不能用迟到的“驳回”回滚已执行授权。

撤回 WITHDRAWN 为可选扩展，一期不要求接入；若将来启用，已撤回申请不能再执行旧批准。数据库短暂故障与业务条件失效分别处理，只有前者适合重试原批准内容。

## 5. 正常流程

| 步骤 | 外部系统/执行器 | 权限中心处理 |
| --- | --- | --- |
| 1 | OA 发送最终结果 | 验证服务身份和请求格式 |
| 2 | — | 查询申请，校验审批关联、固定版本/摘要及最终结果类型 |
| 3 | — | 判断重复或冲突；重复已成功结果返回原记录，冲突结果拒绝 |
| 4 | — | 独立事务可靠保存接收事件及批准/驳回状态；驳回到此结束 |
| 5 | 执行器处理批准申请 | 读取本地固定方案，核对提交时合法依据，按原资格来源复核对应范围及目标条件；不等待管理员接手 |
| 6 | — | 在受并发控制的本地事务中复核版本，按申请类型执行全部变更 |
| 7 | — | 同事务写入执行状态、目标版本与成功审计；全部成功才提交 |
| 8 | OA/管理页面获得结果 | 返回接收与执行状态；后续权限查询按实际已提交数据计算 |

一期可在接收结果后立即尝试执行，无需引入消息队列。批准状态单独落地，使进程在接收后中断时仍可恢复处理，而不是要求 OA 重新审批。

## 6. 三类变更的复核与执行

| 申请类型 | 执行前复核 | 实际写入 |
| --- | --- | --- |
| UC-02 创建角色并配置权限 | 原资格来源对应范围及组织/系统归属、角色基础版本、当前未结束方案、权限类型和有效性；明确移除停用权限不因其停用而阻止清理 | 替换该方案明确的角色权限配置、更新版本；首次配置成功激活角色 |
| UC-03 为员工分配角色 | 原公司/部门/系统范围依据、来源部门及适用任职、来源授权周期、角色版本及关系版本 | 新增批准的独立来源关系；不同部门同角色不覆盖 |
| UC-04 一般撤销员工角色 | 原管理范围、明确来源部门、准确关系 ID 和版本；已失效项不再办理 | 撤销批准的指定来源，保留其他来源与历史；离岗直接关权不经本执行器 |

一般撤销不因角色配置版本变化而失效，但目标关系或来源变化时不能误撤新授权。授予同时检查角色适用资格和来源周期；原部门关闭后，即使是公司级角色或员工后来返回，也不能执行旧批准。

系统进入权限 SYSTEM_ACCESS 随角色配置和分配一起执行，不单独绕过审批。功能操作校验存在、有效、类型及归属合法；所有权限均只记录是否授予。允许进入权限和功能来自当前公司、当前系统不同角色，也允许先分配只有功能权限的角色；缺进入资格时功能不可用，由 UC-05/06 计算，不在执行器中自动补授。

撤销最后一个进入来源只改变批准的关联/配置，不能顺带清空所有功能授权；重新获得进入资格后，未撤销且仍有效的配置可能恢复可用。

## 7. 重复、并发与失败恢复

- 同一申请只允许一次成功执行。结果接收防重和业务执行防重分别控制，不能只因为回调编号不同就再执行。
- 原始批准事件保留；执行尝试可多次，成功业务事件只记一次。相同事件编号带不同内容必须拒绝。
- 两个执行请求并发到达，通过申请执行状态和目标版本的事务锁/条件更新保证一致；具体数据库手段在设计时确定。
- 角色配置的单一未结束方案约束、授予/撤销的关系版本沿用 UC-02～04，防止旧授权复活或旧撤销误伤新授予。
- 整批方案任一项越权、版本失效或写入失败，不执行剩余子集；不能擅自缩小 OA 批准的清单。
- 已批准后写入失败，业务事务回滚；另行记录失败结果。数据库整体不可用时保持可恢复批准状态并记录服务端错误，不承诺审计表此时已保存失败事件。
- 重试只处理同一固定批准方案，按原资格来源复核管理范围、目标条件与版本，不允许重试时增删目标或改变功能权限集合。
- 进程中断时，以数据库中的批准和执行状态恢复：未提交业务事务则重试，已提交成功则返回历史结果。若外部仅因超时不知结果，可查询或重送同一结果，不再发起新授权。

一期由受控的服务端恢复机制处理重试，恢复后自动重试，具体服务端启动／扫描方式留到实现设计；人工触发只能作为辅助恢复方式；普通权限管理员不能通过“重试”将未批准方案变成批准。

## 8. 替代与异常流程

| 编号 | 条件 | 处理 |
| --- | --- | --- |
| E01 | 来源认证失败或仅手填审批号 | 拒绝接收，不执行 |
| E02 | 申请不存在、审批关联不符或内容摘要不一致 | 拒绝，不按回调内容新建授权 |
| E03 | 非最终结果、草稿或已失效申请 | 不执行；返回可披露的状态原因 |
| E04 | 合法驳回 | 保存驳回记录，原配置/授权不变 |
| E05 | 相同成功通知重复 | 返回历史成功结果，不重复变更 |
| E06 | 已批准后收到驳回、已驳回后收到批准 | 作为最终结果冲突处理，不自动反转 |
| E07 | 权限管理员原始申请的公司、部门及系统范围收缩或目标版本陈旧 | 失效重提；原申请人离任不单独阻止自动执行 |
| E08 | 执行/成功审计写入失败 | 整体回滚，记录失败或待恢复状态，不伪报已生效 |
| E09 | 撤销后重新授予，再收到旧撤销通知 | 识别历史执行或版本冲突，不撤新关联 |
| E10 | 任一批量明细条件不满足 | 整批不执行，不部分成功 |

## 9. 数据与结构化处理

读取 AuthorizationChange 及固定明细、申请版本/摘要、OA 关联、提交时固定资格来源及对应范围、目标角色/权限/关联与状态；写入结果接收事件、审批状态、执行结果、目标变更及 AuditLog。

事务边界分为两段：接收结果可靠落地；执行业务变更与成功审计原子提交。等待 OA 不持有事务，执行事务不调用外部 OA。接收成功、执行成功是不同字段/状态，不由前端自行推断。

```text
接收审批结果并执行权限变更
├── 认证 OA 调用并校验参数
├── 匹配固定申请、版本与审批关联
├── 检查重复/冲突并保存最终结果
├── 批准后按原资格来源复核范围与目标条件并自动执行
├── 按类型执行角色配置、授予或撤销
└── 原子保存执行结果及审计，失败保留恢复依据
```

复用 UC-02～04 的范围和版本规则，不因进入执行器而跳过授权边界；共享 UC-08 的事件含义，区分审批、执行失败与重试成功。

| 编号 | 场景 | 预期 |

| UC11-T01 | 合法角色配置批准结果 | 执行成功后配置生效，草稿角色首次激活 |
| UC11-T02 | 合法员工角色分配批准结果 | 只增加批准关联，其他角色保留 |
| UC11-T03 | 合法角色撤销批准结果 | 只撤指定关联，重合权限按剩余来源计算 |
| UC11-T04 | OA 驳回 | 记录驳回，业务数据不变 |
| UC11-T05 | 伪造凭据、申请编号或摘要不一致 | 拒绝，不按请求中的新内容授权 |
| UC11-T06 | 非最终审批意见或草稿收到通知 | 不执行 |
| UC11-T07 | 相同结果重复或并发到达 | 至多一次成功执行，返回原结果 |
| UC11-T08 | 同编号内容改变或最终结果冲突 | 拒绝冲突，不按最新到达覆盖 |
| UC11-T09 | 批准接收后进程中断 | 保留批准状态，恢复时校验后执行 |
| UC11-T10 | 业务或成功审计写入失败 | 整批回滚，不显示已生效，合法重试可恢复 |
| UC11-T11 | 原申请人离任或公司管理范围缩小 | 仅离任不影响自动执行；权限管理员原始申请因范围缩小而不合法时失效重提，总管理员原始申请不受权限管理员系统清单限制 |
| UC11-T12 | 角色配置改变后执行旧授予方案 | 版本校验拒绝，不授予未批准的新权限 |
| UC11-T13 | 系统停用但指定来源仍有效的一般撤销 | 合法且版本一致可执行；已失效历史只读，不再次提交 OA |
| UC11-T14 | 撤销后重授，再收到旧撤销回调 | 不误撤新关联 |
| UC11-T15 | 批量一项不满足条件 | 整批不执行，不自行截取明细 |
| UC11-T16 | 进入权限配置、撤销最后来源及重新授予 | 均按批准方案执行，保留无关功能关联；查询反映进入前提 |

## 11. 后续衔接

UC-01～11 已有详细说明。下一步统一检查术语、状态、管理范围和系统进入前提，再据此设计数据流图、结构化模块、数据库与 API。实际模拟凭据、重试策略和传输协议属于技术设计，不继续扩展 OA 业务范围。

本轮仅编写文档，不调用真实 OA、不修改授权数据库或后端代码。

| 编号 | 场景 | 预期 |

| UC11-U01 | 总管理员原始申请的系统不在权限管理员系统清单内 | 目标合法则执行，不套用权限管理员系统范围 |

| UC11-U04 | 固定批准方案的目标版本已陈旧 | 标记失效并记录客观原因，不执行、不允许强行重试 |

### 停用与任职失效后的旧审批

员工停用、任职条件丧失导致授权失效时，记录目标资格／授权的变化依据；即使恢复身份或重新任职，变化前的旧批准也不能重新产生权限，须由 UC-03 重新申请。目录或系统暂时停用不是员工停用：重新启用只允许尚有效的关联重新参与计算，已失效授权始终不恢复。

### 同批重新任职与迟到批准（2026-10-17澄清）

UC-10明确结束最后一项适用任职形成的来源周期推进，即使同批随后新增该部门任职也不倒退。UC-11不得仅凭批次最终已有适用任职执行离岗前旧授予批准；仍需新的周期匹配和新申请。其他适用兼岗始终存在或仅岗位更名时不误推进整个来源周期。

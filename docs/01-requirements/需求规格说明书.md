# RBAC 权限管理系统需求规格说明书

## 1. 引言与系统概述

### 1.1 系统目标

- 为多个业务系统统一管理功能权限，决定用户可以看到哪些菜单、使用哪些按钮、调用哪些后端接口。
- 为权限管理系统自身、课程管理系统及后续接入的其他业务系统提供统一账号、登录、退出和权限检查服务；各业务系统不另设独立密码。
- 同一用户在不同应用中的权限分别管理；权限先分配给业务角色，再将角色分配给用户。例如，“新增用户”和“删除用户”是两项不同的权限，可以分别授予。

### 1.2 系统边界

- **权限中心职责**：统一身份认证与令牌会话管理、组织部门树维护、应用与菜单/按钮/API 功能权限管理、业务角色与角色继承配置、管理员部门范围控制、权限申请与角色创建申请审批、关键操作审计记录，以及面向接入系统的统一身份与选人目录服务。
- **接入业务系统职责**：权限中心不管理业务数据的访问范围。课程成员、任课教师、小组成员等具体业务对象的访问规则由各业务系统自行判断；业务系统后端必须校验直接发送的 HTTP 请求，不能仅依靠前端隐藏菜单或按钮。

### 1.3 阶段演进范围对照（RBAC0 基线 vs RBAC1 扩展）

除下表明确标注调整或扩展的内容外，RBAC1 其余功能与业务规则均沿用 RBAC0 基线。

| 业务维度               | RBAC0 基线规则                                                     | RBAC1 扩展与调整                                                                                                                             |
| ---------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **角色模型**           | 扁平业务角色，无继承关系；一个角色可包含多个应用的权限             | 在业务角色上增加**多父、多层角色继承**（DAG）；禁止自继承和循环继承；`TOTAL_ADMIN` 与 `DEPARTMENT_ADMIN` 不参与继承                          |
| **权限计算与展示**     | 角色有效权限即其直接勾选的权限；用户有效权限为所分配角色权限的并集 | 角色有效权限为**直接权限与全部可达父角色权限的并集**；展示区分**直接、继承、同时存在**，并列出全部直接配置来源角色（不含仅传递的中间角色）   |
| **账号与权限编码**     | 登录使用用户名和密码；权限标识采用 `资源:操作` 格式                | 登录兼容**字符串账号及数值学号**；权限标识兼容课程系统的**大写字母数字短码**（如 `CV`）；前端权限检查不限编码格式                            |
| **角色编辑与删除**     | 仅校验角色自身菜单与按钮依赖；仅当业务角色未关联用户时允许删除     | 保存时**同事务校验直接权限与父角色列表**，校验**自身及全部直接/间接子角色**的按钮菜单依赖；删除前还须**解除双向继承关系**                    |
| **权限申请与审核**     | 仅按直接赋予角色的权限判断已拥有权限和候选角色无关权限             | 可申请目录、候选角色及全应用无关权限评估均**纳入继承权限**；父子继承或直接授权变更后，受影响用户的待审核申请已满足时转为“已满足”             |
| **角色创建申请**       | 填写角色名称、说明和直接权限                                       | 表单扩展支持**选择业务父角色**并预览实时有效权限；只存直接权限与父角色快照，审批实际创建时按父角色最新配置重算校验                           |
| **统一身份与目录接入** | 统一登录/退出、获取当前应用角色 ID 列表与权限                      | 新增**按应用映射角色码**（如 `teacher`、`student`、`admin`）；支持**课程系统逐层选部门、分页选人、查人目录**及已配置前端来源的 **CORS 预检** |

### 1.4 术语与定义

| 术语                        | 定义                                                                                                                        |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **业务应用（Application）** | 接入权限中心统一管理权限的系统单元。权限管理系统自身与课程管理系统均作为一个应用分别登记。                                  |
| **菜单权限 / 按钮权限**     | 归属于指定应用的树形功能权限节点。按钮必须归属同一应用下的某个菜单。                                                        |
| **权限标识**                | 由业务系统制定并在权限中心登记的应用内唯一编码。标准格式为 `资源:操作`，RBAC1 同时兼容课程系统大写字母数字短码（如 `CV`）。 |
| **`operationId`**           | 业务系统 API 文档中用于唯一标识接口操作的名称，例如 `createCourse`。                                                        |
| **业务角色**                | 管理员创建并用于承载多应用菜单、按钮权限的角色，可分配给用户；RBAC1 中仅业务角色之间可建立继承关系。                        |
| **预置管理角色**            | 系统预置的 `TOTAL_ADMIN`（总管理员）和 `DEPARTMENT_ADMIN`（部门管理员），不可删除，且不参与 RBAC1 业务角色继承。            |
| **直接权限**                | 直接勾选配置在某个业务角色上的菜单或按钮权限。                                                                              |
| **继承权限**                | `[RBAC1]` 子角色通过一条或多条继承路径从可达父角色获得的权限。                                                              |
| **有效权限**                | 角色或用户实际生效的权限集合。在 RBAC1 中等于直接权限与全部可达父角色有效权限去重后的并集。                                 |
| **配置来源角色**            | `[RBAC1]` 直接勾选了该项权限的角色。仅负责传递继承权限的中间角色不作为配置来源。                                            |
| **应用角色码映射**          | `[RBAC1]` 部署方在启用映射的应用下为指定业务角色 ID 配置的应用侧身份编码（如 `teacher`、`student`、`admin`）。              |
| **有向无环图（DAG）**       | `[RBAC1]` 支持多父、多层继承但不存在有向环路的角色继承图结构，确保权限传递方向清晰且可终止。                                |

## 2. 参与者与管理范围

### 2.1 参与者职责总览

| 参与者           | 身份说明                                       | 核心可执行的业务行为                                                                                                                                                                                                                             |
| ---------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **普通用户**     | 正常启用状态的业务用户（停用后无任何操作资格） | 统一登录与退出；在「我的权限」查看自己拥有的角色及按应用汇总的权限；发起权限申请与撤回待审核申请；使用已获授权的菜单、按钮及接入应用功能。                                                                                                       |
| **部门管理员**   | 被总管理员分配 `DEPARTMENT_ADMIN` 角色的用户   | 查看本部门及下级部门结构；维护管理范围内的用户（查询、新增、修改、停用）；为管理范围内用户单独或批量分配/撤销已有业务角色；审核管理范围内员工的权限申请；提交角色创建申请；查看操作发生时属于管理范围内用户的管理操作记录。                      |
| **总管理员**     | 系统预置 `TOTAL_ADMIN` 账号                    | 负责系统首次配置和全局管理：维护公司/分公司/部门上下级关系与员工跨部门调动；任免部门管理员；维护业务应用、权限及 API 登记与关联；创建、修改和删除业务角色（含配置 RBAC1 角色继承）；审核全部权限申请与全部角色创建申请；查看全部及全局操作记录。 |
| **接入业务系统** | 权限管理系统自身、课程管理系统等应用系统       | 委托权限中心完成登录与单点退出；查询当前用户在目标应用中的身份、角色（或映射角色码）和菜单/按钮权限；在执行受保护操作前调用权限中心检查 API 或权限标识；按权限中心目录接口读取部门与选人信息（RBAC1）。                                          |

### 2.2 管理员职责与范围规则

1. **角色赋权原则**：管理员也是系统用户，通过拥有管理角色获得管理权限；系统预置一个总管理员账号，负责首次配置和全局管理。
2. **管理范围确定**：总管理员可以给用户分配「部门管理员」角色；系统根据该用户当前所属部门确定其管理范围，覆盖**本部门及全部下级部门**。
3. **跨部门权限隔离**：部门管理员只能在管理范围内维护用户、分配或撤销已有业务角色、审核权限申请，没有创建或修改角色的权限。
4. **职责边界**：部门范围仅用于限制管理员可以管理哪些用户，不决定业务数据的访问范围。

## 3. 功能需求规格说明

### 3.1 统一身份认证与外部系统接入（FR-01）

#### 3.1.1 统一登录、身份查询与退出 `[RBAC0 基线]`

- **FR-01.1 统一账号体系**：权限管理系统、课程管理系统及后续接入的其他业务系统，统一使用权限中心维护的账号和登录、退出服务；各业务系统不另设独立密码。
- **FR-01.2 统一登录与多形态账号兼容**：用户使用同一账号和密码登录接入系统时，由权限中心验证身份并返回登录令牌；各系统根据有效的登录令牌识别当前用户。`[RBAC1 扩展]` 登录同时接受字符串账号及数值学号。
- **FR-01.3 身份与权限查询**：登录后，接入系统可以查询当前用户信息、角色和当前应用中的菜单、按钮权限；权限中心的「我的权限」页面按应用汇总展示用户拥有的有效权限。
- **FR-01.4 单点退出**：用户可以从任一接入系统发起退出；权限中心使本次登录令牌失效，使用该令牌的各接入系统不能继续访问受保护接口。

#### 3.1.2 接入应用角色码映射 `[RBAC1 扩展]`

- **FR-01.5 角色码映射规则**：接入应用可以启用角色码映射。每条映射绑定目标应用、业务角色 ID 和应用识别的角色码；同一个角色码可以在不同应用中独立使用。
- **FR-01.6 身份查询映射计算**：查询当前身份时，系统从直接分配的业务角色和全部可达父角色中查找目标应用的映射；无论该角色是否配置了应用权限均可映射（如零权限角色也可获得身份）。返回的角色码去重，无匹配时返回空列表。
- **FR-01.7 映射稳定性与未启用兼容**：角色码映射关联业务角色 ID，角色改名不影响映射。未启用映射的应用沿用角色 ID 字符串响应；各应用的权限及 API 授权继续按目标应用独立检查，跨应用权限相互隔离。

#### 3.1.3 课程管理系统统一身份与选人目录接入 `[RBAC1 扩展]`

- **FR-01.8 课程角色身份与权限协同**：将课程业务角色映射为 `teacher`、`student`、`admin`。课程系统的教师入口要求 `teacher`，学生入口要求 `student`；具体课程管理操作还须具备对应权限码。
- **FR-01.9 组织与人员目录查询**：已授权的课程系统用户可逐层浏览部门，按姓名、工号或学号分页查询指定部门内的启用用户，再按统一身份 ID 读取选中人员的信息。目录查询按目标应用登记的 API 和调用人有效权限判断，未授权访问返回 `403`。
- **FR-01.10 目录身份标识一致**：目录返回的用户 ID 与登录令牌（JWT）的 `sub` 一致，登录账号作为工号或学号。
- **FR-01.11 浏览器跨域预检**：课程系统浏览器可从已配置的前端来源地址直接调用权限中心；浏览器 CORS 预检请求无需登录，实际请求仍按接口规则校验会话与授权。

---

### 3.2 组织部门与用户管理（FR-02） `[RBAC0 基线，RBAC1 沿用]`

- **FR-02.1 部门结构维护**：总管理员维护公司、分公司和部门的上下级关系（查看、新增部门、修改名称或调整上级部门）；部门管理员可查看管理范围内的部门结构。
- **FR-02.2 用户维护与停用阻断**：管理员可以查询、新增、修改和停用管理范围内的用户；新增用户时必须选择所属部门。用户停用后，不能登录、不能使用任何受保护功能、也不能申请权限。
- **FR-02.3 员工跨部门调动**：员工跨部门调动由总管理员负责。调动后，员工保留原有的业务角色；调入部门的管理员随后可按需为其分配或撤销角色。
- **FR-02.4 部门管理员任免**：总管理员可在用户维护时赋予或取消用户的「部门管理员」角色；管理范围随用户所属部门及下级部门自动确定。

---

### 3.3 业务应用、权限与 API 管理（FR-03）

- **FR-03.1 应用登记与管理 `[RBAC0 基线]`**：总管理员可以查看、新增和修改业务应用。权限管理系统自身也作为一个应用进行管理，其菜单、按钮和管理 API 在本系统中统一配置；后续接入的业务系统按应用分别登记权限和 API。
- **FR-03.2 菜单与按钮权限维护 `[RBAC0 基线]`**：选择一个应用后，总管理员可以查看、新增和修改该应用的菜单和按钮权限。新增按钮时，必须选择它所属的菜单。新权限保存后立即出现在该应用的角色配置树中，总管理员可以勾选并授予角色。
- **FR-03.3 权限标识命名与唯一性**：权限标识由业务系统制定并提供，总管理员在对应应用下登记，权限中心不自动生成权限标识。同一应用内权限标识必须唯一。
  - `[RBAC0 基线]` 权限标识格式为 `资源:操作`。
  - `[RBAC1 扩展]` 权限登记兼容课程系统的大写字母数字短码（如 `CV`）。
- **FR-03.4 API 登记与关联管理 `[RBAC0 基线]`**：
  - 总管理员在权限配置中查看、新增、修改和移除关联的 API；登记时填写业务系统 API 文档提供的 `operationId`、请求方法和请求路径。权限中心保存并校验这些信息，不生成业务接口代码。
  - 一项菜单或按钮权限可以关联多个 API，一个 API 也可以关联多个菜单或按钮权限；权限与 API 通过关联表建立多对多关系，二者必须属于同一应用。
  - 同一应用内，`operationId` 必须唯一，“请求方法 + 请求路径”的组合也必须唯一。
  - 角色配置仍然只勾选菜单和按钮权限，不单独勾选 API；用户通过角色获得菜单或按钮权限后，即获得调用该权限关联 API 的资格。

### 3.4 角色管理与角色继承（FR-04）

#### 3.4.1 角色创建与跨应用配置 `[RBAC0 基线]`

- **FR-04.1 业务角色配置**：总管理员可以创建和修改业务角色。配置角色时，在同一个界面切换选择业务应用，在一棵权限树中勾选菜单和按钮并一并保存；一个角色可以包含多个应用的权限。

#### 3.4.2 角色继承规则 `[RBAC1 扩展]`

- **FR-04.2 多父与多层继承（DAG）**：子角色继承父角色的全部有效权限；支持多继承和多层继承，继承关系必须构成有向无环图（DAG），严禁自继承和循环继承。
- **FR-04.3 继承对象限制**：`TOTAL_ADMIN` 和 `DEPARTMENT_ADMIN` 不参与业务角色继承，角色继承只发生在业务角色之间。
- **FR-04.4 跨应用继承传递**：角色不绑定单一应用；子角色对父角色的继承将包含父角色在所有应用中的有效权限。

#### 3.4.3 有效权限计算与来源展示 `[RBAC1 扩展]`

- **FR-04.5 并集计算**：角色有效权限为其直接权限与所有可达父角色权限的并集；用户有效权限为其所有业务角色有效权限的并集；重复权限只计算一次。
- **FR-04.6 权限来源展示规范**：角色权限页面展示权限名称、获得方式（**直接配置**、**继承**、**直接与继承同时存在**）和配置来源角色；同一权限本身只显示一行。
- **FR-04.7 源角色去重与中间节点过滤**：配置来源角色仅指直接勾选该权限的角色；仅传递继承权限的中间角色不作为配置来源。同一权限有多个配置来源时，列出全部来源角色；多条继承路径指向同一配置来源时，该来源只显示一次。
- **FR-04.8 来源冗余保护**：权限或继承关系保存成功后，下一次权限检查立即反映变更。移除一个权限来源时，若该权限仍有其他直接或继承来源提供，则继续有效。

#### 3.4.4 继承编辑保存与级联校验 `[RBAC1 扩展]`

- **FR-04.9 联合配置与原子提交**：创建和编辑角色时，一并配置“角色直接权限”和“当前角色继承的父角色列表”。修改时提交最终继承角色列表，系统据此新增、保留或解除继承关系；直接权限和继承关系须一起校验并在同一事务中保存，形成循环或校验失败时整次操作失败，原配置不变。
- **FR-04.10 继承权限只读与防重复勾选**：仅通过继承获得的权限在界面显示为只读，不能勾选为新的直接权限，也不能在当前角色中取消继承权限。新增直接权限时按本次选择的父角色计算继承权限，已继承的权限不允许新增重复的直接配置，后端保存时执行同一规则。
- **FR-04.11 历史重叠保留与取消规则**：已有直接权限后来因父角色权限变化或继承关系调整而与继承权限重叠时，保留原有直接配置不自动删除，并同时展示两种获得方式和全部配置来源。对同时具有直接和继承来源的权限，允许取消当前角色的直接配置；只要继承来源仍存在，该权限继续有效。
- **FR-04.12 后代菜单依赖级联校验**：修改角色权限或继承关系时，系统校验当前角色及**全部直接、间接子角色**的最终有效权限。若修改后某个角色仍拥有按钮却失去所属菜单，且无其他权限来源能提供该菜单，拒绝整次保存并提示受影响的角色、按钮和菜单，保留原配置；其他来源仍能提供该菜单时，允许修改。

#### 3.4.5 业务角色删除

- **FR-04.13 预置角色保护 `[RBAC0 基线]`**：`TOTAL_ADMIN` 和 `DEPARTMENT_ADMIN` 等预置管理角色禁止删除。
- **FR-04.14 用户关联禁删 `[RBAC0 基线]`**：总管理员仅可删除未关联用户的业务角色；角色仍关联用户（含停用账号的关联）时禁止删除，并提示关联人数，须先撤销用户关联后再删除。
- **FR-04.15 继承关系禁删 `[RBAC1 扩展]`**：当前角色仍继承其他角色，或仍被其他角色继承时，拒绝删除，并提示先解除继承关系。
- **FR-04.16 删除清理与留痕 `[RBAC0 基线]`**：删除业务角色时一并清理角色权限关联，保留用户、权限本身和历史操作日志，并记录本次删除操作。

### 3.5 用户角色分配与撤销（FR-05） `[RBAC0 基线，RBAC1 沿用]`

- **FR-05.1 单用户角色维护**：管理员可以为管理范围内的用户分配或撤销已有的业务角色，保存成功后直接生效。
- **FR-05.2 批量角色维护**：批量操作时，管理员勾选多名管理范围内的用户，选择要分配或撤销的角色；用户原有的其他角色保留。
- **FR-05.3 多角色权限合并**：一个用户可以拥有多个业务角色，同时拥有这些角色的有效权限，重复权限只算一次；撤销某个角色后，用户通过其他角色获得的权限仍然保留。

### 3.6 前后端权限检查（FR-06）

- **FR-06.1 前端展示与权限标识检查**：
  - `[RBAC0 基线]` 前端保留本应用的菜单和按钮，根据当前用户的有效权限控制能否使用（无权限的展示与申请入口按 FR-07.2 执行）；需要时可单独查询当前用户是否拥有某项菜单或按钮权限。
  - `[RBAC1 扩展]` 前端按编码检查权限时不限编码格式，未登记的编码返回不具备。
- **FR-06.2 业务系统接口权限检查流程 `[RBAC0 基线，RBAC1 纳入继承权限]`**：
  1. 用户发起受保护的操作时，业务系统后端验证当前登录身份，并根据实际请求确定业务系统提供的 `operationId`。执行操作前，使用当前用户的登录令牌、目标应用和 `operationId` 向权限中心检查权限；用户身份由登录令牌确定，不得由前端任意指定用户 ID。
  2. 权限中心识别当前用户和目标应用，查找该应用中该 API 关联的权限。用户通过有效角色（含 RBAC1 继承权限）拥有其中**任意一项**权限，即通过该 API 的功能权限检查；管理员职责、部门范围和业务对象访问规则仍需满足。
  3. 登录令牌无效、用户停用、用户不存在、API 未登记或用户未获授权时，拒绝操作。业务系统收到允许结果后才执行操作；收到拒绝结果或无法完成检查时，不执行操作并提示用户。
- **FR-06.3 权限中心自举检查 `[RBAC0 基线]`**：权限管理系统自身受保护的管理接口也使用同一套身份认证、API 权限检查与管理员部门范围规则；按 API 检查时，接口所需权限由已登记的关联关系确定。
- **FR-06.4 变更实时生效 `[RBAC0 基线，RBAC1 涵盖继承变更]`**：角色、权限、继承关系或 API 关联修改保存后，下一次权限检查立即反映修改结果；移除 API 登记后，针对该接口的检查返回拒绝。

### 3.7 权限申请与审核（FR-07）

- **FR-07.1 申请资格与理由 `[RBAC0 基线]`**：正常状态的用户可以申请业务菜单或功能按钮，提交申请时须填写申请理由；停用用户不能申请权限。
- **FR-07.2 无权限前端交互引导 `[RBAC0 基线]`**：
  - 无权限的菜单继续显示；用户点击后，系统显示“暂时无法访问”页面并提供申请入口，不展示受保护的业务数据。
  - 无权限的功能按钮继续显示；用户点击后，系统提示没有权限并提供申请入口。
- **FR-07.3 可申请目录规则 `[RBAC0 基线 + RBAC1 扩展]`**：申请目录按应用区分菜单和按钮，只列出用户尚未获得的有效权限（在 RBAC1 中，直接或继承获得的权限均视为已拥有，不再列出；已拥有权限在「我的权限」查看）。尚未获得菜单时只展示该菜单；获得菜单后（含通过继承获得菜单），才展示其下尚未获得的按钮。
- **FR-07.4 审核权限范围 `[RBAC0 基线]`**：部门管理员只能审核自己管理范围内员工的申请；总管理员可以审核全部申请。
- **FR-07.5 最小权限候选角色评估与授权 `[RBAC0 基线 + RBAC1 扩展]`**：
  - 申请不直接授予单项权限；审批通过后，管理员选择包含所申请权限的现有业务角色，仅通过建立用户与该业务角色的关联授予权限（RBAC1 中继承权限由角色关系动态计算）。
  - 管理员审核时可以查看候选角色的全部有效权限（RBAC1 展示直接权限、继承权限及实际配置来源），并按候选角色在**所有应用**中的有效权限统一评估：候选角色应包含申请权限，且不得附带超出“申请人已有有效权限、本次申请权限及必要所属菜单”的无关权限。
  - 审批提交时按最新授权重新计算并校验候选角色；现有角色包含无关权限时，不能直接使用该角色，应先拆分或新建最小权限角色。
- **FR-07.6 权限申请状态与流转规则**：

| 状态       | 触发条件与约束规则                                                                                                                                 |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **待审核** | 用户提交权限申请后的初始状态；等待具备管理范围的管理员审核。                                                                                       |
| **已通过** | 管理员选择符合最小权限校验的候选业务角色批准通过；授予的权限不设置有效期。                                                                         |
| **已拒绝** | 管理员拒绝申请；被拒绝的申请不会因后续创建角色或授权变更而恢复。                                                                                   |
| **已满足** | 待审核期间，当用户关联角色、角色直接权限或角色继承关系变化后，受影响用户的待审核申请若已获得所申请权限，则自动转为“已满足”；其他历史状态保持不变。 |
| **已撤回** | 申请人在申请处于“待审核”状态时主动撤回，状态变为“已撤回”。                                                                                         |

### 3.8 角色创建申请与审批（FR-08）

- **FR-08.1 发起主体与触发场景 `[RBAC0 基线]`**：部门管理员没有创建或修改角色的权限；当现有业务角色无法满足员工权限需求时，部门管理员可以提交角色创建申请。提交申请不会创建角色，也不会改变用户权限。
- **FR-08.2 申请表单与预览规则 `[RBAC0 基线 + RBAC1 扩展]`**：
  - 角色创建申请复用总管理员创建角色的编辑界面。
  - `[RBAC0 基线]` 申请内容包括角色名称、角色说明和直接权限。
  - `[RBAC1 扩展]` 表单扩展支持选择父角色（父角色只能是业务角色），界面展示合并后的有效权限和实际配置来源（继承权限只读；重复直接配置及按钮菜单依赖按新建角色规则校验）。申请只保存直接权限和父角色选择（含父角色快照），不保存继承权限副本；展示和审核时根据父角色当前配置实时计算有效权限。
- **FR-08.3 受理、调整与事务提交 `[RBAC0 基线 + RBAC1 扩展]`**：
  - 总管理员可以拒绝申请，或受理申请并进入角色编辑界面；进入编辑界面后，申请仍保持“待审核”。
  - 总管理员可以调整角色名称、说明、直接权限和父角色；实际创建角色时，按父角色最新配置重新计算并执行与正常创建角色相同的校验规则。
  - `[RBAC1 扩展]` 角色、直接权限关联、继承关系、审批结果和成功操作记录在同一事务中保存；取消编辑、创建失败或未完成角色创建时，申请保持“待审核”。
- **FR-08.4 不自动授权规则 `[RBAC0 基线]`**：角色成功创建并使申请转为“已通过”后，不自动授予员工该角色；员工需要重新发起权限申请，或由管理员按正常流程分配角色。
- **FR-08.5 角色创建申请状态流转**：

| 状态       | 触发条件与流转规则                                                                               |
| ---------- | ------------------------------------------------------------------------------------------------ |
| **待审核** | 部门管理员提交申请后的初始状态；总管理员受理进入编辑界面、取消编辑或创建校验失败时均保持该状态。 |
| **已通过** | 总管理员完成配置并成功创建角色后状态转为“已通过”。                                               |
| **已拒绝** | 总管理员拒绝该角色创建申请后转为“已拒绝”。                                                       |

### 3.9 操作审计记录（FR-09） `[RBAC0 基线，RBAC1 沿用并覆盖继承配置]`

- **FR-09.1 记录范围与内容要素**：系统记录应用登记、权限配置、API 登记与关联修改、角色与继承关系配置、角色删除、角色分配与撤销、账号停用、员工跨部门调动、权限申请与角色创建申请处理等重要操作；每条记录包含**操作人、时间、操作对象、操作内容和结果**。
- **FR-09.2 不记录与区分边界**：系统不记录打开页面、浏览菜单或未保存的编辑行为。通过用户角色管理解除用户与角色关联时，记录为“解除用户角色关联”，不记录为撤销权限申请。
- **FR-09.3 查看范围控制**：
  - **总管理员**：可查看全部操作记录；应用登记、API 配置、角色权限与继承配置、员工跨部门调动，以及权限申请和角色创建申请处理等全局操作记录仅由总管理员查看。
  - **部门管理员**：可查看本部门及下级部门用户的管理记录（例如分配角色、撤销角色和停用账号）。查看范围按**操作发生时被操作用户的所属部门**判断；一次操作涉及多名用户时，部门管理员只看到管理范围内的用户。

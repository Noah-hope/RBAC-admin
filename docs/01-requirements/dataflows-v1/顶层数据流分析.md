# 集中权限管理系统：顶层数据流分析

2026-10-15。依据当前 [用例说明](../usecases-v1/用例说明.md) 与 UC-01～11 详细用例。本文仅整理已确认的系统边界与数据交换，不新增业务规则，不确定数据库字段或接口协议。

## 1. 顶层的含义

本次“顶层数据流图”采用**系统上下文图**的粒度：过程 0 表示整个集中权限管理系统，外部实体表示数据来源或接收方，箭头表示有名称的数据流。

不展开数据库、内部文件存储、Controller／Service 或各功能模块，不画执行先后、决策分支和审批内部步骤。不同教材对“0 层／顶层”的命名可能不同，交付图明确标为“顶层（系统上下文）”；后续第一层才把过程 0 分解为多个处理过程及逻辑数据存储。

## 2. 五类外部实体

| 外部实体 | 与权限中心的关系 | 范围说明 |
| --- | --- | --- |
| 权限中心总管理员 | 提交维护、配置、查询及账号管理请求，接收管理结果 | 所有公司、所有系统及权限管理员；UC-02 配置、UC-03 分配、UC-04 一般撤销需 OA；离岗关权直接办理 |
| 权限管理员 | 提交角色配置、分配、撤销及范围内查询，接收办理结果 | 当前有效任命对应的公司及获准系统，同一指定部门/系统范围内协作 |
| HR 系统／人员组织数据来源 | 提供组织、岗位、员工、任职及明确变更数据 | 一期使用文件或模拟来源，由总管理员上传、映射、确认，不表示已实现实时 HR 接口 |
| OA 系统 | 接收固定变更申请，提供审批关联和最终结果，接收结果处理反馈 | 不设计 OA 内部审批人员、页面或流程；一期模拟结果交互 |
| 业务系统后端 | 提交可信权限查询／单项校验请求，接收权限结果 | 自行认证员工，按当前公司与系统查询；实际功能访问拦截由调用方实施 |

总公司与各分公司是被管理的组织数据，不各自画成新的系统外部实体。普通员工也是被管理对象：其身份由业务系统认证，不要求直接登录权限中心，因此不另画“员工 → 权限中心”数据流。

HR、OA 可以同时也是权限目录中的被接入应用。本图中的 HR、OA 分别代表“人员数据提供方”和“外部审批方”的交互职责；它们若查询自身员工权限，采用业务系统后端的 F09／F10，不混淆这些职责。

## 3. 十条边界数据流

图中将同一方向、同一外部实体的相关数据归组以保持顶层可读性。归组不代表它们是同一个 HTTP 请求，也不代表必须一次返回全部数据。

| 编号 | 方向 | 数据内容 | 关联用例 |
| --- | --- | --- | --- |
| F01 | 总管理员 → 权限中心 | 登录凭据或现有会话；目录维护内容；角色配置、员工分配／撤销方案及原因；权限管理员任命和系统范围；后台账号创建／重置与本人账号请求；导入指令、映射及确认；查询条件 | UC-01～04、07～10 |
| F02 | 权限中心 → 总管理员 | 登录及会话处理结果、身份和全局管理范围；可读目录／角色／人员配置；预览差异和实际申请／执行状态；账号办理结果；导入报告；审计列表与详情；相应错误信息 | UC-01～04、07～10 |
| F03 | 权限管理员 → 权限中心 | 登录凭据或现有会话；本公司获准系统内的角色配置、分配／撤销方案及原因；范围内查询条件；本人改密、退出请求 | UC-02～04、08、09 |
| F04 | 权限中心 → 权限管理员 | 登录及会话结果、当前公司管理范围；范围内可读配置、预览差异、实际申请／执行状态；审计记录；本人账号办理结果及相应错误信息 | UC-02～04、08、09 |
| F05 | HR 数据来源 → 权限中心 | 组织、岗位、员工及任职资料；稳定来源标识；明确新增任职、结束任职、停用、恢复等变更数据 | UC-10 |
| F06 | 权限中心 → OA | 已保存的固定角色配置／员工分配／员工撤销方案；本地申请编号、版本／摘要及必要关联信息 | UC-02～04、11 |
| F07 | OA → 权限中心 | 提交申请后取得的外部审批关联信息；带可信服务身份的最终批准／驳回结果及关联申请、版本／摘要、结果事件信息 | UC-02～04、11 |
| F08 | 权限中心 → OA | 结果接收／处理状态，区分接收成功、重复返回、拒绝、已执行、执行失败／待恢复或申请失效等实际状态 | UC-11 |
| F09 | 业务系统 → 权限中心 | 调用服务身份、可信员工标识、当前公司与目标系统；单项校验另含指定权限编码 | UC-05、06 |
| F10 | 权限中心 → 业务系统 | 查询结果：系统进入资格、可见菜单、允许功能操作集合；或单项功能校验结果；调用错误／服务错误信息 | UC-05、06 |

F01／F03 的“身份”不表示浏览器自报的管理员角色可以成为授权依据，权限中心必须校验会话及最新管理资格。F09 的服务身份需与调用系统绑定，员工标识来自业务系统的可信登录上下文。

## 4. 需要保持清楚的边界

### HR 文件与管理员操作不是两次人员导入

F05 表示人员资料的逻辑来源；一期由总管理员上传 HR 文件，把文件送入权限中心。F01 中的导入指令、映射与确认表示管理员对此批资料的办理输入。它们是同一导入场景中的不同数据，不要求另建一条实时 HR 网络接口，也不重复导入一批员工。

预检问题与正式执行报告返回发起导入的总管理员，归入 F02；当前用例没有要求向 HR 自动回写授权或推送人员处理报告，所以不凭空添加“权限中心 → HR”数据流。

### OA 批准不是权限立即生效

F06 提交固定方案时不改变有效授权。F07 的可信最终批准需先可靠记录，再由权限中心自动复核、执行；成功提交后权限才改变。F08 的“结果已接收”不能解读为“权限已生效”；管理员通过 F02／F04 查看实际状态。故障恢复重试属于内部处理，不增加外部人工再次确认的数据流。

F07 的审批关联信息与最终审批结果可能在不同时间、不同交互中取得，顶层合并表达不表示它们必须同时交付。

### 权限结果不包含外部业务记录

F10 只说明当前员工在当前公司、当前系统可进入什么、可执行哪些功能。权限中心不接收报销单、合同等业务对象或过滤条件，不设计业务数据权限。业务系统按结果执行功能访问拦截及自身业务校验。

没有有效授权是正常拒绝或空权限集合；身份／参数错误与数据库等服务故障是不同结果，不能用正常 `false` 或空集合掩盖故障。无进入资格时，查询返回不可进入及空菜单／操作；仅有进入资格时可以进入，但菜单／操作仍可为空。

## 5. 下一层分解的约束

第一层数据流图需要继续容纳 F01～F10 的边界内容，可把组合数据流拆细，但不能无依据增加外部交互或遗漏已有输入输出。第一层再识别人员组织、权限目录、角色配置、员工授权、后台身份及管理范围、变更申请、审计等逻辑数据存储；这些不是已经定稿的数据库表。

可先将“后台身份及管理范围、目录维护、人员组织导入、角色／员工授权申请、审批结果及执行、权限查询校验、审计查询”作为待分析处理职责，再结合数据流确定分解，而不是把每个用例或每张表机械画成一个处理过程。最终结构化模块划分还需后续设计，不由本张上下文图直接确定。

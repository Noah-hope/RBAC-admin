# 数据库设计交接（逻辑约束）

当前Git契约为1.2.0，数据库草案1.1；正式跨阶段修订见[CONSISTENCY-REVIEW.md](../04-database/CONSISTENCY-REVIEW.md)。补充：配置保留停用项合法、完整任职依据不按目标上限裁剪、来源关闭响应按当前可见范围投影、删除草稿后以内部固定范围事实复核当前授权再幂等重放。具体物理设计归数据库目录，下述逻辑边界继续适用。
本阶段只确定 API 需要持久化的事实、唯一性、历史、版本和事务边界。后续采用 MySQL + Spring Data JPA；不在此确定物理表、字段类型、主键算法、ER 图、索引 DDL 或锁实现。不得据路由一一生成表。

## 持久化与唯一性

| 逻辑对象 | 必须保存的事实与约束 |
| --- | --- |
| 员工及来源标识 | employeeId 稳定；平台统一employeeKey全局唯一，另保留sourceSystem＋源标识唯一映射；来源不同不允许静默建立同统一键的另一个员工；明确旧新用户名映射依据，姓名不是主键，不复制真实人事信息到契约 |
| 公司/部门/岗位/任职 | 稳定 ID/code；部门属于一公司且平级，无部门parent/state；岗位按明确部门识别；任职可兼岗、保存结束历史；公司code全局唯一、部门code公司内唯一、岗位code部门内唯一 |
| 系统/目录/权限 | 系统code全局唯一；目录code和权限code分别在系统内唯一；一系统唯一SYSTEM_ACCESS；操作关联同系统FUNCTION，目录无环、父级同系统，启用FUNCTION绑定本功能合法查看/进入操作；操作名称在同一功能内不可重复 |
| 角色/当前配置 | role code全局唯一且生成不可并发重复；角色固定一公司/可选部门/一系统；有效配置非空、集合去重；metadataVersion和configurationVersion分开；无角色停用字段 |
| 授权来源 | 员工＋来源公司＋部门＋系统的周期依据，尚无有效关联也须可推进；失去全部适用任职、关权、全局停用后旧周期不可复用 |
| 独立授权关系 | 员工＋角色＋来源公司＋部门在同一时期最多一个ACTIVE；不同部门可并存；记录适用任职、来源epoch、relationVersion及结束原因；历史结束不删除，重授新ID/版本，不重置关系基线 |
| 管理范围与任命 | scopeId/version与appointmentId/version独立；一范围一个公司一个部门/系统集合；同范围同账号最多一项有效任命；可无人/空系统，不设人数上限；任命结束保留，不按名单删除原范围 |
| 后台账号及会话 | loginName全局唯一，员工至多一个后台账号；安全密码摘要、强制改密标记、credentialVersion；sid/jti、到期/撤销状态；退出撤销单会话，停用/改密/重置撤销所有旧会话；JWT本身不替代当前状态 |
| 变更申请与占用 | 草稿/固定明细、reason、原资格快照、版本/摘要、OA投递/审批/执行三轴；一角色最多一份占用配置方案；同关系的未结束变更互斥；终态释放但历史保留 |
| OA关联与结果接收 | OA实例＋eventId唯一；OA实例＋oaApprovalId只能关联一申请；申请只接受一项一致最终结果，业务执行最多成功一次；不同事件ID不能绕过申请防重 |
| HTTP幂等记录 | 主体＋方法＋规范路径＋key唯一，至少7天；规范请求摘要/状态/资源/安全响应引用原子保存；不保存密码明文、JWT或服务凭据；密码摘要比较使用受保护机制 |
| 导入文件/映射/批次 | 原文件SHA、明确字段/组织映射、规范行、目标版本和依赖基线、planned/actual计数；sourceSystem＋sourceBatchId唯一且同内容回放、不同内容冲突；成功批次长期防重 |
| 审计/事件/执行尝试 | 追加事件、当时名称与来源/差异快照、操作者/原提交者/执行服务分别表达；提交/批准/实际执行分别记录；一次成功授予只有一业务成功事件；失败尝试不覆盖历史 |
| 影响预览 | 可短期持久或受控存储的5分钟快照、内容摘要、范围、依赖基线及可见明细；一致统计/分页，不把previewId当授权凭证 |

唯一性须由数据库可靠约束/事务支撑，不能只靠查询后判断或前端禁用。软删除、历史表、条件唯一索引的具体落地由数据库阶段比较 MySQL 能力后决定；不直接预定 JPA 注解。

## 原子事务与隔离要求

| 事务边界 | 必须一起提交/回滚 |
| --- | --- |
| 系统/目录维护 | 本次全部命令＋唯一进入权限/目录绑定＋聚合/对象版本＋成功审计＋幂等结果 |
| 角色创建 | 角色UNCONFIGURED＋初始配置草稿＋占用＋审计；不得只保存一半 |
| 草稿/提交 | 协作版本＋实际明细＋占用；提交另冻结原依据/内容/版本/摘要/投递待办＋提交审计，不改变有效权限 |
| OA接收 | 最终结果＋接收记录＋APPROVED/REJECTED及可恢复执行依据；独立于实际业务执行事务 |
| 申请执行 | 所有明细条件复核＋全部关系/配置＋版本＋执行成功状态＋成功审计＋释放占用；任一失败全部回滚 |
| 来源关闭 | 来源周期/版本＋该来源关系失效＋受影响旧分配申请整份失效＋关系版本＋审计；包括从未有有效关系的来源 |
| 员工停用/任职结束 | 身份/任职变更＋确实不再适用来源/关系及任命持久失效＋周期/版本＋会话失效依据＋审计；恢复不逆转旧记录 |
| 范围/任命变更 | 范围版本、名单差异、相关管理上下文失效、实际不合法原申请失效及审计；不删除业务授权 |
| 账号/密码 | 账号/密码摘要/凭据版本＋强制改密＋立即会话失效＋安全审计/幂等结果，不改变业务角色 |
| 导入正式提交 | 所有组织/人员/任职更新＋来源/关系/任命必要失效＋会话依据＋batch成功结果和actualCounts＋成功摘要；禁止跳错行提交 |

等待OA、网络投递和HTTP响应不持有数据库事务。投递需可恢复待办，首次发送超时后按同一业务键重试。失败记录在业务事务回滚后另存；数据库完全不可用时依靠已可靠批准状态恢复，不能伪报失败审计落库。

关权/停用/任职变化与自动执行须有可证明的串行先后，版本检查不能放在写事务之外。来源不存在的0基线也要防并发“先查不存在、后任意插入”漏洞。权限查询的进入资格/菜单/操作来自同一已提交一致快照；撤权提交后开始的新查询必须可见新状态，一期不引入权限缓存。管理员写事务提交前再次复核当前资格/范围，防止并发取消资格后写入。

## 索引与容量分析输入（待数据库阶段设计）

后续按 ENDPOINTS 的筛选组合评估索引：按公司/来源部门/系统读取关系及历史；按员工/公司/系统计算有效来源；按角色读取配置及影响；按当前scope过滤申请；按状态/nextRetryAt恢复执行；按历史来源/occurredAt/id读取审计；按sourceBatchId查导入。不得为每个筛选字段盲目建索引，也不能用业务数据范围字段替代这些管理/授权来源约束。

用户输入最大长度、100条授权批次、1000行导入及分页上限见公共约定；这只是请求限制，不是吞吐承诺。审计/文件保留期、归档策略、实际权限目录规模和备份恢复在后续设计确认；API目前没有清空历史入口。

## 数据库阶段必须回查的场景

API评审修订补充（1.1.0，仍非物理表设计）：固定申请保存submittedAt并与原始摘要一致；预览保存同快照的角色/关系/来源/任命/申请目标影响及可见分类计数。导入规范行保存完整归属代码和字段前后值，首次缺代码的预检候选值也要冻结，提交时复核唯一性。状态组合的Schema只是静态防错，当前账号/范围、同系统、无环、关系唯一及并发授权检查不能交给Schema替代。

发送器领取/发送前须与申请失效受同一状态并发控制，不能因SEND_FAILED历史值而重投INVALIDATED申请；已在途的网络请求无法作跨系统回滚保证，迟到结果只记历史、不执行。幂等回放在当前认证/范围检查后、目标版本重校之前定位原已提交结果，避免成功请求因自身版本推进无法恢复；历史接受回放不是当前申请状态，应通过GET读取最新状态。

并发重复创建账号/角色/关系、双执行器、重复和冲突OA回调、无关系来源关权、关权和执行竞态、旧撤销误伤重授、任职结束但保留适用兼岗、范围缩小后恢复、全局停用后恢复、批次第N行失败、审计写入失败、进程在批准落地后或成功提交后中断。数据库方案若无法满足契约，应先提交影响分析回补API；不得静默删减已确认业务行为。

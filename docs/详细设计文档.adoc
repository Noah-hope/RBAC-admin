== 结构化设计与基于 DDD 的体系结构对比

`rbac1-structured`（默认端口 8081）与 `rbac1-ddd`（默认端口 8082）严格实现同一份 OpenAPI 契约（47 个 HTTP 接口）并共享同一套 MySQL 数据库与 RSA/Argon2 安全参数，但在软件体系结构与职责分配上采用两种截然不同的设计范式：

[cols="2,4,4",options="header"]
|===
|对比维度 |面向功能 / 结构化设计（`rbac1-structured`） |面向对象 / DDD 设计（`rbac1-ddd`）
|分层与依赖方向 |`controller → service → mapper → entity` 自上而下直线依赖，业务层直接依赖数据访问层与表映射实体 |`interfaces → application → domain ← infrastructure`，基础设施层实现领域仓储端口与应用端口（**依赖倒置 DIP**），由 `LayerDependencyTest` 强制守护
|核心模型形态 |**贫血模型（Anemic Model）**：`entity.*` 仅含 JPA 注解字段与 Lombok Getter/Setter，不包含任何业务方法 |**充血模型（Rich Domain Model）**：`domain.*` 为零框架依赖的纯 JDK 聚合根、值对象与领域服务，封装状态变更与业务不变式
|业务规则归属 |集中在 `RoleService`、`UserService`、`PermissionRequestService` 等事务脚本式方法中，跨表逻辑靠静态工具或辅助 Service 编排 |单聚合规则归聚合根（如 `Role`、`User`、`PermissionRequest`），跨聚合规则归不可变领域服务（如 `RoleHierarchy`、`DepartmentTree`、`ApprovalCandidates`），应用服务仅做薄编排
|持久化边界 |Service 直接注入并组合多个 Spring Data `JpaRepository`（`Mapper`），手动增删多张关联桥表行 |**一聚合一仓储端口**：领域层定义 `RoleRepository`、`UserRepository` 等接口，基础设施层 `Jpa*Repository` 封装主子表差量同步
|对象转换与 CloneFactory |`DTO → CloneFactory.copy → JPA Entity`，Service 直接构造并返回 `VO` |`DTO → Command → Domain → Result → VO`；领域层禁用 CloneFactory（保护封装），`@CopyFrom/@CopyNotNullTo` 仅标注在基础设施层 `*Po` 上用于 PO↔Domain 拷贝
|日志与异常处理 |`config/LayerLoggingAspect` 切入 `controller/service/mapper` 三层写 Logback 日志；`ManagementFailure` 由 `ApiExceptionHandler` 统一转 HTTP 状态码 |`infrastructure/logging/LayerLoggingAspect` 切入 `interfaces/application/infrastructure` 三层；领域层抛纯业务 `DomainException`、持久化适配器翻译唯一约束冲突，由 `RestExceptionHandler` 统一映射
|可测试性 |业务规则与数据库访问紧耦合，主要依赖启动 Spring + H2 的 MVC 集成测试验证 |领域核心规则可直接用毫秒级纯 JUnit 单元测试验证，辅以架构依赖测试与完整契约集成测试
|===

=== GRASP 职责分配原则在 DDD 实现中的落地

[cols="2,3,5",options="header"]
|===
|GRASP 原则 |代表性领域/应用类型 |职责分配理由与代码体现
|信息专家（Information Expert） |`Role`、`User`、`Department`、`PermissionDefinition`、`PermissionRequest`、`Operator` |谁拥有完成校验与状态改变所需的数据，职责就分给谁：例如 `User` 持有 `roleIds` 与 `status`，因此由 `User` 自己计算有效角色、执行业务角色差量替换、跨部门调动与管理员任免；`Operator` 持有操作者身份与部门，因此由它在应用层判断管理范围。
|创建者（Creator） |`Role.createBusiness`、`PermissionDefinition.register`、`PermissionRequest.submit`、`ApprovalCandidates.evaluate` |聚合与复杂值对象通过语义明确的静态工厂方法创建，创建时立即完成不变式校验（如菜单不能有父节点、按钮父节点必为同应用菜单），保证内存中不存在非法领域对象。
|控制器（Controller） |`*ApplicationService`（如 `RoleApplicationService`、`UserApplicationService`） |应用服务充当用例控制器，承接 REST 层转换后的 Command，协调事务、锁、权限守卫、领域行为、仓储持久化与审计记录，自身不堆砌业务分支计算。
|纯虚构（Pure Fabrication） |`RoleHierarchy`、`DepartmentTree`、`ApprovalCandidates`、`PermissionCatalog`、`RequestCatalog` |多角色 DAG 成环检测、后代按钮菜单完整性推演、组织子树遍历、审批最小权限候选筛选均跨越多个聚合实例，强塞进单个 `Role` 或 `Department` 会破坏低耦合，故提炼纯内存只读领域服务承担图算法。
|低耦合与高内聚（Low Coupling / High Cohesion） |聚合间 ID 引用、`RoleCreationRequestApplicationService` 复用 `RoleApplicationService.create` |聚合间仅存 ID 避免级联加载大对象网；角色创建审批直接复用建角色应用服务共享事务，使申请域与角色域高内聚、低耦合。
|间接与保护变化（Indirection / Protected Variations） |`RoleRepository` / `JpaRoleRepository`、`SessionStore` / `JpaSessionStore`、`ApplicationRoleCodeReader` |通过领域仓储端口与应用层端口隔离 JPA 多表操作、会话存储与外部系统角色码 SQL，数据库表或 ORM 细节变化不会波及领域层与应用层。
|===

== Docker Swarm 集群部署与课程系统统一身份接入

权限管理系统与课程项目管理系统均部署在 Docker Swarm 集群上（编排定义见 `deploy/stack.yml`）。集群通过节点标签（`node.labels.rbac.role`）将网关前端、结构化后端、DDD 后端与 MySQL 8.4 隔离调度至对应 Worker 节点，经加密 Overlay 网络 `rbac-net` 内部通信，并通过 Swarm Secrets 安全挂载数据库密码与 RSA 签名密钥对。

image::rbac1-swarm-deployment.svg[RBAC1-部署图-DockerSwarm集群,width=100%]

link:design-atlas/assets/rbac1-swarm-deployment.svg[在新窗口打开原尺寸矢量图（Docker Swarm 集群部署拓扑图） ↗]

* **双系统统一权限纳管**：权限管理后台（`permission-center`）与课程项目管理系统（`course-project-management`）均作为业务应用登记在权限中心。课程后端调用 `POST /auth/login` 签发多受众 RS256 JWT，使用 `/.well-known/jwks.json` 验签并调用 `GET /auth/api-permissions/{operationId}` 校验接口权限；课程前端携带同一令牌跨域调用 `GET /auth/me` 获取角色码（`teacher` / `student` / `admin`）与菜单许可，使菜单随 RBAC 授权动态变化。
* **三层 Logback 日志核验**：前端切换菜单触发请求时，后端 AOP 切面 `LayerLoggingAspect` 在数据访问层、业务/应用层、接口层依次输出同一请求线程的 Logback 日志，可通过 `docker service logs --tail 0 --follow rbac_structured`（或 `rbac_ddd`）实时观察。

== 核心 API 双实现详细设计（7 组代表性用例）

以下精选覆盖角色继承、权限申请、角色创建申请、用户组织管理、权限与 API 登记、部门树防环、统一身份鉴权 **全部 7 个核心领域模块**的代表性 API，逐一展示面向对象（DDD）与面向功能（结构化）的真实类图与顺序图对照。

=== 用例 01：角色继承配置（`PUT /api/v1/roles/{roleId}`）

单事务替换业务角色的直接权限与直接父角色列表：校验预置管理角色只读、禁止将已继承权限重复勾选为新增直接权限、禁止自继承与多跳循环继承，并验证当前角色及全部直接/间接后代角色的按钮仍具备所属菜单；成功后同步结算受影响用户的待审核权限申请。

==== 结构化 vs DDD 设计差异

[cols="2,4,4",options="header"]
|===
|维度 |结构化实现（`rbac1-structured`） |面向对象 DDD 实现（`rbac1-ddd`）
|业务规则位置 |全部集中在 `RoleService.update` 与 `validateConfiguration` 过程方法中 |聚合内部规则归 `Role.reconfigure`，跨角色图推演归 `RoleHierarchy`，菜单依赖归 `PermissionCatalog`
|实体形态 |`entity.Role` 仅有数据库列与 Getter/Setter（贫血模型） |`domain.role.Role` 为纯 Java 充血聚合根，无任何 Spring/JPA 注解
|持久化粒度 |`RoleService` 直接调用 `RoleMapper`、`RolePermissionMapper`、`RoleInheritanceMapper` 分别删增桥表 |应用服务仅调用一次 `RoleRepository.save(role)`，多表差量同步封装在基础设施层
|对象拷贝 |Service 手动构造关联实体行并赋值 |基础设施层在 `RolePo` 上使用 `@CopyFrom/@CopyNotNullTo` 配合 `CloneFactory` 完成 PO 与领域对象转换
|===

==== GRASP 职责分配（DDD 版）

* **信息专家（Information Expert）**：`Role.reconfigure` 持有自身直接权限与父角色集合，负责编辑资格校验与差量替换，并通过只读集合视图保护聚合不变式。
* **纯虚构（Pure Fabrication）**：`RoleHierarchy` 将全量业务角色多继承 DAG 封装为不可变内存快照，提供 `withConfiguration` 推演修改后的祖先成环与后代菜单完整性，避免污染单个 `Role` 聚合。
* **控制器（Controller）**：`RoleApplicationService.update` 仅协调权限守卫、加锁读取、领域规则调用、仓储保存、操作记录与申请自动结算，不包含图遍历细节。
* **间接与保护变化（Indirection / Protected Variations）**：`JpaRoleRepository` 实现领域层 `RoleRepository` 端口，内部封装 `sys_role`、`sys_role_permission`、`sys_role_inheritance` 三张表的差量持久化与重名异常翻译。

=== 用例 02：权限申请审核（`POST /api/v1/permission-requests/{requestId}/reviews`）

管理员在职责与部门范围内审核待处理权限申请：若申请人当前通过直接或继承角色已拥有目标权限，直接转为 `SATISFIED`；审批通过时按最新继承图筛选覆盖目标权限且不含无关权限的最小业务角色授予申请人，并联动结算该用户其余待审核申请。

==== 结构化 vs DDD 设计差异

[cols="2,4,4",options="header"]
|===
|维度 |结构化实现（`rbac1-structured`） |面向对象 DDD 实现（`rbac1-ddd`）
|状态流转控制 |`PermissionRequestService` 直接 `request.setStatus(...)` 依赖 JPA 脏检查写库 |领域枚举 `RequestStatus` + `PermissionRequest.approve/reject/settleWith` 严格受控
|最小角色筛选 |Service 循环调用静态工具 `ApprovalRules.extraPermissions` 过程式筛选 |独立领域对象 `ApprovalCandidates.evaluate` 建模候选资格与额外权限集合
|赋权持久化 |Service 直接 `new UserRole()` 并调用 `UserRoleMapper.save` 插入关联行 |调用 `User.grantBusinessRoles(Set.of(roleId))` 后通过 `UserRepository.save(applicant)` 保存聚合
|===

==== GRASP 职责分配（DDD 版）

* **信息专家（Information Expert）**：`PermissionRequest` 聚合根维护申请状态机（`PENDING → APPROVED / REJECTED / SATISFIED / WITHDRAWN`），确保终态不可逆转。
* **纯虚构与创建者（Pure Fabrication / Creator）**：`ApprovalCandidates.evaluate` 静态工厂遍历 `RoleHierarchy` 计算每个业务角色的有效权限与多余权限，构造不可变候选角色集合。
* **高内聚（High Cohesion）**：用户赋权委托给 `User.grantBusinessRoles` 聚合方法，申请状态流转归 `PermissionRequest.approve`，各自聚焦单一领域职责。
* **控制器（Controller）**：`PermissionRequestApplicationService.review` 编排操作者管理范围核验、行锁加载、赋权落库、审计与 `PermissionRequestSettlement` 联动结算。

=== 用例 03：角色创建申请审批（`POST /api/v1/role-creation-requests/{requestId}/reviews`）

总管理员审核部门管理员提交的角色创建申请：驳回时直接更新状态；通过时可调整角色配置，并在同一事务中复用新建业务角色流程按最新父角色继承图完成校验与建角色，任何环路、重名或菜单缺失均使事务整体回滚，申请保持待审核。

==== 结构化 vs DDD 设计差异

[cols="2,4,4",options="header"]
|===
|维度 |结构化实现（`rbac1-structured`） |面向对象 DDD 实现（`rbac1-ddd`）

|===

==== GRASP 职责分配（DDD 版）

* **创建者（Creator）**：`Role.createBusiness` 静态工厂同时被直接建角色、提交创建申请预校验和审批通过建角色三处复用，规则零重复。
* **信息专家（Information Expert）**：`RoleCreationRequest` 保存父角色 ID 与名称快照（`ParentRoleSnapshot`），自行校验待审状态并在 `approve` 中绑定新建角色 ID。

* **间接（Indirection）**：`JpaRoleCreationRequestRepository` 封装主表与直接权限、父角色快照两张子表的聚合重建与保存。

=== 用例 06：部门调整与防环校验（`PATCH /api/v1/departments/{departmentId}`）

总管理员修改组织部门名称或调整其上级部门（`parentId = null` 表示移为顶层部门）：校验新上级存在且不能是当前部门自身或其任意层级的下级部门，防止组织树出现环路；有实际变更时写入全局操作日志。

==== 结构化 vs DDD 设计差异

[cols="2,4,4",options="header"]
|===
|维度 |结构化实现（`rbac1-structured`） |面向对象 DDD 实现（`rbac1-ddd`）
|防环算法组织 |`DepartmentService.update` 在方法体内加载全表构造临时 `Map`，用 `for` 循环沿 `parentId` 向上回溯检查是否遇到当前部门 ID |抽离不可变领域服务 `DepartmentTree`，既复用于管理范围子树计算，又提供 `ensureCanMove` 防环断言

* **纯虚构（Pure Fabrication）**：`DepartmentTree` 构造时将父指针反转为子邻接表，`ensureCanMove` 利用 `subtreeOf(departmentId)` 广度优先判断目标上级是否落在当前子树内。
* **控制器（Controller）**：`DepartmentApplicationService.update` 编排总管理员校验、按需加载 `DepartmentTree`、保存聚合与记录前后上级名称变化。

=== 用例 07：统一身份与有效权限查询（`GET /auth/me`）

为权限管理前端与接入的课程项目管理系统返回当前登录用户在目标应用中的统一身份、角色列表及去重后的有效权限编码（含多父多层继承）。启用应用角色码映射时返回映射后的角色码（如 `teacher`/`student`/`admin`），未启用时返回在该应用提供有效权限的直接角色 ID。

==== 结构化 vs DDD 设计差异

[cols="2,4,4",options="header"]
|===
|维度 |结构化实现（`rbac1-structured`） |面向对象 DDD 实现（`rbac1-ddd`）

|继承权限计算 |`RolePermissionService` 加载五表构建 `Graph` 记录，在无状态 Service 方法中传参遍历 Map |`User`、`RoleHierarchy`、`PermissionCatalog` 三者按信息专家协作计算有效权限与角色列表

* **信息专家（Information Expert）**：`AuthenticatedSession.applicationContext` 校验请求头 `X-Application-Code` 是否包含在 JWT 受众（`aud`）中；`User` 结合 `RoleHierarchy` 计算有效权限与可达业务角色。

## 结论

**有条件通过，可以启动 API 设计。** 已具备接口建模所需的业务边界、参与者、页面、主要流程、状态及异常依据；未发现必须重新开启需求分析的重大矛盾。无需继续以全面视觉调整作为进入 API 阶段的前置条件。

“有路径”不等于每项详细验收均已自动化验证。源代码和浏览器检查随 Git 保存，测试在 [e2e](prototype/e2e/) 中。

| 用例 | 页面/路径 | 评审结果 |
| --- | --- | --- |
| UC-01 | 系统与权限目录 | 系统/功能/操作、系统进入、启停、菜单可见条件、自定义操作；排序呈现待补 |
| UC-02 | 角色权限 → 草稿/配置/差异预览 → 变更申请 | 编码生成、共享角色只读、操作独立、配置经 OA；员工影响摘要待补 |

| UC-04 | 员工来源详情 → 一般撤销/关闭原部门权限 | 两种生效方式区分，其他来源保留、历史只读；批量一般撤销待补 |
| UC-05 | 权限调用演示 → 查询有效权限 | 当前公司与系统隔离、系统进入前提、菜单/操作分别展示；只编辑不推导查看 |

R-01～R-03 不需要新增业务决策，其需求依据已经存在；它们不应因原型省略而在 API 中被删掉。R-04 是工具协作方式，不是新增业务模块。

## API 阶段的首批工作

1. 明确契约权威来源、Apifox 导入及 MCP 回读流程，建立用例—页面—接口追踪表。
2. 统一公司、部门、任职、来源授权、来源周期、角色、权限、后台任命、固定申请及导入批次的标识和版本含义；角色编码由后端生成，不沿用浏览器序号作为正式算法。
3. 区分管理员会话、受信业务系统调用、OA 结果回调三类入口，定义调用身份与范围校验。来源关闭后迟到批准、原申请人离任、原范围缩小分别按需求处理。
4. 定义请求/响应、分页、字段校验、权限不足、状态冲突、版本冲突、无变化、依赖故障及失败恢复；落实请求幂等、重复/冲突回调、固定方案和批量整体结果。
5. 设计 OA 投递、可信最终结果接收、服务端自动执行与重试；不把“已批准”作为“执行成功”，不增加管理员接手或二次确认步骤。
6. 补齐 R-01～R-03 的响应及原型演示，再评审契约，后续进入数据库设计。

以上是下一阶段待办，尚非已确定的路由、字段或实现技术。正式后端认证、幂等、并发、数据库事务及跨服务恢复均仍须后续设计和验证，原型测试不替代正式实现的 TDD。

## 非阻塞未决项

- 原材料中“全部”、空白 I340、“系统管理后台”及本人限定来源差异仍需核对；不影响通用权限模型和接口设计，在初始化真实权限/角色数据前解决，不猜测或使用未来权限通配。
- 最新共享文档已记录 Spring Boot + Spring Data JPA、MySQL、RESTful API 及 JWT 等技术选型；具体版本、JWT 生命周期/失效、真实 Excel/HR/OA 接入和完整事务/并发方案仍待后续设计。已有 Mock 边界不能被当作正式数据格式或后端限制。
- 后续细节视觉优化、完整无障碍审计和多浏览器兼容验证可继续跟踪，不要求先完成所有视觉修改才开展 API 设计。

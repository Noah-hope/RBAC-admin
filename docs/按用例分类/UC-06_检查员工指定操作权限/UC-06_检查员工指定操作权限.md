# UC-06 检查员工指定操作权限

版本：V1.0，2026-10-13。状态：本轮需求审视已确认的最终用例基线，供小组设计与验收使用。

本轮更新：统一公司上下文、任职持续资格、失效不自动恢复、操作支持范围及人员资料规则。

### 最终需求基线（2026-10-13）

- 一期实现 RBAC0 权限管理：员工经角色获得权限，无角色继承、直接用户授权或显式拒绝。外部系统只做简单 HTTP 调用演示，不实现其内部业务。
- 角色属于一个公司和一个业务系统，可限定部门；公司级角色要求本公司有效任职，部门级角色要求在该部门直接有效任职，不自动覆盖下属部门。岗位不自动绑定角色；任职条件与权限需要均未改变时，不因岗位名称变化更换角色。
- UC-05/06 按“员工＋当前公司＋业务系统”计算权限。仅合并该公司、该系统内的有效角色；系统进入资格与功能权限也必须来自该公司、该系统。公司数据隔离、SELF 对象判断和过滤由业务系统实施。
- 任职变化后不再满足角色条件的授权立即失效；有其他符合条件的兼岗则保留该授权。员工全局停用使其全部业务授权及公司专员任命失效，不区分临时停用与离职。保留历史，不物理删除；恢复身份或任职不自动恢复失效授权，业务角色重新申请 OA 批准，专员由总管理员按 UC-07 重新任命。
- 操作目录明确支持范围：有明确本人语义的操作可支持 SELF/ALL，其他功能操作一期仅支持 ALL；SYSTEM_ACCESS 不适用范围，scope=null。配置及执行均校验所选范围属于支持集合。
- 员工、公司、部门使用稳定内部 ID；首次导入以源唯一用户名建立员工映射，组织分配稳定编码，更名不改变身份。人员变更模板明确新增任职、结束任职、停用、恢复等动作，不从文件缺行推断离职。
- 一期使用至少两个公司、两个系统的代表性数据，覆盖多角色、兼岗、公司隔离、本人范围、审批生效、撤销、失效及重新申请。其余资料后续逐步补齐。

以上为本轮已确认规则，详细流程与验收必须遵循；描述的是需求设计，不代表代码已实现或真实外部系统已完成对接。

## 1. 用例概述

| 项目 | 说明 |
| --- | --- |
| 编号 | UC-06，沿用原编号；旧图名为“校验业务访问权限” |
| 名称 | 检查员工指定操作权限 |
| 目标 | 判断员工在调用方所属业务系统中是否拥有指定操作权限，并返回有效数据范围 |
| 主要参与者 | 已登记且通过服务身份认证的业务系统后端 |
| 触发 | 外部系统需要检查某名员工的一项操作权限 |
| 前置条件 | 调用方身份及系统绑定有效；业务系统自行认证员工，并提供稳定的员工统一标识 |
| 成功结果 | 功能操作有权限时返回 ALL／SELF；系统进入权限有权限时 scope=null；无权限返回 false、null |
| 后置条件 | 不修改角色、授权或外部业务数据，仅记录必要调用信息 |

UC-05 返回员工在当前系统的全部有效权限，UC-06 只检查指定的一项。二者可独立调用，不要求先查询全部权限再检查单项权限。本用例不经过 OA 审批。

### 统一管理与公司边界（本轮已确认）

“公司权限管理专员”即公司授权管理员（早期图中称部门授权管理员）；总公司和各分公司各自指定 1～3 名，可仅一名。公司人员范围按明确公司归属及所属部门层级计算，遇到另一个公司节点停止，不因总公司位于组织树上层而包含全部分公司。

权限中心总管理员可管理所有公司、所有系统及所有公司专员，也可办理 UC-02～04；公司专员仅在本公司获准系统内办理。双方的业务角色配置、分配、撤销均经过 OA。总管理员跨公司办理时仍明确目标公司；每份申请按一个公司归属保存，系统状态、目标合法性及版本校验照常执行。

一期不配置逐操作及 ALL／SELF 的申请上限，也不逐个指定可分配角色。获准系统目录内的合法权限可以申请，角色授权内容仍由 OA 审批。后台资格不自动产生外部业务系统进入权限。


## 2. 职责边界

| 权限中心负责 | 外部业务系统负责 |
| --- | --- |
| 定义调用参数、认证要求及返回格式 | 按接口约定接入，决定何时调用 |
| 验证调用身份及系统范围 | 登录认证员工，从自身登录上下文取得员工标识 |
| 计算指定操作的当前有效授权和范围 | 确定业务功能对应哪个权限编码 |
| 返回有无权限及 ALL／SELF | 判断记录是否属于该员工、过滤列表、执行实际拦截 |

权限中心不接收业务记录 ID、记录所属员工 ownerId 等上下文，不连接外部业务数据库，不替外部系统判断某条记录是否可编辑。外部系统内部如何实现归属校验、页面和查询语句不在本项目展开。

接口返回“有编辑权限，范围 SELF”仅表示拥有编辑本人数据的资格，不表示已批准编辑任意记录。ALL 表示不附加本人限制，也不取代外部系统其他业务规则。

### 系统进入权限（已确认）

本接口同时支持检查系统进入权限和功能操作。先认证调用方并验证绑定系统、员工状态。目标为 SYSTEM_ACCESS 时，直接检查其有效授权来源，无需递归检查自己；有则返回 `hasPermission=true, scope=null`，无则返回 `false, null`。

目标为 FUNCTION_OPERATION 时，必须先确认当前公司、当前系统有效进入授权；缺少时直接返回 `hasPermission=false, scope=null`，即使角色仍配置着该功能操作。有进入资格后再检查目标操作并合并 ALL／SELF，权限可来自同系统不同角色。只有功能操作返回 true 时 scope 才必须为 ALL 或 SELF；进入权限 true 时 null 表示不适用，绝不是 ALL。

响应建议回显 permissionCode 和 permissionType，方便调用方区分范围语义。未知编码返回 false、null（类型也可为 null）；所有认证错误与服务故障仍按错误响应处理，不能伪装成无权限或放行。

## 3. 输入与输出

| 输入 | 说明 |
| --- | --- |
| 服务调用凭据 | 识别已登记调用方并确定其绑定业务系统，不放在浏览器公开使用 |
| 当前公司标识 | 必填；调用方提供当前业务公司，权限中心验证公司有效及员工任职，不跨公司合并 |
| 员工统一标识 | 由受信业务后端取得，不按姓名或岗位名称猜测身份 |
| 权限编码 | 当前系统内唯一，可指定系统访问权限或功能操作权限 |
| 系统编码（若请求保留） | 必须与服务身份绑定的系统一致，不能靠改参数跨系统查询 |
| 请求编号 | 关联排错记录，不是授权凭据 |

建议使用 hasPermission 表达“拥有该操作权限”，避免 allow 被理解为已对具体业务记录放行。以下 JSON 只说明含义，接口地址、字段及错误码在 API 设计时最终确定：

```json
{
  "systemCode": "hr",
  "companyId": "COMP_BRIDGE",
  "employeeId": "EMP_DEMO_001",
  "permissionCode": "employee:edit",
  "requestId": "example-check-001"
}
```

有功能操作权限（已满足当前系统进入资格）：

```json
{"permissionCode": "employee:edit", "permissionType": "FUNCTION_OPERATION", "hasPermission": true, "scope": "SELF", "requestId": "example-check-001"}
```

无权限：

```json
{"permissionCode": "employee:edit", "permissionType": "FUNCTION_OPERATION", "hasPermission": false, "scope": null, "requestId": "example-check-001"}
```

返回范围属于被检查的这一项操作，不是员工的统一全局范围。调用方不得只检查 hasPermission 而忽略 SELF。

直接检查系统进入权限的成功响应示例：

```json
{"permissionCode":"hr:access","permissionType":"SYSTEM_ACCESS","hasPermission":true,"scope":null,"requestId":"example-check-002"}
```

## 4. 核心规则

1. 只读取员工在当前公司、当前系统已生效且未失效的角色授权，并核对适用任职。其他系统同名权限不参与计算；跨公司兼岗时按当前公司分别查询，其他公司的角色不参与本次计算。
2. 按操作取有效授权并集：无来源则无权限；全部来源为 SELF 则 SELF；任一来源为 ALL 则 ALL。查看 ALL 不扩大编辑 SELF。
3. 员工停用、角色尚未生效、权限停用或关联撤销时，相应来源不产生有效权限；员工停用直接返回无权限。
4. 草稿、待审批和批准待执行的新增方案不能提前增加权限；撤销待审批本身不扣除权限。只读实际生效状态。
5. 不从岗位名称、角色显示名称或菜单是否显示推导操作授权；编辑不自动包含查看，菜单父子关系不等于权限继承。
6. 一期与 UC-05 共用有效授权和范围合并规则，不引入权限缓存。返回结果代表本次读取时的状态，不是永久访问凭证。
7. 系统进入权限是功能操作检查的必要前提；直接检查进入权限不递归检查自身，不因获得进入资格授予全部功能。

目录有效性与 UC-05 一致：按 [UC-01_维护业务系统与权限目录.md](../UC-01_维护业务系统与权限目录/UC-01_维护业务系统与权限目录.md) 的一期约定，功能或任一祖先目录停用时，该功能操作不参与授权计算。重新启用可能恢复仍有效的旧授权，但不恢复已撤销关联。

## 5. 正常流程

| 步骤 | 外部系统操作 | 权限中心处理 |
| --- | --- | --- |
| 1 | 携带服务凭据发送员工标识和操作编码 | 校验参数、服务身份及系统绑定 |
| 2 | 等待结果 | 检查员工状态及当前公司任职，查找当前系统目标权限及其有效性 |
| 3 | — | 先查系统进入资格：直接检查 SYSTEM_ACCESS 则返回其结果；检查功能时，无进入资格直接返回 false，否则再查目标操作来源 |
| 4 | — | 无来源时返回无权限；有来源时合并该操作的 ALL／SELF 范围 |
| 5 | — | 记录必要调用摘要并返回结果，认证失败或服务故障另行返回错误 |
| 6 | 接收结果 | 外部系统自行执行拒绝、当前公司数据隔离、SELF 限制及其他业务校验；权限中心不继续处理业务记录 |

接口正常返回无权限与调用失败是不同结果。权限中心不使用超时、数据库异常等故障伪造正常的无权限响应，更不能故障默认放行。

## 6. 替代与异常流程

本稿采用以下接口行为约定，具体 HTTP 状态码留到 API 设计：

| 编号 | 条件 | 处理 |
| --- | --- | --- |
| E01 | 员工标识或操作编码缺失、格式错误 | 参数错误，不使用默认员工或默认权限 |
| E02 | 调用凭据无效、缺失 | 认证错误，不返回权限结果 |
| E03 | 请求跨出绑定系统，或绑定系统已停用 | 授权错误，不检查其他系统权限 |
| E04 | 员工不存在或停用 | 正常返回 hasPermission=false、scope=null，不泄露额外人员资料 |
| E05 | 操作不存在、停用或无有效授权来源 | 正常返回无权限，不把未知编码当成无限制操作 |
| E06 | 多角色重复授予指定操作 | 合并为一个结果；SELF＋ALL＝ALL |
| E07 | 所需数据范围非法、数据库不可用 | 返回服务错误，不默认 ALL 或假成功 |
| E08 | 查询期间发生授权变更 | 按一致读取的已提交状态返回；变更成功后发起的新检查反映新状态 |

外部系统应将接口错误视为本次检查未成功，不能据此执行受保护操作；此处只声明调用契约，不设计其内部故障处理框架。

## 7. 交互示例

员工甲已有 HR 系统进入资格。HR 后端询问“员工甲是否有编辑员工信息权限”，权限中心返回有权限、SELF。HR 再依据自身数据确定目标记录是否属于员工甲：属于甲才满足本人限制，属于乙则不满足。记录归属不发送到本接口，权限中心没有对这条具体记录作最终决定。

如果员工甲另有有效 HR 角色提供该操作 ALL，接口返回 ALL；撤销 ALL 来源并执行成功后，再次检查返回 SELF。若最后一个编辑授权也被撤销，则返回无权限。

列表操作同样可以检查其对应权限及范围，但返回 SELF 不是具体行列表；业务系统负责将本人限制应用于数据读取。权限中心不返回外部业务数据。

## 8. 数据与事务边界

读取员工、系统、员工角色关联、角色、角色权限及操作目录的有效状态。无需读取外部业务记录，不读取 OA 审批节点，不写授权关系。

复用 UC-05 的有效性过滤和逐操作范围合并，保证相同数据状态下，单项检查与全量查询对应操作一致。采用本地一致读取；接口不持有跨系统事务，也不承诺回滚已经开始或完成的外部操作。

调用日志记录请求编号、系统、必要员工标识、操作编码、结果/范围和时间，不记录服务凭据及无关人员资料。具体日志失败策略在公共日志设计中统一，不引入新的审批流程。

## 9. 结构化功能分解

```text
检查员工指定操作权限
├── 校验请求参数与调用身份
├── 确定绑定系统、员工和目标操作
├── 判断系统进入资格（直接检查进入权限则返回结果）
├── 有进入资格后查询目标功能操作有效授权来源
├── 判定有无权限并合并该操作范围
└── 记录调用摘要并返回

外部业务系统：接收结果 → 执行本人限制及其他业务规则 → 放行或拦截
```

与 UC-05 共用查询和合并的内部处理模块即可，不要求拆为独立服务；两个用例没有必须先后调用的关系。

## 11. 后续衔接

- API 设计确定服务认证、参数、响应和错误码；外部系统按约定接入。
- UC-05 与 UC-06 共享有效授权规则；本人记录判断与列表过滤由外部系统实现，不再列为权限中心内部功能。
- 用例图与正文均使用“UC-06 检查员工指定操作权限”，已统一文字并保留手工布局。

### 本轮补充验收

| 场景 | 预期 |
| --- | --- |
| 当前公司缺失或公司不存在／停用 | 缺失／格式错误返回参数错误；未知／停用公司返回无进入资格／无权限，不混合其他公司授权 |

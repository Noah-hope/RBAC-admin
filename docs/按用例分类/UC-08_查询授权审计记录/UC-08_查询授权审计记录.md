# UC-08 查询授权审计记录

版本：V1.1，2026-10-15。状态：功能权限范围已按用户确认修订，其他业务规则沿用原基线，供小组设计与验收使用。

本轮更新：按用户要求限定为功能权限管理，移除业务数据权限设计；保留公司授权上下文、任职持续资格、审批执行及历史规则。

### 当前需求基线（2026-10-15，功能权限修订）

- 一期实现 RBAC0 权限管理：员工经角色获得权限，无角色继承、直接用户授权或显式拒绝。外部系统只做简单 HTTP 调用演示，不实现其内部业务。
- 角色属于一个公司和一个业务系统，可限定部门；公司级角色要求本公司有效任职，部门级角色要求在该部门直接有效任职，不自动覆盖下属部门。岗位不自动绑定角色；任职条件与权限需要均未改变时，不因岗位名称变化更换角色。
- UC-05/06 按“员工＋当前公司＋业务系统”计算权限。仅合并该公司、该系统内的有效角色；系统进入资格与功能权限也必须来自该公司、该系统。公司上下文隔离的是功能授权来源，不定义业务数据访问范围。
- 任职变化后不再满足角色条件的授权立即失效；有其他符合条件的兼岗则保留该授权。员工全局停用使其全部业务授权及公司专员任命失效，不区分临时停用与离职。保留历史，不物理删除；恢复身份或任职不自动恢复失效授权，业务角色重新申请 OA 批准，专员由总管理员按 UC-07 重新任命。
- 当前 RBAC 系统只管理功能权限。目录登记系统进入权限与功能操作，角色配置是否授予；不定义、保存或返回业务数据范围，不设计本人记录判断或行过滤规则。
- 员工、公司、部门使用稳定内部 ID；首次导入以源唯一用户名建立员工映射，组织分配稳定编码，更名不改变身份。人员变更模板明确新增任职、结束任职、停用、恢复等动作，不从文件缺行推断离职。
- 一期使用至少两个公司、两个系统的代表性数据，覆盖多角色、兼岗、公司授权隔离、功能操作独立与去重、审批生效、撤销、失效及重新申请。其余资料后续逐步补齐。

以上为本轮已确认规则，详细流程与验收必须遵循；描述的是需求设计，不代表代码已实现或真实外部系统已完成对接。

## 1. 用例概述

| 项目 | 说明 |
| --- | --- |
| 编号与名称 | UC-08 查询授权审计记录 |
| 目标 | 在有权查看的范围内追溯谁对哪些角色、员工或管理配置作了什么变更，以及申请、审批和执行结果 |
| 参与者 | 权限中心总管理员、具备查询资格的公司权限管理专员 |
| 触发 | 核对授权结果、处理疑问、检查历史配置或定位失败原因 |
| 前置条件 | 管理员登录及资格有效；当前身份具有相应审计范围 |
| 成功结果 | 返回范围内的分页记录和详情，包括变更内容、来源与结果 |
| 后置条件 | 不修改审计记录，不改变角色、员工权限或申请状态 |

查询不经 OA 审批。此处“审计”是追溯已有操作记录，不是再次审批申请，也不代表本项目实现专业合规审计平台。

### 统一管理与公司边界（本轮已确认）

“公司权限管理专员”即公司授权管理员（早期图中称部门授权管理员）；总公司和各分公司各自指定 1～3 名，可仅一名。公司人员范围按明确公司归属及所属部门层级计算，遇到另一个公司节点停止，不因总公司位于组织树上层而包含全部分公司。

权限中心总管理员可管理所有公司、所有系统及所有公司专员，也可办理 UC-02～04；公司专员仅在本公司获准系统内办理。双方的业务角色配置、分配、撤销均经过 OA。总管理员跨公司办理时仍明确目标公司；每份申请按一个公司归属保存，系统状态、目标合法性及版本校验照常执行。

一期公司管理范围只限定人员、角色归属与获准系统，不逐项指定可分配角色或可申请操作。获准系统目录内的合法权限可以申请，角色授权内容仍由 OA 审批。后台资格不自动产生外部业务系统进入权限。


## 2. 一期范围与查询权限

一期提供筛选、分页、详情查看和同一申请的关联事件查看。不提供修改/删除日志、导出、复杂报表、自动风险判定或从审计页面恢复旧权限。

| 身份/记录类别 | 本稿查询规则 |
| --- | --- |
| 权限中心总管理员 | 可查看平台范围内的目录、管理员配置及角色授权审计 |
| 公司权限管理专员 | 查看来源属于本公司及所属部门及其下级部门（不跨其他公司边界）、业务系统在当前获准范围内的角色配置、分配、撤销及对应执行事件 |
| 同公司其他专员办理的申请 | 共享范围内可查，不限本人创建或执行的记录 |
| 全局目录维护、专员任免和范围配置记录 | 一期由总管理员查看，不因同公司共享角色管理而开放全局管理日志 |
| 普通业务员工、外部系统调用方 | 不能凭业务角色或服务凭据访问后台审计查询 |

上述细分为一期设计约定，查询资格与 UC-07 的当前任命及公司范围保持一致。判断采用记录产生时的来源组织/系统和查询者当前管理范围：员工调岗不把旧日志迁到新公司；专员权限缩小或取消后不能凭旧会话继续查原范围。

无明确来源、混合来源而无法安全分隔的管理记录暂仅总管理员可见，不靠操作者姓名猜测归属。列表、数量统计、详情以及关联申请记录均使用同一范围过滤。

### 系统进入权限（已确认）

审计详情区分系统进入权限与功能操作，记录各自类型、编码及授予/移除变化。撤销最后一个进入来源会使功能不可用，但不等于全部功能关联已被删除。

历史快照反映当次配置/关联变化；是否仍有其他进入来源，以事件时实际记录为准，不能用当前权限倒推。重新获得进入资格后旧功能授权恢复可用，不补造“重新分配全部功能”的历史事件。后台审计查询资格仍由 UC-07 决定。

## 3. 审计内容与事件来源

| 来源用例 | 主要记录 |
| --- | --- |
| UC-01 | 目录登记、修改、启停、菜单可见条件变更 |
| UC-02 | 角色草稿、权限配置申请及固定变更内容 |
| UC-03/04 | 员工角色分配/撤销申请、目标关联和原因 |
| UC-07 | 专员任免、公司系统管理范围调整 |
| UC-11 | OA 最终结果接收、批准后执行成功或失败 |

UC-05/06 的权限 API 调用日志、UC-09 登录日志和 UC-10 导入报告可独立保留，一期不全部混入授权审计列表。数据库报错堆栈属于服务端诊断日志，不向专员直接展示。

申请提交、OA 批准、实际执行分别记录不同事件。即使审批通过，仍须看到执行成功才能说明变更已落地；执行失败不能记成成功授权。OA 只记录交付的最终结果和关联编号，不要求导入其内部节点、审批人流转历史。

## 4. 输入与输出

| 查询输入 | 说明 |
| --- | --- |
| 时间范围 | 按事件发生时间筛选，起止边界及显示时区在 API 中统一 |
| 公司/部门、业务系统 | 总管理员可选择；专员只能在当前范围内进一步缩小 |
| 员工、角色、操作者标识 | 用稳定 ID 定位，不把同名人员当作同一人 |
| 操作类型、事件结果 | 如角色配置、分配、撤销；提交、驳回、执行成功、执行失败 |
| 申请/请求/审批编号 | 定位同一业务操作的关联记录，不凭编号绕过范围检查 |
| 页码与每页条数 | 后端校验并限制最大条数，具体值在 API 设计确定 |

输出分为摘要列表和按需加载的详情：

- 摘要：记录 ID、时间、事件类型、来源公司/系统、操作者摘要、目标摘要、事件结果、申请编号。
- 详情：原申请人、实际操作人或执行服务、目标员工/角色的 ID 与必要名称、变更前后快照或差异、原因、方案版本、外部审批编号、执行结果及可披露错误说明。
- 关联事件：同一申请的提交、最终审批结果、执行尝试及最终结果，按时间和稳定记录 ID 排序。

不返回密码、令牌、服务密钥、完整手机号、原始回调凭据或完整异常堆栈。名称使用事件时快照辅助阅读，当前改名不改写历史。

## 5. 正常流程

| 步骤 | 管理员操作 | 系统处理 |
| --- | --- | --- |
| 1 | 打开审计查询页面 | 校验会话、当前管理资格并计算可查询范围 |
| 2 | 填写筛选条件 | 校验字段、时间范围和分页参数，范围由后端强制附加 |
| 3 | 点击查询 | 在权限范围与筛选条件交集中分页读取，返回安全摘要及同范围总数 |
| 4 | 选择一条记录 | 重新验证详情查询资格和记录来源，不能只依赖列表曾出现过该记录 |
| 5 | 查看差异与关联事件 | 展示申请内容、审批结果及执行结果，区分拟变更与已发生变更 |
| 6 | 调整条件或返回列表 | 继续只读查询，不触发审批、重新执行或撤销 |

当前无匹配记录时正常显示“无符合条件的记录”。查询服务故障返回错误，不显示成没有日志。

## 6. 变更前后内容示例

| 事件 | 详情展示重点 |
| --- | --- |
| 角色配置申请 | 拟新增/移除的功能操作、基础版本；标注尚未执行 |
| 分配执行成功 | 哪名员工新增哪个角色关联、来源组织、执行时间；不把所有角色权限重复保存为直接用户授权 |
| 撤销执行成功 | 哪条关联从有效变为已撤销；不声称重合权限一定消失 |
| 公司范围调整 | 原系统集合、新系统集合及增减差异 |
| 专员任免 | 原名单、新名单及明确的新增/取消项，不涉及业务角色自动撤销 |

例如申请 Q001：专员甲提交“撤销员工乙的角色 A”，OA 返回批准，但第一次执行数据库失败。页面应显示“已批准、执行失败”，原关联尚未因这次失败而撤销。后来重试成功再追加成功事件，保留失败历史，不覆盖成从未失败。

详情中的“拟变更前后”来自固定申请，“实际变更前后”来自执行事务，不能混用。审计快照用于追溯当时事件，不代替 UC-05 查询员工现在仍有哪些权限；后续角色变化可能已改变当前结果。

## 7. 替代与异常流程

| 编号 | 条件 | 处理 |
| --- | --- | --- |
| E01 | 会话过期、专员资格取消或无查询能力 | 拒绝查询，不因页面仍打开而允许读取 |
| E02 | 显式请求其他公司或未获准系统的筛选范围 | 拒绝越范围请求；不返回目标是否存在等多余信息 |
| E03 | 猜测越范围详情 ID 或审批编号 | 与不存在详情采用统一的不可访问/未找到响应，不泄露内容 |
| E04 | 无符合条件记录 | 返回正常空列表与零条匹配结果 |
| E05 | 时间倒置、非法页码、过大条数 | 参数错误或按已公布限制处理，不执行无界查询 |
| E06 | 员工或角色已改名、员工已停用或关联已撤销 | 有权限时仍可按稳定标识与历史快照追溯 |
| E07 | 审计数据库查询失败 | 返回服务错误，不伪装为空列表 |
| E08 | 范围在列表与详情请求之间缩小 | 详情按最新范围拒绝，不继续使用旧快照权限 |
| E09 | 多次相同 OA 成功通知 | 关联到原成功执行记录，不伪造多次授权成功事件 |
| E10 | 专员请求修改/删除记录或从详情重放操作 | 本用例不提供该能力；后端也不开放相应入口 |

## 8. 记录可靠性与数据边界

UC-08 负责读取，不在查询时补造“成功审计”。各写入用例负责在变更发生时记录事件：

- 配置/授权变更、执行状态与成功审计在同一本地事务提交，审计写入失败则业务变更回滚。
- 失败执行记录在回滚后另行可靠记录；数据库整体不可用时通过服务端诊断日志保留错误并在恢复流程中处理，不能承诺此时审计表一定已有失败记录。
- 原始事件追加保存；重试、驳回重提及后续成功作为新的关联事件，不覆盖旧事件。方案当前状态可以变化，但历史事件不随之重写。
- 权限中心不声称提供防数据库管理员篡改的专用审计基础设施。一期通过业务接口只读、写入事务及必要权限隔离支持追溯。

逻辑数据包括 AuditLog/审计事件、变更快照及 AuthorizationChange 的关联编号。查询业务对象只用于允许的辅助信息，不能用当前角色配置替代历史差异。

查询不修改授权，可生成普通访问诊断日志；一期不要求每次读取都再产生授权审计事件。保留期限、归档和导出后续确定，本用例不提供清空历史操作。

## 9. 结构化功能分解

```text
查询授权审计记录
├── 校验管理员会话与当前资格
├── 计算组织、系统及记录类型的可见范围
├── 校验筛选与分页参数
├── 查询范围内记录及匹配数量
├── 校验详情/关联事件的访问范围
└── 整理快照、差异和结果并脱敏展示

其他用例：在提交、执行或配置变更时记录事件
UC-08：只读追溯，不审批、不执行历史操作
```

列表、详情及关联查询共用范围校验模块，避免只有页面入口受限而详情接口泄露数据。记录分页采用稳定排序，避免相同时间戳导致顺序随机。

| UC08-T16 | 参数非法或越过分页上限 | 参数校验生效，不执行无界查询 |

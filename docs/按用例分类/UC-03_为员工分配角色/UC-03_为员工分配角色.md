# UC-03 为员工分配角色

版本：V1.0，2026-10-13。状态：本轮需求审视已确认的最终用例基线，供小组设计与验收使用。

本轮更新：统一公司上下文、任职持续资格、失效不自动恢复、操作支持范围及人员资料规则。

### 最终需求基线（2026-10-13）

- 一期实现 RBAC0 权限管理：员工经角色获得权限，无角色继承、直接用户授权或显式拒绝。外部系统只做简单 HTTP 调用演示，不实现其内部业务。
- 角色属于一个公司和一个业务系统，可限定部门；公司级角色要求本公司有效任职，部门级角色要求在该部门直接有效任职，不自动覆盖下属部门。岗位不自动绑定角色；任职条件与权限需要均未改变时，不因岗位名称变化更换角色。
- UC-05/06 按“员工＋当前公司＋业务系统”计算权限。仅合并该公司、该系统内的有效角色；系统进入资格与功能权限也必须来自该公司、该系统。公司数据隔离、SELF 对象判断和过滤由业务系统实施。
- 任职变化后不再满足角色条件的授权立即失效；有其他符合条件的兼岗则保留该授权。员工全局停用使其全部业务授权及公司专员任命失效，不区分临时停用与离职。保留历史，不物理删除；恢复身份或任职不自动恢复失效授权，业务角色重新申请 OA 批准，专员由总管理员按 UC-07 重新任命。
- 操作目录明确支持范围：有明确本人语义的操作可支持 SELF/ALL，其他功能操作一期仅支持 ALL；SYSTEM_ACCESS 不适用范围，scope=null。配置及执行均校验所选范围属于支持集合。
- 员工、公司、部门使用稳定内部 ID；首次导入以源唯一用户名建立员工映射，组织分配稳定编码，更名不改变身份。人员变更模板明确新增任职、结束任职、停用、恢复等动作，不从文件缺行推断离职。
- 一期使用至少两个公司、两个系统的代表性数据，覆盖多角色、兼岗、公司隔离、本人范围、审批生效、撤销、失效及重新申请。其余资料后续逐步补齐。

以上为本轮已确认规则，详细流程与验收必须遵循；描述的是需求设计，不代表代码已实现或真实外部系统已完成对接。

## 1. 用例概述

| 项目 | 说明 |
| --- | --- |
| 编号与名称 | UC-03 为员工分配角色，与用例图编号对应 |
| 目标 | 将已批准并有效的业务角色分配给范围内员工，批准执行后员工通过角色获得权限 |
| 发起者 | 权限中心总管理员或公司权限管理专员；公司专员每公司 1～3 名；同公司专员共享共同管理范围，不限于自己申请的角色 |
| 外部参与者 | OA 系统按配置流程组织审批，返回可信最终结果 |
| 执行者 | 权限中心，通过 UC-11 接收审批结果并执行权限变更 |
| 触发 | 管理员在员工授权页面选择“分配角色”，或选择多名员工进行批量分配 |
| 前置条件 | 管理员登录且办理资格有效；目标员工有效并有适用的任职关系；角色已批准执行、可分配；角色所属系统有效 |
| 提交成功结果 | 保存待审批的员工角色分配方案，不改变员工当前权限 |
| 执行成功结果 | 原子保存批准的员工角色关系、执行状态及审计；下一次权限查询/校验反映新授权 |
| 失败保证 | 提交失败、审批驳回、方案失效或执行失败均不增加有效授权；不删除员工原有角色 |

UC-02 决定“角色拥有哪些权限”，UC-03 决定“哪些员工获得该角色”。角色本身获批不意味着所有员工都能直接获授；两项审批的对象不同。

### 统一管理与公司边界（本轮已确认）

“公司权限管理专员”即公司授权管理员（早期图中称部门授权管理员）；总公司和各分公司各自指定 1～3 名，可仅一名。公司人员范围按明确公司归属及所属部门层级计算，遇到另一个公司节点停止，不因总公司位于组织树上层而包含全部分公司。

权限中心总管理员可管理所有公司、所有系统及所有公司专员，也可办理 UC-02～04；公司专员仅在本公司获准系统内办理。双方的业务角色配置、分配、撤销均经过 OA。总管理员跨公司办理时仍明确目标公司；每份申请按一个公司归属保存，系统状态、目标合法性及版本校验照常执行。

一期不配置逐操作及 ALL／SELF 的申请上限，也不逐个指定可分配角色。获准系统目录内的合法权限可以申请，角色授权内容仍由 OA 审批。后台资格不自动产生外部业务系统进入权限。


## 2. 已确认规则与本稿约定

已确认：每个公司指定 1～3 名专员；同公司专员共享范围内配置申请及员工分配资格；角色单系统归属；员工可拥有多个角色并兼岗；本用例必须经 OA 审批。

OA 是外部系统。权限中心只提交固定申请、接收可信最终结果，并在批准后校验和执行；不规定审批人、审批层级或内部流转，也不把这些内容列为本项目待确认事项。业务必要性在外部审批中判断，不额外增加确认操作。

一期通过模拟 OA 返回批准/驳回结果验证交互即可，不实现审批页面或流程引擎；模拟结果走相同的来源校验、申请匹配和防重复执行逻辑，模拟入口仅用于开发与验收。

为使流程可实现，本稿采用以下设计约定：

1. 同一方案只办理一个来源公司（总公司或分公司）的授权，可包含多个员工和多个系统的角色；每条角色关系分别检查系统和组织归属，不创建跨系统角色。
2. 一期批量方案整体批准、整体执行；任一目标越权或执行失败，整体拒绝/回滚。若需只批准部分条目，先拆分方案并重新提交，不按原整批批准结果自行截取。
3. UC-03 只增加明确选中的关系，不执行“用本次列表替换全部角色”。撤销及替换中的删除部分属于 UC-04。
4. 一期默认为执行成功后立即有效、不设置授权到期时间；未来如支持期限，期限必须进入批准内容，不能在执行时临时扩大。
5. 管理员分配资格不等于自动获得业务角色。专员若作为目标员工，仍须走 OA；权限中心管理页面不能直接批准申请或借管理身份使授权生效。审批人员安排由外部 OA 负责。

### 系统进入权限（已确认）

角色分配本身不自动授予系统进入权限，专员应在预览中看到所选角色是否提供该系统进入资格。允许分配仅含功能权限的角色；若员工尚无该系统进入权限，功能授权关系可以保存，但不可使用，不自动追加进入权限。

进入权限和功能权限可来自当前公司、当前系统的不同角色；不同公司或不同系统的进入权限均不能代替。跨公司兼岗分别查询各公司权限。是否可用由 UC-05/06 按完整有效角色集合计算，不以专员可见角色范围代替员工实际授权集合。

### 申请归属、资格来源与自动执行（已确认）

角色和已提交申请归属目标公司，不归原申请人个人。原申请人离任或失去后台管理资格，仅影响其后续人工操作，不删除有效角色，也不单独使已提交申请失效。保留原提交人、提交时资格依据与固定内容；同公司有资格专员或总管理员可查看和处理后续事项，但不得改写原申请身份或批准内容。

提交时校验当前办理管理员并固定资格来源：总管理员使用全局管理资格，公司专员使用目标公司的任命及系统范围。UC-11 执行时核对提交时合法依据；总管理员原始申请不受公司专员的系统清单限制，专员原始申请仍须符合该公司当前获准系统范围。总管理员查看或处理专员申请，不改变原申请的资格来源，不能绕过已经缩小的公司范围。双方均明确目标公司，并按申请类型校验组织归属、目标条件及版本。

收到可信最终批准后，权限中心自动尝试执行合法的固定方案，不等待任何管理员点击接手或再次确认；原申请人离任、公司暂时没有专员均不单独阻止执行。短暂故障保留批准依据并由服务端重试，重试仍检查原资格来源对应的范围及目标条件；仅实际范围或目标条件不再合法时标记失效。员工角色分配仍须检查目标员工有效任职，撤销历史关联不要求目标员工仍在原岗位。

一期不提供人为取消已批准方案的入口，不以“失效”代替任意取消。合法方案执行或在短暂故障后重试；实际条件不再合法则失效并记录原因。执行成功后如需调整，按 UC-02～04 重新申请。未提交草稿的删除规则保持独立。

未提交草稿可由范围内管理员删除并记录删除事件，释放变更占用；新角色从未提交、从未生效且无引用时一并删除空草稿。已正式提交或已生效的角色/申请保留历史，不借删除绕过审批。正式角色配置提交后须至少包含一项权限（系统进入权限或功能操作均可），不产生已生效空角色；清理员工授权走 UC-04。


## 3. 输入、输出与授权对象

| 输入 | 含义 |
| --- | --- |
| 来源公司（总公司或分公司）/授权组织 ID | 明确本次授权由哪一组织负责；后端检查，不能相信请求任意填写 |
| 分配明细 | 明确的“员工 ID＋角色 ID”配对列表；批量选择产生的组合须逐条可预览，不隐式给全部员工分配全部角色 |
| 角色有效配置版本 | 记录审批时引用的已生效角色权限版本，防止审批期间角色内容改变 |
| 授权关系基础状态/版本 | 识别目标关系是否已有、被撤销或在审批期间变化，防止旧批准通知恢复已撤销或已失效权限 |
| 分配原因 | 例如职责需要、入职授权或兼岗授权，作为审批和审计依据 |
| 方案/编辑版本、提交请求编号 | 用于共同编辑冲突检测、重试幂等和定位固定方案 |

操作者由后端登录上下文取得；员工使用稳定 ID/统一标识，不用姓名匹配。角色使用 ID 关联，编码全局唯一，名称仅显示。

输出分为两次：提交返回方案编号、状态、实际新增明细；执行返回执行结果、实际新增关系及审计关联编号。拒绝、无变化、待审批、已批准待执行与已生效不可混用。

权限范围 ALL/SELF 来自所选角色，专员不能在分配页面给单个员工改成另一范围。如需不同权限组合或范围，先通过 UC-02 配置合适角色。

## 4. 正常流程

| 步骤 | 管理员/外部系统操作 | 权限中心处理 |
| --- | --- | --- |
| 1 | 管理员进入员工授权页面 | 验证会话及总管理员或公司专员资格；总管理员可选全部公司和系统，专员按本公司获准范围展示员工和角色 |
| 2 | 选择一名或多名员工 | 展示可见范围内的任职、已有角色及授权来源；其他来源不可见不等于没有授权 |
| 3 | 为员工选择拟新增角色 | 仅展示获准分配且已生效的角色；支持同公司其他专员申请的角色 |
| 4 | 预览新增授权并填写原因 | 展示员工—角色配对、所属系统、角色权限摘要/数据范围、有效配置版本；标记已存在关系 |
| 5 | 管理员确认提交 | 后端逐条检查人员/组织/系统/角色范围、任职、有效状态及版本，去除无变化项，固定实际新增明细 |
| 6 | 管理员查看提交结果 | 事务保存方案、摘要、版本和提交记录，返回待审批；原有授权保持不变 |
| 7 | OA 按配置流程审批 | OA 对同一份员工—角色明细和角色版本作出结果；权限中心不建设审批引擎 |
| 8 | OA 交付最终批准结果 | UC-11 验证服务身份、方案及审批编号、内容摘要、最终状态和重复通知 |
| 9 | 权限中心执行方案 | 按原资格来源复核对应范围、员工任职/状态、系统/角色/权限状态、角色及授权关系版本；同事务增加全部关系、保存执行状态与成功审计 |
| 10 | 管理员查看结果；业务系统再次查询 | 页面显示执行成功；员工在各系统的有效权限按全部有效角色取并集，业务端仍需执行 公司数据隔离、SELF 对象校验和列表过滤 |

只收到 OA 批准但未成功执行时，页面显示“已批准待执行”或“执行失败”，不显示员工已获得权限。

## 5. OA、方案状态与重试

沿用 UC-02 的方案状态：DRAFT 草稿、PENDING 待审批、REJECTED 已驳回、APPROVED 已批准待执行、EXECUTED 执行成功、EXECUTION_FAILED 执行失败。INVALIDATED 已失效用于终止不能继续执行的方案。WITHDRAWN 已撤回作为可选扩展，一期不要求对接 OA 撤回接口；未支持时已提交申请不能本地直接取消或修改。

- 草稿可编辑；提交后员工列表、角色列表、角色版本和原因固定。改员工、增角色等均须重新提交审批。
- 驳回保留原方案和原因；复制成新草稿修改重提，不把原拒绝记录改成通过。
- 短暂数据库故障回滚后可以重试相同的已批准方案；重试仍按原资格来源检查对应范围、目标条件与版本。
- 目标员工调岗后不再满足所申请角色的任职条件、全局离职/停用，或角色配置版本改变、目标授权关系出现后续撤销等导致原方案不合法时，旧方案失效并重新申请；仍满足任职条件的调岗不单独导致失效。
- 同编号不同内容拒绝；重复成功通知返回已执行结果，不重复建立关系或记录新的成功授予事件。
- 审批未通过期间，员工原有授权不受影响。一次新增方案失败，不清除已有角色。

### 任职变化与待执行分配申请

判断的是目标员工当前是否仍满足所申请角色的任职条件，不以“发生过调岗”直接判定失效。公司级角色要求员工在对应公司有有效任职；部门级角色要求在对应部门直接有效任职，不自动包含下属部门。兼岗时检查仍有效的适用任职，不要求固定为提交时同一条任职记录。

同公司部门间调岗后仍符合公司级角色条件，其他范围、角色版本及关联版本均合法时，原批准方案可执行；离开目标部门且无该部门其他有效任职时，部门级角色的待执行分配申请失效。跨公司调岗但仍保留原公司合法兼岗，也按实际适用任职判断。批量中有一项不满足则整批不执行。此任职规则同时约束已生效授权的持续有效性。调岗后不再满足条件的授权由 UC-10 标记失效，历史保留；重新任职后按本用例重新申请，不自动恢复。已失效历史不能作为重复有效关系阻止重新申请。

### 多名专员共同办理与并发

角色不属于申请专员个人。甲创建的角色，乙可提出员工分配申请；同一方案允许公司范围内专员查看，草稿协作修改须校验编辑版本并记录操作者。已提交方案仍记录原提交人，不在其离任后悄悄改写申请身份。

不沿用 UC-02“一个角色只能一份未结束配置方案”的限制来锁住全部员工授权：不同员工可以同时申请同一个角色。对于相同“员工＋角色＋授权来源”的待执行新增关系，一期建议拒绝重叠提交并提示原方案，避免多人重复申请；数据库唯一约束兜底，提交与执行时均检查。

授予与撤销的并发需要统一的关系版本/串行执行规则：关系即使已撤销也保留足以识别版本的记录或历史标记，旧授予审批不得因记录被删除而被误判为首次授权。与 UC-04、UC-11 联合设计，不以通知到达顺序决定最终权限。

| 员工乙 | 桥梁分公司工程部 | 桥梁公司—项目系统—项目查询员 |

预览应明确显示 3 条新增关系，不能因为选择了 2 名员工、2 个角色就不加说明地产生 4 条授权。

审批执行前甲、乙不通过本次方案获得权限；执行后在各自已具备相应系统进入资格的前提下，甲可使用两个系统的相应功能、乙只获得项目系统相应功能。角色中的“查看/编辑本人”在员工甲身份下指员工甲本人，不指提交专员或角色创建人。

若员工甲还兼任其他分公司的岗位，其他分公司的角色与本次新增互不覆盖；本公司专员不能以兼岗为理由扩大到另一公司角色的管理范围。部门专用角色要求员工在对应部门直接具备有效任职，不自动覆盖下属部门，公司级角色要求在该公司具备有效任职；任职判断和管理员可操作范围分别校验。

建议页面分区：员工筛选、已有角色（只读）、拟新增角色、变更预览、申请原因、方案状态。按钮为“保存草稿”“预览”“提交 OA 审批”“取消”。已存在角色旁的取消勾选不得在本用例中暗中触发撤销。

## 7. 替代与异常流程

| 编号 | 条件 | 系统处理 |
| --- | --- | --- |
| E01 | 既无总管理员资格也无公司专员资格、会话无效、超公司/员工/角色/系统范围 | 拒绝整次请求；不披露越权目标的敏感细节 |
| E02 | 角色未批准执行，或系统无效 | 不可选择；伪造请求也在后端拒绝 |
| E03 | 员工不存在、停用、任职不满足 | 提交或执行时拒绝，审批不能替代资格校验 |
| E04 | 相同来源的有效角色关系已经存在 | 不重复插入，不修改原来源/有效期；提交前作为无变化项排除。全部无变化则不发起审批 |
| E05 | 多人批量中一项无效或越权 | 整体拒绝；不擅自用原整批批准结果执行剩余项 |
| E06 | OA 驳回（可选扩展：可信撤回） | 不新增授权，保留历史；修改后新方案重提 |
| E07 | 审批期间角色配置版本变化 | 不以新权限内容执行旧审批，失效并要求重新申请 |
| E08 | 原专员离任，或目标员工任职/角色状态改变 | 仅原申请人离任不阻止批准后自动执行；目标不合法时才失效重提 |
| E09 | 同关系存在未结束新增方案，或出现后续撤销／失效 | 重复方案冲突，陈旧授予失效；不能恢复已撤销关系 |
| E10 | 业务写入或成功审计写入失败 | 整批事务回滚，员工原有角色保留；执行失败记录在回滚后另行可靠保存 |
| E11 | 重复/伪造 OA 通知 | 合法重复成功通知幂等返回；无服务认证、非最终批准或内容不一致拒绝 |
| E12 | 管理员删除未提交草稿 | 记录删除、释放占用，不改变员工授权，不发起 OA 审批 |

## 8. 数据与事务边界

| 处理 | 读取数据 | 写入数据 | 一致性要求 |
| --- | --- | --- | --- |
| 选择员工和角色 | 办理管理员资格及对应管理范围、员工任职、角色/权限/系统、已有关系 | 无 | 分页查询；看不到的关系不能误删 |
| 保存/提交方案 | 当前资格、配对列表、角色版本、关系版本、重叠方案 | 方案、冻结明细与摘要、提交审计、防重信息 | 原子提交，不更新有效授权；并发提交同关系要受控 |
| 接收批准，UC-11 | OA 调用身份、方案、批准内容 | 已批准待执行状态、接收记录 | 可靠落地、幂等，不把批准等同于生效 |
| 执行方案，UC-11 | 提交资格依据及对应范围、目标版本、已批准明细 | 员工角色关系、来源、操作者、审批依据、执行状态、成功审计 | 整个批次同一本地事务；不能只校验后无锁地任意写入 |

逻辑实体：Employee、EmployeeAssignment、Role、RolePermission、EmployeeRole、AdminScope、AuthorizationChange 及其明细、AuditLog。角色定义和角色权限集合不由 UC-03 修改。等待 OA 期间不持有数据库事务。

单人/批量共享同一套规则。批量数量上限、分页和消息重试参数在接口设计确定，不据此承诺万人同时授权或特定性能。

## 9. 结构化功能分解草案

```text
员工角色分配
├── 读取范围内员工、角色及已有授权
├── 整理员工—角色配对明细
├── 校验总管理员或公司专员资格及对应范围、员工任职与角色可分配性
├── 去重与新增差异计算
├── 检查版本及重叠申请
└── 保存固定方案、提交记录并关联 OA

OA：对具体员工获得具体角色的必要性作审批
UC-11：验证最终结果 → 按原资格来源复核范围及目标版本 → 原子新增关系及审计
UC-05/06：读取当前公司、系统的有效权限；业务系统执行公司及本人限制
```

这是功能分解，不是把每一步建成独立服务。图中的 UC-03、UC-11、UC-05/06 仍为独立目标，不能因上述衔接就把所有连线都画成 include。

## 10. 验收示例

| 编号 | 场景 | 预期 |
| --- | --- | --- |

| UC03-T02 | 收到合法最终批准并执行成功 | 指定员工获得批准角色，关系及审计一致 |

| UC03-T05 | 相同有效关系重复提交 | 不重复授权、不覆盖来源，全部无变化时不发起审批 |

| UC03-T14 | 查询、编辑本人权限分配给员工甲 | 本人指甲；甲访问乙的数据被业务后端拒绝 |

### 重新申请与部门边界补充验收

失效历史关系不阻止新授权申请；新批准执行建立新的授权记录或版本，不复活旧记录。部门级角色不能分配给仅在其下属部门任职的员工。岗位名称改变但公司／部门任职条件及权限需要相同时保留原授权；离开适用部门且无其他适用兼岗时旧授权失效。
